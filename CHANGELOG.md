# Mimic Changelog

**Purpose**: Record what each release of Mimic changes for users and developers, what it claims with evidence, and what it does not claim.

Versions are git tags; `RunProperties/Version` in every HDF5 output and `metadata/` in every run directory record the exact build (from the first post-v1.2 build, the release name as well as the commit). There was no v1.1 release.

---

## Unreleased

### New capabilities

- **A vertical writer for forest-blocked horizontal datasets: `convert/mimic-convert/write_vertical_trees.py`.** `plan` derives every forest's halo total from a version 3 dataset and cuts the forests into files of contiguous `ForestIndex` ranges (by default at most 100,000,000 halos and 1,000,000 forests per file, a larger forest alone in its file), writing `file_plan.json`; `convert` writes any forest-blocked version 3 dataset, whatever its source route, as L-Halo binary in the record the named simulation package's `halo_properties.yaml` declares (the C layout, derived by the tool), with forests in ascending `ForestIndex`, records placed by `HaloRankInForest` and links mapped to forest-local ranks (a link that leaves its forest is refused), so the vertical driver's `UniqueGalaxyID` equals the horizontal driver's. Every file is re-read and its SHA-256 checked before it is renamed, a manifest records the conversion, a rerun resumes, a lock allows one `convert` per output directory, and an interrupt stops the run after the files in flight complete. `convert` prints its per-worker memory bound before it starts. The dataset must carry the dense `SourceHaloID` that version 3 datasets have; gapped datasets are refused. Exit 0 complete, 1 verification failure, 2 any refusal or other failure.
- **A new simulation package, `simulations/shin-uchuu-lhalo/`.** The cut Shin-Uchuu trees as L-Halo binary (`tree_type: lhalo_binary`), in the package's own 88-byte record in the horizontal dataset's native units, with run files for `halos-only` and `sage16`, a committed test-sized fixture the generic test tiers run on, and tests of the record layout and reader. There are now sixteen simulation packages. Its `last_file` is 360, the last file of the production dataset's plan: 361 files, 244,953,607 forests and 22,503,649,037 halos, 1,981,300,932,572 B, written by `write_vertical_trees.py` at commit `944364d4`. The largest forest (126,380,326 halos) needs about 165 GB of resident memory for `sage16` and about 143 GB for `halos-only` under the vertical driver, measured with the macOS allocator's large-block cache disabled (`MallocLargeCache=0`).
- **A reverse-direction cross-format identity gate.** `simulations/shin-uchuu-lhalo/_tests/scientific/test_cross_format_identity.py` compares vertical `shin-uchuu-lhalo` with horizontal `shin-uchuu`, for `halos-only` and `sage16` with fixed and dynamic timesteps. The shared harness `tests/framework/parity_gate.py` gains `GatePackage.vertical_dataset` beside `horizontal_dataset` (a vertical side that reads a dataset outside its package, run through a scratch variant of the committed run file that adds exactly `input.simulation_dir`, `input.first_file` and `input.last_file`), `GatePackage.header_source_format` (the dataset header's `source_format` pinned apart from the vertical package's `tree_type`) and an inventory proof that reads the conversion directory's `manifest.json`.
- **A harness option for a vertical conversion of a dataset.** `convert/mimic-convert/tests/run_generalisation_acceptance.py compare` gains `--dataset-source-format`, naming the dataset header's `source_format` when it differs from the reader the dump was made with, as for a Consistent-Trees ASCII dataset compared with its `lhalo_binary` conversion.

### Claims and limits

- **`sage16` on the production vertical dataset is bitwise identical to the cut horizontal run.** A vertical `sage16` run on the cut Shin-Uchuu dataset in `shin-uchuu-lhalo` (361 files, under `mpirun -np 4`) is identical, galaxy for galaxy, to the recorded cut horizontal `sage16` run of `shin-uchuu`: 2,059,547,378 galaxies over ten output snapshots (69, 52, 43, 40, 20, 10, 5, 2, 1 and 0), `UniqueGalaxyID` sets identical with no duplicates and all 42 fields byte for byte, 313,753,033 galaxies at z = 0. The 22 `mimic-plot` figures drawn from it with the `shin-uchuu` plot profile are byte-identical to the horizontal run's.
- **`halos-only` and `sage16` are gated at subset scale.** The cut Shin-Uchuu subset (406,668,896 halos, 7,206,195 forests) converted to L-Halo binary is read by Mimic's `lhalo_binary` reader exactly as its horizontal dataset says, halo by halo, link by link and bit by bit, and the gate passes all four legs bitwise in every field over eight output snapshots (`halos-only` 92,429,377 galaxies; `sage16` 60,033,537 fixed and 60,033,573 dynamic). A vertical `sage16` run under `mpirun -np 4` equals the serial run bitwise.
- **Not claimed.** No `hod` or `sham` identity, and no run of either on this package: the vertical created-record identity space does not fit int64 at its 244,953,607 forests with a largest forest of 126,380,326 halos, so the run logs that it cannot create records and a module that creates one is refused (`halos-only` and `sage16` create none). No production-scale identity for `halos-only` (it ran on file 0 alone, without a comparison), and no run of SAGE26 on the files.

### Developer-facing changes

- **A byte gate against an ancestor commit: `make tests-reference-identity REFERENCE_COMMIT=<hash>`.** A manual test that builds the reference commit (an ancestor of HEAD that ships the same run files and the package paths the legs select) and HEAD and requires per-`UniqueGalaxyID` byte identity, with the same files, HDF5 objects, attributes (apart from named provenance) and metadata, on the real mini-Millennium data for `halos-only` and `sage16`, both drivers, fixed and dynamic timestepping (eight legs); it fails rather than skips when a dataset is absent, and `REFERENCE_IDENTITY_HEAD_EXTRA_CFLAGS`/`_LDFLAGS` gate a candidate build flag. The worktree, reference and output-comparison helpers of `tests-snapshot-global-identity` moved into `tests/framework/parity_gate.py` for it, and that test's behaviour is unchanged.
- **`DEBUG_LOG` is free when debug output is off.** The macro now tests the log level inline, over state `src/util/error.c` exports, before any call, so a disabled `DEBUG_LOG` makes no function call and does not evaluate its arguments; it was a cross-file call on every use, including under `--quiet`. On mini-Millennium with `sage16` the default run is about 6% faster under both drivers (vertical 2.7804 s to 2.6004 s, horizontal 2.8763 s to 2.7085 s, means of 14 runs on one machine); every galaxy is byte-identical to the previous build, and no debug message changes. A call site's arguments must therefore not carry a side effect the program relies on (none in the tree does). The macro's two contracts are covered by `tests/unit/test_debug_log_gate.c`.
- **Each phase's dispatch lists are built once at startup.** `module_system_init()` now splits every non-empty FoF phase's entries into its full-halo, per-event and by-galaxy modules once, after every module's `init()` has succeeded, and `execute_phase()` walks those lists instead of testing every entry's mode on every call; it skips the galaxy loop in a phase with no by-galaxy module and the post-callback event dispatch when no event is pending. Dispatch order, event delivery and every galaxy are unchanged (byte-identical to the previous build). On mini-Millennium with `sage16` the default run is about 4.5% faster (vertical 2.4576 s to 2.3455 s, horizontal 2.5656 s to 2.4541 s, means of 40 interleaved runs on one machine). A phase configuration must not change between `module_system_init()` and `module_system_cleanup()`; `execute_phase()` refuses one with no matching dispatch list.
- **The vertical output buffer is seeded like the horizontal one and no longer zero-filled.** `load_unit()` seeds `ProcessedHalos` at the tree's halo count plus 5% headroom (at least 1,000 records) through `output_buffer_seed_capacity()` in `src/core/output_buffer.h`, the rule the horizontal driver already used, instead of five times the halo count, and no longer zero-fills it, since every reader is bounded by the output count. The run memory profile's `C` on vertical runs therefore now tracks the forest size: on mini-Millennium with `sage16` it reads 15,869 records (was 74,345) against `P` 14,648, and peak RSS falls from 0.071 to 0.037 GB. A tree whose output outgrows the seed grows the buffer as before. The FoF workspace keeps its seed (half the tree's halos, at least `INITIAL_FOF_HALOS`) as a rule of its own. `MAXHALOFAC` is removed and `HORIZONTAL_OUTPUT_SEED_HEADROOM` is renamed `OUTPUT_SEED_HEADROOM`. Every galaxy is unchanged.
- **Build flags measured, none adopted: the default stays `-g -O2`.** Six candidate sets were each timed against the default build on mini-Millennium with `sage16`, vertical and horizontal, back to back from the repository root (15 repeats, the first discarded; difference of means in standard errors, negative is faster), and each was gated with `make tests-reference-identity` against the `-O2` reference with the HEAD build under the set: all six gates passed, all eight legs byte-identical in every case. A set was to be adopted only if it was more than 2 standard errors faster on both drivers; none was. `-fno-math-errno`: vertical −1.16% (−1.4 SE), horizontal +6.41% (+2.7 SE), rejected for no resolved vertical saving and a slower horizontal mean (its after runs carry two elevated repeats, 3.035 s and 3.144 s). `-flto`: +1.80% (+1.5 SE) and −0.11% (−0.2 SE), rejected for no saving. `-O3`: −0.99% (−0.9 SE) and −1.86% (−3.6 SE), rejected because the vertical driver shows no resolved saving. `-fno-math-errno -flto`: −1.57% (−2.3 SE) and +1.39% (+2.6 SE), rejected for a slower horizontal mean. `-fno-math-errno -O3`: −2.79% (−3.7 SE) and −0.73% (−1.1 SE), rejected because the horizontal driver shows no resolved saving. `-fno-math-errno -flto -O3`: −0.49% (−0.7 SE) and −0.26% (−0.2 SE), rejected for no saving. No flag is adopted, so the default build and the user's output are unchanged. Bit-identity was proven on macOS arm64 Clang only: GCC's default `-ffp-contract=fast` can fuse multiply-add across inlining on targets with FMA, and CI's `ubuntu-latest` x86-64 default target has none, so a green CI run would not prove identity for an aarch64 Linux host; any future adoption must be weighed against that. The figures are from one dataset on one Apple M3 Ultra, with a few percent of run-to-run noise.
- **`scripts/benchmark_mimic.sh` passes `EXTRA_LDFLAGS` through to `make` and records it.** The link-step counterpart of `EXTRA_CFLAGS` (for example `EXTRA_CFLAGS=-flto EXTRA_LDFLAGS=-flto`) reaches the build, is named in the build log line and the run summary, and is written to the result JSON as `configuration.extra_ldflags` (`none` when unset); `--help` documents it.
- **`make tests` no longer runs the converter suite.** Its 1655 cases (about 6 min, against under 2 min for the rest of the suite) cover the one-off conversion tools, not ordinary Mimic development. Run `make tests-converter` by hand when a change touches the converter or a Mimic file it reads or builds (listed under Testing in the Developer Guide); CI still runs it.

## v1.5 (2026-10-17)

Mimic v1.5 distributes the horizontal driver over MPI ranks and sweeps its slabs in chunks, adds snapshot-wide physics modules and module-created galaxy records (a calibrated `sham` and the new `hod` package), and puts the Shin-Uchuu production dataset on the horizontal driver in a cut form that a 16 GiB-class laptop measurement fits (a proxy until a laptop of that class runs it). Version 3 is now the only horizontal format. The converter gains a dataset rewriter, a forest census and a bounded-memory validation mode, and the Consistent-Trees ASCII route follows the same identity convention as the other two. Each route's evidence is in the format specification's V3 Runtime Support table and its package README.

Read "Changes that alter output" before comparing catalogues or datasets across versions.

### New capabilities

- **Horizontal runs distribute over MPI ranks by forest.** `mpirun -np N ./mimic <run file>` on an MPI build now runs the horizontal driver on `N > 1` ranks (it was serial-only, and the v1.2 note below that says so is superseded). Each rank owns a contiguous range of forests, chosen as the minimum-makespan partition of the forests' peak occupancies (each forest's largest halo count in any one snapshot) and broadcast from rank 0, and reads only those forests' rows of every snapshot slab; links are rebased to local rows and a link that leaves a rank's range aborts as a cut forest. Tree-row identity is unchanged and created-record identity encodes the host's global row (`HaloNr + row_offset`, a new `struct RecordIdentitySpace` member), so a distributed run produces, per `UniqueGalaxyID`, the bytes the serial run produces at every rank count (gated at 1, 2, 3, 4 and 8 ranks). `input.retention_memory_ceiling_mb` and the retention accounting are per rank. Measured on the real micro-Uchuu box at `-np 4` against the pre-feature serial runs, with each forest weighted by its rows in the widest snapshot (the driver now weighs peak occupancy): `sage16`, `sham` and `hod` bitwise identical, per-rank peak RSS 0.53 to 0.73 GB against 2.24 to 2.45 GB serial, wall-clock 11.24, 2.25 and 2.34 s against 41.32, 8.49 and 6.26 s. A forest is never split, so the largest forest's share of the widest snapshot (micro-Uchuu 1.60%) bounds the saving; the Shin-Uchuu super-forest (61.86% of its widest snapshot) means forest sharding alone does not put that uncut dataset on small-memory nodes (the production dataset is cut; see the Shin-Uchuu entry). New reader contract: `open_run` takes `struct HorizontalOpenOptions` (`validate_columns`) and publishes `source_format`, `load_slab` takes a row range and publishes `row_offset`, and a new `scan_forest_index` hook streams the `ForestIndex` column; the property generator emits `mimic_tree_set_<role>()` for the five link roles.

- **A refusal for datasets that cannot be distributed.** A multi-rank horizontal run is refused at startup, after the dataset is opened, for a version 3 dataset whose `ForestIndex` is not non-decreasing in every snapshot (the message names the snapshot, the rows, the values and the dataset's `source_format`), and says to run with one rank (and, since chunking, `input.forest_chunks: 1`). The format document gains a non-normative note recording this consumer dependency; no format rule or `format_version` changes.

- **Output naming under MPI.** With more than one rank every rank writes one partition per requested snapshot, `<base>_<snap:03d>_task<task:03d>.hdf5` (empty partitions included), and rank 0 writes the master with `Snap<snap:03d>/File<snap:03d>_task<task:03d>` links. A run on one rank, including an MPI build at `-np 1`, keeps the serial names and master layout. `struct OutputPartitionSource` gains `partition_task(p)`.

- **The horizontal partition weighs each forest by its peak occupancy.** A distributed or chunked run's task and chunk cuts are the same minimum-makespan contiguous packing as before, but each forest now weighs its largest row count in any one snapshot instead of its rows in the widest snapshot alone. A range's summed peaks bound its rows in every snapshot, so forests that hold few rows in the widest snapshot but many in a later one (late-growing forests, such as the small pieces a forest cut leaves) no longer pack into one chunk that swells late. Task 0 computes the peaks at startup in one `ForestIndex` pass over every snapshot, which now also carries the forest-blocking check, so a dataset that is not forest-blocked is refused before any cut; the second pass places the row cuts as before. The weights stay 8 B per forest on task 0, freed before any generation is sized; the first pass allocates nothing per halo and adds 8 B × (total halos − the widest snapshot's halos) of startup reads (175.7 MB on micro-Uchuu, where the startup partition took about 0.11 s instead of 0.05 s with the files cached; about 176 GB on the 22.5-billion-halo Shin-Uchuu catalogue). A serial unchunked run is unchanged. Nothing is stored in the dataset and no run-file key is added. The partition log names the weighting and gives each task's and chunk's peak weight beside its rows of the widest snapshot. Galaxies do not depend on the partition: on micro-Uchuu the cuts moved, and `forest_chunks: 4` and `-np 4` runs of `sage16` and `halos-only` stayed bitwise identical per `UniqueGalaxyID` to serial. The forest census's partition simulation (`forest_census.py partition` and `cut`) weighs the same way and reproduces the driver's cuts.

- **Chunked slab streaming: `input.forest_chunks`.** A horizontal run can sweep each task's forests in `G` contiguous chunks (`input.forest_chunks: G`, an integer of at least 1, default 1, on one process or under `mpirun`), running the whole snapshot loop once per chunk with only that chunk's rows of every retained generation resident, so peak memory follows the widest chunk rather than the widest slab. The partition is two-level: the task ranges are unchanged and each is cut into `G` chunks by the same minimum-makespan rule, so on one task `G` chunks are the ranges `G` tasks would own. Output is unchanged at every `G` (same partitions, names, master and `TotHalosPerSnap`, galaxies bitwise identical per `UniqueGalaxyID`, and, on every chunked leg the gate checks (serial and MPI; the MPI task partitions concatenated in task order), in the same row order). `input.retention_memory_ceiling_mb` and the sizing apply per chunk; the width refusals and warning now name `input.forest_chunks` as the lever, and the `INT_MAX` record cap states that neither chunks nor tasks lift it. `modules.post_snapshot` modules do not run under chunking: `sham`, and `hod` with its audit configured, need `forest_chunks: 1`.

- **Two configuration rejections for `input.forest_chunks`.** A value above 1 is rejected for a vertical reader (which sweeps no slab), and for a horizontal reader together with a non-empty `modules.post_snapshot` (a chunked sweep never holds a whole snapshot, so the message says the snapshot scope needs `forest_chunks: 1`). Zero, negative, fractional, non-numeric, sequence and overflowing values are fatal at parse time.

- **Widened startup refusals.** The not-forest-blocked refusal also fires for a chunked run on a single task, with a message naming both the task count and `input.forest_chunks`; a dataset that is not forest-blocked cannot be chunked, exactly as it cannot be distributed.

- **Per-visit output and its failure window.** A horizontal output partition is now created by the first chunk that reaches its snapshot, reopened read-write and appended by each later chunk, and finalised (`TotHalosPerSnap` stamped) by the last. At `forest_chunks: 1` the same partitions, names and master are written and every galaxy is bitwise identical per `UniqueGalaxyID` to before. Under `G > 1` a partition is in flight from the first chunk to the last, so a failing run removes every partition of the failing task that is not yet final, while partitions finalised earlier survive.

- **Chunk gate legs and integration test.** `make tests-distributed` gains chunked serial legs at `forest_chunks` 2, 3 and 8 and MPI legs at `-np 2 × 2` and `-np 3 × 3` for `halos-only`, `sage16` and `hod` (through `forest_blocks_hod_chunked.yaml`, the fixture run file without its snapshot audit), with partition row-order checks on every chunked leg (serial and MPI; the MPI task partitions concatenated in task order), chunk-log checks and the refusal of `sham` and the shipped `hod` run file; the target runs 264 live checks in all. `make tests-horizontal-v3` gains `test_chunked_sweep.py` (serial identity at 1, 2, 3 and 8 chunks and 2 with `--compress`, idle chunks, and the multi-visit failure window).

- **Recorded memory and floor.** On `micro-uchuu-horizontal` (440,651 forests, 22,580,924 halos, widest snapshot 621,360 halos), single serial runs on one macOS host measured peak RSS of 2.452, 1.215, 0.577 and 0.307 GB for `sage16` and 4.998, 3.701, 2.477 and 1.453 GB for `halos-only` at `G` = 1, 2, 4 and 8, every run bitwise identical to `G = 1`; wall-clock stayed within about 6%. Those figures include freed generation buffers that macOS libc's large-allocation cache keeps mapped; with the cache disabled (`MallocLargeCache=0`) peak RSS tracked the accounted retention and fell nearly as `1/G` for both models (0.655 to 0.097 GB for `halos-only`, 0.698 to 0.102 GB for `sage16`, `G` = 1 to 8). A forest is never split, so the largest forest's share of the widest slab is a floor on what any task and chunk count achieves: 1.60% on micro-Uchuu, 61.86% for Shin-Uchuu's percolation super-forest in its uncut dataset (the production dataset is cut; see the Shin-Uchuu entry). Full Uchuu stays unclaimed.

- **Comparator flag and make target.** `scripts/compare_cross_format_identity.py --compare-created` compares created (negative-id) rows byte for byte, accepts the `_task###` names and treats a mix of suffixed and unsuffixed names as an input error. `make tests-distributed` (MPI required; `MPIRUN="mpirun --oversubscribe"` on small machines) proves serial-versus-MPI identity on a committed multi-forest fixture for `halos-only`, `sage16`, `sham` and `hod`, and runs an MPI control test of the collectives; the CI `horizontal-v3` job runs it.

- **Snapshot collectives and `snapshot_distribution`.** `process_snapshot` modules reach whole-population quantities through six core functions (`module_snapshot_rank`, `module_snapshot_sum_i64`, `module_snapshot_sum_f64`, `module_snapshot_min_max_f64`, `module_snapshot_any`, `module_snapshot_is_root_task`), the identity in a serial run. A module declares `snapshot_distribution: collective` in `module_info.yaml` (default `serial_only`); startup refuses a `serial_only` module under `modules.post_snapshot` when `NTask > 1`. `sham_rank_match` and `hod_populate` are ported with serial output unchanged; `module_snapshot_sum_f64` may differ from a serial sum in the last bits, which affects only `hod_populate`'s audit line.

- **Snapshot-wide modules: `modules.post_snapshot` and the `process_snapshot` callback.** A module can now advertise a fourth processing mode, `process_snapshot` (`PROCESSING_MODE_SNAPSHOT`), implemented by a `process_snapshot` callback family that receives a snapshot's whole processed population (Type 0, 1 and 2 galaxies across every FoF group) instead of one FoF workspace; a module advertises one typed callback per family it supports, and `init()` and `cleanup()` are shared. Such modules are listed under the new fixed run-file phase `modules.post_snapshot`, which only the horizontal driver runs: once per input snapshot, after that snapshot's FoF sweep and before it is inherited from or written, in YAML order. Only `process_snapshot` is allowed in the phase and it is not allowed in any FoF phase; each entry must be one `name: mode` pair (this rule now applies to every phase: a `pre_timestep`, `post_timestep` or `phases:` entry listing a second pair used to start the run and silently drop that module, and now stops it at startup), a module may appear once, a vertical run rejects a non-empty phase, and every violation stops the run at startup before any `init()`. A snapshot module may write galaxy properties only (halo fields are read-only) and cannot emit or consume FoF events. The `RunProperties/EnabledModules` record gains `post_snapshot` rows only when the phase is configured, so a run that does not use it records exactly the provenance it did before. `models/sham`'s `sham_rank_match` and `models/hod`'s `hod_populate` (below) are the modules that use it. Tests: a new model-neutral fixture `test_snapshot_fixture` and a `test_fixture` that now serves both callback families, plus three make targets, `tests-snapshot-global` (the phase, typed-callback, `sham` and `hod` batteries on the committed horizontal fixtures), `tests-snapshot-global-sham` and `tests-snapshot-global-hod` (each package's unit and end-to-end tests) and `tests-snapshot-global-identity` (a manual comparison proving that runs with the phase absent or with an empty list reproduce the pre-feature commit's output). The v1.2 "Not claimed" entry for snapshot-global physics modules no longer applies; `--skip` on horizontal runs and binary output from horizontal runs are still not implemented. See the User Guide, "Snapshot-wide modules".

- **Modules can create galaxy records: `module_create_record()` and created-record identity.** A `process_full_halo` module, in any FoF phase and under either driver, can now ask core for new galaxy records. Core stages each row during the callback and appends it to the FoF workspace when the callback returns, so the same snapshot's later modules, phases, substeps and by-galaxy passes see it as an ordinary row; the row is marshalled inside its host's output segment, and the next snapshot inherits it as a Type 2 orphan. A created row starts as a copy of its Type 0 or 1 host passed through the same orphan rule inheritance uses (`Mvir` and `Len` zero, infall fields from the host); the module sets what it owns. Created records carry a negative `UniqueGalaxyID`, `-(1 + ordinal + 1024 * host_key)`, deterministic for a fixed dataset and run file and independent of traversal order; tree galaxies keep their positive IDs, and the 1024 per host per FoF step is an identity radix, not a physics cap. The host key is the host's catalogue position (horizontal `row + rows_per_unit * snapshot`, vertical `halonr + rows_per_unit * forest`), so vertical readers gained one hook, `max_partition_unit_halos`, reporting the largest forest in a partition (answered from the headers by `lhalo_binary` and `lhalo_hdf5`, from the per-forest counts by `consistent_trees_hdf5`, and as unknown by `consistent_trees_ascii`). Each driver checks at startup whether the identity space fits int64 and logs the verdict (`Created-record identity space (...): ... fits int64`); a run that creates no record is never affected, and the first creation call in a run whose space does not fit fails with both numbers. The budget fits the committed fixtures, mini-Millennium and full Millennium under both drivers, and does not fit the vertical driver on Shin-Uchuu ASCII or full Uchuu (no horizontal Uchuu package exists, so its budget is not evaluated). By-galaxy, per-event and snapshot callbacks cannot create, and an event cannot name a row created in the same callback. Both drivers now hold their FoF workspace in one `struct FoFWorkspace` with one growth function; output is byte-identical with no module creating records (the disabled-mode identity gate and the `sage16` baselines are unchanged). The framework fixture `test_fixture` gained the optional `TestFixtureCreateRecords` parameter that the contract tests drive. The contract is the developer guide's "Record Creation Contract" and VISION Principle 4 gained the matching requirement.

- **New `hod` model package: a halo occupation distribution on the snapshot-global mode.** `models/hod/` ships one dual-mode module, `hod_populate`, which draws the Zheng, Coil & Zehavi (2007) SDSS `Mr < -20` five-parameter occupation (`log Mmin 12.02, sigma_logM 0.26, log M0 11.38, log M1' 13.31, alpha 1.06`, all run-file parameters) for every FoF host in `post_timestep`: a central gated by `<Ncen>`, then Poisson satellites that are created records placed at NFW radii inside the host's current virial radius (from its current `Mvir` at the snapshot redshift, not the peak-mass `Rvir` field inheritance keeps) with the Duffy et al. (2008) concentration (physical offsets converted to comoving, periodic wrap) and isothermal Gaussian velocities, from a counter-based random generator keyed on the host's ID so draws do not depend on traversal order. Satellites are regenerated on every output snapshot; inherited and tree-born Type 2 rows are retired to Type 3, and the `HODGhost` flag marks scaffold rows outside the sample, so consumers select `HODGhost == 0`. A whole-box audit in `post_snapshot` logs expected against realised density and satellite fraction per output snapshot. Run files cover the committed fixture, the real 100 Mpc/h micro-Uchuu box and the vertical mini-Millennium files, the package has five figures (`halo_mass_function`, `hod_occupation` with the analytic law overlaid, `hod_satellite_profile` for the radial and velocity profiles, `hod_correlation_function` from a new shared pair-count helper in `plot/mimic-plot/output_utils.py`, and `spatial_distribution`), and its tests run in `make tests-snapshot-global`. First real-data measurement (micro-Uchuu, eight output snapshots, single process): 7.7 s, 2.23 GB peak RSS, 3,114,016 rows written of which 10,986 are sample members, and every audit line within one Poisson standard deviation of expectation (5,359 realised against 5,341 expected at z = 0.0005, satellite fraction 0.185 against 0.181). Caveats, stated in the README and not claimed away: the fit's halo mass is 200 times the mean density and its cosmology differs from the catalogues', so the output demonstrates the framework with published parameters and is not a calibrated SDSS mock; there is no in-run `M_min` solve, secondary-property HOD or observational clustering overlay.

- **Millennium and mini-Uchuu run horizontally over the whole simulation.** `millennium-horizontal` (760,667,000 halos in all 512 files, with 15,026,757 gapped `Descendant` links, longest span 2) and `mini-uchuu-horizontal` (1,451,359,554 halos in all 128 files, adjacent links) now convert and run the whole simulations rather than files 0–15, and their parity gates ran over every file under `halos-only` with fixed and dynamic timesteps: horizontal output is bitwise identical, per `UniqueGalaxyID`, to the vertical `lhalo_binary` reader over the same files, in all 20 fields (148,798,431 and 299,185,269 galaxies over eight output snapshots each; the gates took 15 and 27 minutes). Both routes move from "files 0–15 only" to complete in the supported-routes tables. Nothing is claimed for `sage16` on either, or for equality across source formats. The horizontal run files and packages declare the full extent (`first_file: 0`, `last_file: 511` and `127`); the horizontal reader ignores these keys, and `mimic-plot` uses the package's extent as the denominator of the volume fraction. The vertical Millennium and mini-Uchuu run files still read files 0–15 and 0–3 so they stay quick to run. The Millennium `Vel` test range widens from ±5000 to ±6000 km/s because the whole catalogue reaches ±5243 km/s. Converting a source with this many trees needs a larger `--memory-budget-mb` than the default (which is refused), and the converter refuses a stage directory that holds a macOS `.DS_Store`; both are documented in `convert/mimic-convert/README.md`, with the measured storage, memory and time of the two conversions.

- **Shin-Uchuu's production dataset is version 3 and cut, and `sage16` is validated on it.** `simulations/shin-uchuu/snapshots` holds a forest-blocked version 3 dataset (22,503,649,037 halos in 70 snapshot files plus the `forests.h5` sidecar) in place of the version 2 conversion, which the horizontal driver refused to distribute or chunk and whose largest forest holds 61.86% of the widest snapshot. It was made from the version 2 conversion of the Shin-Uchuu Consistent-Trees ASCII catalogue, never from the ASCII, in two steps. **The migration** (an operation of `rewrite_trees.py`, since retired) gives an uncut version 3 dataset of 166,547,771 forests whose `sage16` run is bitwise identical to the recorded version 2 run: 2,058,518,068 galaxies over 10 output snapshots in all 42 fields, with every z = 0 science value equal to the version 2 reference's. **The cut** (`rewrite_trees.py cut`) partitions every forest into its z = 0 FoF groups, which is exactly the partition that cuts every co-membership (a pair of trees, one holding a FoF member of a group centred in the other) that ended before the final snapshot and keeps every one present at it; every z = 0 FoF group of the input is preserved exactly. 166,547,771 forests become 244,953,607 (8,053,562 split into 86,459,398 pieces) and 481,296,108 halos are promoted to centrals, none at z = 0. `sage16` on the cut dataset gives the uncut run's galaxies unchanged outside the split forests (all 42 fields bitwise except `UniqueGalaxyID`, the pairing key, with `UniqueCentralGalaxyID` compared through the pairing); inside them the differences are by design, reported and not gated (of their records, 1,338,523,829 are identical and 180,067,108 differ). At z = 0 the cut keeps all 244,953,607 centrals and an identical halo mass function, with 13,485 fewer satellites (313,753,033 galaxies against 313,766,518) and summed galaxy masses that move by at most 2.25% (black holes; stellar mass +0.27%, global baryon fraction +0.017%). The cut removes the floor: `sage16` at one task and `forest_chunks: 128` peaked at 6,170,116,096 B RSS, 0.575 of a 16 GiB laptop's 10 GiB usable budget. That figure is a **proxy**, a Mac measurement under `MallocLargeCache=0`, and becomes the laptop acceptance only when a laptop of that class runs it. No `hod` or `sham` identity is claimed on either production dataset (`sham`, and `hod` with its audit, need `forest_chunks: 1`, and neither was run on the cut dataset at production scale). The format specification's runtime-support table gains the `shin-uchuu` row. Its evidence differs in kind from the other rows', because the full catalogue cannot run vertical: the comparison with the version 2 run above, and a vertical-against-horizontal subset gate over the 2,744-file Shin-Uchuu subset whose four legs pass (`halos-only` 92,413,007 galaxies in all 20 fields, fixed and dynamic; `sage16` 60,016,178 fixed and 60,016,233 dynamic in all 42). `sage16` is now gated on three packages. The package README records how the dataset was made. The route available from the repository today is `convert_trees.py ingest --cut-table`, which converts the catalogue directly into its cut form; its equality with the rewriter's cut is shown on the subset and on micro-Uchuu only, not on the full catalogue. The shipped `halos-only` and `sage16` run files write output snapshots 69, 48, 44, 37, 32, 30, 27 and 24; the measurements above used 69, 52, 43, 40, 20, 10, 5, 2, 1 and 0.

- **`rewrite_trees.py` rewrites a version 3 dataset slab by slab: `noop` and `cut`.** `convert/mimic-convert/rewrite_trees.py` reads a version 3 horizontal dataset of a Consistent-Trees ASCII catalogue slab by slab and writes a version 3 dataset, for datasets with `links_adjacent 1` only (a gapped dataset is refused), with every scratch and output location an explicit argument. `noop` rewrites it under the identity table and must reproduce its input in every value, dtype and metadata item; `cut` rewrites it under a declared cut table. A cut table is a `forests.list`-shaped file that gives every tree root of the index files exactly one forest id and keeps an uncut forest's id; a split forest's largest piece keeps the original id and every other piece gets a fresh id above the catalogue's maximum, so every untouched forest keeps its `ForestIndex` and `UniqueGalaxyID`. An input holding an object or attribute the format does not define is refused by name. Each written slab is verified against its input before it is kept: links by row identity, and for a cut every FoF group as one run of rows from its central and every progenitor chain as exactly its descendant's progenitors, so a cycle is refused. The output is a converter-shaped workdir with a manifest binding every file's SHA-256; every snapshot file and the sidecar are flushed to disk before the rename, so an interrupted run resumes after its last verified slab and a resume under different arguments is refused. `rewriter.inputs.MEMORY_FORMULAS` states every memory term once. `noop` reproduces its input, and `cut` equals a conversion of the same ASCII under `convert_trees.py ingest --cut-table` with the same table (shown on the 2,744-file Shin-Uchuu subset and on micro-Uchuu); a rerun and a run killed and resumed give byte-identical datasets on the subset and on micro-Uchuu. Seven adversarial cut fixtures pass an independent reference leg in every field.

- **`forest_census.py` decides and records a cut table.** `convert/mimic-convert/forest_census.py` reads a horizontal dataset in bounded slab reads and measures its forests with five subcommands: `occupancy` (per-snapshot occupancy), `trees` (effective descendant trees, checked against the index files' tree roots and per-file row counts), `partition` (the driver's partition simulation), `table` (the decided cut table, every forest partitioned into its z = 0 FoF groups, with its record and summary) and `cut` (a cut's promotions, progenitor-order changes and affected histories, and the partition with the pieces installed). The rewriter reads the table through the same invariant checks. `trees` refuses a gapped dataset or an aggregate directory produced from another dataset before it loads the index files, an out-of-range `ForestIndex` is refused by name (exit 2), and `cut` checks that the installed partition's rows equal each slab's. The summaries of `table` and `cut` record the bytes they read and the peak resident set they measured, and `cut` records its first pass's time under `measurements`; the measured values differ between runs. On the production dataset the census's per-snapshot predictions equal the rewriter's cut in every snapshot.

- **The version 3 producer battery has two modes, and `convert_trees.py` separates a refusal from a failure.** `convert_trees.py validate` and `report` run one battery of 20 checks, in the default external-sort mode for every dataset or, with `--bounded`, in a bounded mode over an adjacent dataset (every snapshot file declaring `links_adjacent 1`; anything else is refused by name) that sorts and spills nothing. The two modes share one public interface in `validate_v3.py` and settle the same checks, names and verdicts; counts, examples and wording can differ. The bounded mode's working arrays are bounded by a ceiling the run prints at start; it refuses a `--memory-budget-mb` below the ceiling and a snapshot above `INT32_MAX` rows, and at Shin-Uchuu's size the ceiling is 40,531,696,078 B for the uncut dataset and 41,158,942,766 B for the cut one (`validate_bounded.py ceiling` evaluates it for any dataset). On two subset datasets the two modes give the same 20 PASS verdicts, the bounded mode peaking at 0.95 GB with no spill against 6.89 GB and a spill of 75.8 to 77.7 GB; its chain walk's time grows with the longest chain (about 7.6 µs per link) and was not measured at full scale. `validate` and `report` refuse an ASCII workdir that records no `identity_scheme: forest-rank`, before reading or writing anything. **Exit status:** `convert_trees.py` exits 0 on success, 1 when `validate` or `report` finds the dataset failing the battery, and 2 when a command is refused or stops on an error (bad arguments, a stage run out of order, an outdated workdir, a dataset the bounded mode does not take, an unreadable file); a script that tested for 1 on a refusal must now test for 2. `rewrite_trees.py` and `forest_census.py` also exit 2 on a refusal.

- **The cross-format comparator pairs by catalogue key and lineage, reports a cut's differences, checks that pairings persist, and holds less in memory.** `scripts/compare_cross_format_identity.py` gains `--match-by-catalogue-id` (tree galaxies paired by `MostBoundID` within a snapshot, for datasets whose forest enumeration differs), `--match-created-by-lineage` (created records paired by their birth host's `MostBoundID`, snapshot and creation ordinal) and, with `--cut-record` and the two sidecars, a cut-difference report in which every difference inside a split forest is reported and every one outside is a failure. In the two pairing modes each paired `UniqueGalaxyID` must keep its partner from one compared snapshot to the next (16 B per pair held between snapshots); that check cannot see an id relabelled identically in both runs, or across a snapshot where it is not paired. A run directory must hold its master file and exactly the partitions that master links, and the cut report needs the record's dataset identity to match one of the sidecars and the runs to carry `UniqueCentralGalaxyID`; each is an input error. **Exit status:** 0 no failed comparison, 1 a failed comparison, 2 a usage or input error, 3 a failure of the comparator itself (a traceback, which says nothing about the two runs). Pairing sorts int64 keys, and when every row is compared the comparator copies no run's records: its peak memory per row of one run is 57, 99 and 114 B (default, catalogue pairing and cut report), and the duplicate checks and pairing of 8 million rows per side take about 1.3 s against about 27 s with structured keys. Verdicts and report text of the default mode are unchanged.

- **Outputs name their release.** `RunProperties/Version/version` in every HDF5 output, `version` in the run-local `metadata/version_info.json`, and the startup banner carry the build's `git describe --tags` string: the tag name for a release build (`v1.2`), or the tag plus its distance and commit for a later build (`v1.2-3-g23da5ae9`, with `-dirty` when the tree had uncommitted changes). The commit, branch and dates are recorded as before; the attribute is additive, so `hdf5_format_version` stays at `1.2`. A build from a checkout without tags (a shallow CI clone) records the commit hash instead. The header is written by one script, `scripts/generate_git_version.sh`, for the Makefile and both test build scripts, which previously carried their own copies of the recipe.

### Changes that alter output

- **Version 3 is the only horizontal format.** See the retirement entry below; a version 2 dataset is not read and must be reconverted from source.

- **The Consistent-Trees ASCII route follows the forest-rank identity convention, and `micro-uchuu-ascii-horizontal` is a version 3 package.** The format keeps `format_version = 3`, and for `consistent_trees_ascii` `SourceHaloID` is the halo's 1-based position in (`ForestIndex`, `HaloRankInForest`) order, the convention the other two routes have, instead of a prefix sum over per-file units that inverted to a physical source row. Rows sort by that position and every slab is grouped by forest, so a dataset of this route is distributable and chunkable like the others. The adapter's unit is the whole forest (the inventory is one unit per forest and records no per-file summary), the converter's manifest binds an `identity_scheme` of `forest-rank` and refuses a workdir without it, the producer battery's position check gates all three routes (a sampled ASCII inventory fails it), and the acceptance harness's C-dump `compare` leg checks `SourceHaloID` on every route while `compare-extras` joins ASCII on the catalogue key (`SnapNum`, `MostBoundID`). Every payload value, every logical link target, chain order, `ForestIndex`, `HaloRankInForest` and tree-halo `UniqueGalaxyID` is the same as under the earlier convention, and with them every value a module's physics reads; the link columns are snapshot-local row indices and follow the row order, and because a module-created record's `UniqueGalaxyID` encodes its host's slab row, created-record ids may differ between conversions of one catalogue and are compared by birth lineage. **Datasets that do not conform:** a version 3 ASCII dataset written by `convert_trees.py` up to and including release v1.2, recognisable because its `SourceHaloID` is not its (`ForestIndex`, `HaloRankInForest`) position; it fails the producer battery and must be reconverted, a conversion workdir started under the earlier convention does not resume, and a distributed or chunked run refuses such a dataset at startup if its rows are not grouped by forest. **Package:** `simulations/micro-uchuu-ascii-horizontal/` reads a version 3 dataset (22,580,924 halos in 440,651 forests across 50 snapshot files, `links_adjacent 1`). **Gate legs:** the package's parity gate passes against the vertical `consistent_trees_ascii` reader for `halos-only` (4,409,643 galaxies over 8 output snapshots in all 20 fields, fixed and dynamic) and `sage16` (3,112,186 fixed and 3,112,152 dynamic galaxies in all 42 fields) and its vertical-path preservation stage passes; `-np 4` and `forest_chunks: 4` runs of both models are bitwise identical to serial, with the driver's forest-blocking scan passing over all 50 slabs; and a `sham` run is byte-identical to the same run on the earlier conversion of the catalogue (557,669 galaxies in 24 fields). The format specification records the convention in its errata and the runtime-support row.

- **`sham` is replaced by a calibrated global rank match, `sham_rank_match`.** The package's two legacy modules (`sham_assign_stellar_mass`, `sham_global_rank`), its vertical run files, its `parameter_units.yaml` and the properties only they used (`BulgeMass`, the metals masses, `StarFormationRate`, `ShamStellarMassNoScatter`, `ShamScatterDex`, `ShamOrphanAge`) are removed; the package is horizontal-only now. One dual-mode module ranks Type 0 and Type 1 rows with accumulated peak circular velocity `ShamVpeak` at or above `ShamMinVpeak` (a completeness floor; peaks accumulate in `pre_timestep` over every processed snapshot, and carried Type 2 rows are retired) across the whole snapshot in `post_snapshot`, and gives rank `r` the stellar mass at which the target's cumulative density equals `(r + 0.5) / V`, with ties broken by `UniqueGalaxyID`. The target is the Baldry et al. (2012) GAMA double Schechter, rescaled to the simulation's `h`, evaluated by a quadrature table and inverted by bisection against a double-precision reference script; candidates denser than the target's low-mass validity floor are masked (`ShamGhost = 1`, `StellarMass = 0`), never extrapolated, and startup fails if an output snapshot lies above the declared redshift window. There is no scatter and no orphan mode. First real-data measurement (micro-Uchuu box, snapshot 49, `ShamMinVpeak 80`): 5.25 s, 2.30 GB peak RSS, 557,669 rows written, 74,596 candidates with none masked (`SHAM audit z=0.0005 candidates=74596 assigned=74596 masked=0`), and the sample's stellar mass function matches the target within about one galaxy per 0.25 dex bin from `10^8.5 Msun` up; that is a target-recovery check on the ranked population, not an observational parity claim. The figures were rewritten for the new model (stellar mass function against its target line, stellar-to-halo and satellite-fraction relations, a correlation function by stellar-mass threshold) and the evolution figures and the occupation figure were removed from the package.

- **The horizontal micro-Uchuu packages are named for their source format, like the vertical ones.** The vertical packages are `micro-uchuu` (L-Halo binary), `micro-uchuu-hdf5` and `micro-uchuu-ascii`, and the horizontal packages now follow the same pattern: `micro-uchuu-horizontal` (version 3, from L-Halo binary), `micro-uchuu-hdf5-horizontal` (version 3, unchanged) and `micro-uchuu-ascii-horizontal` (version 3, from Consistent-Trees ASCII). Two names changed meaning: v1.2's `micro-uchuu-horizontal` is now `micro-uchuu-ascii-horizontal`, and v1.2's `micro-uchuu-lhalo-horizontal` is now `micro-uchuu-horizontal`. The `halos-only` and `sage16` run files, and the `output/<model>-<package>` directories they write to, carry the new names. A package's `snapshots/` link is machine-local, so after updating, point `simulations/micro-uchuu-horizontal/snapshots` at your L-Halo conversion and `simulations/micro-uchuu-ascii-horizontal/snapshots` at your ASCII one, and move or remove any old `output/<model>-micro-uchuu-horizontal` directory so a new run does not mix with it. The v1.2 notes below keep the names as released.

- **`convert_trees.py` exits 2, not 1, for a refused or failed command.** Exit 1 is left for a battery failure; see the battery entry above.

### Fixes

- **Three MPI lifecycle fixes, for every driver.** A fatal error on any rank under `NTask > 1` now calls `MPI_Abort` (after removing that rank's in-progress outputs), so the job ends instead of the other ranks hanging at the barrier; run metadata is written by rank 0 only instead of every rank truncating the same files; and every log line carries a `task <n>:` prefix when `NTask > 1`.

- **`--skip` redoes vertical partitions left in flight.** The vertical driver now creates a marker, `<OutputDir>/<OutputFileBaseName>_<NNN>.inflight` (one per partition, whatever the output format), just before it claims a partition's output files and removes it once they are closed; an orderly failure removes it with the partial outputs. A `--skip` resume redoes any partition whose marker exists, so the partial files that ranks killed by `MPI_Abort` (including the SIGXCPU time-limit stop) or a `SIGKILL` leave behind are no longer accepted as complete. Unmarked partitions are skipped or refused exactly as before, and output bytes are unchanged; a `--skip` resume of output written before this change sees no markers and behaves as it did. Horizontal runs still do not support `--skip`.

### Retired

- **Horizontal format version 2 is retired: the reader accepts version 3 only.** `read_horizontal_hdf5.c` and the horizontal driver carry no version 2 path, so a run opening any dataset whose `format_version` is not 3 stops at startup, naming the file and the version found ("this reader supports only version 3"; a missing snapshot-0 `format_version` is rejected the same way, and version 1 keeps its message that it must be reconverted from source). A version 2 dataset is reconverted from source with `convert_trees.py`. The version 2 converter side is gone with it: `convert_ctrees.py`, the version 2 writer, producer battery and report, `crosscheck.py` and the default version 1 mode of `mimic-topology-dump` (its `--source-payload` mode is the one mode), the ASCII preparation stages' release, finalize, batch and consumptive options, the rewriter's `migrate` operation (`rewrite_trees.py` offers `cut` and `noop`), the converter's legacy 108-byte scratch layout and its per-record source-coordinate stamps, and the version 2 input of the bounded reader and the census. The committed version 2 test fixtures, their generator, `check_fixture_conformance.py`, `make check-horizontal-fixture` and its CI step are deleted, and `make tests-distributed` has no version 2 refusal leg. The format document keeps its version 2 text unchanged under a historical heading and records the retirement in its errata. The retirement removes 22,479 lines and adds 3,846 across 150 files.

### Not claimed in v1.5

- Full Uchuu is not claimed: it is storage-bound before it is memory-bound, and its largest forest bounds any chunk. It has no version 3 package.
- No `hod` or `sham` identity is claimed on either Shin-Uchuu production dataset (the uncut migration or the cut dataset), and no distributed or unchunked run of the cut production dataset was made (that identity is measured at subset scale).
- The 16 GiB laptop acceptance is not claimed: 6.170 GB RSS is a Mac-measured proxy until a laptop of that class runs it.
- `sage16` is gated on mini-Millennium, micro-Uchuu from Consistent-Trees ASCII and Shin-Uchuu only, and Shin-Uchuu's evidence differs in kind (no vertical parity over the full catalogue).
- `convert_trees.py ingest --cut-table` is shown equal to the rewriter's cut on the Shin-Uchuu subset and on micro-Uchuu only.
- The bounded battery's chain-walk time at full Shin-Uchuu scale was not measured.
- `--skip` on horizontal runs and binary output from horizontal runs are not implemented.

### Developer-facing changes

- **Test outcome `NA` (not applicable), so SKIP stays loud.** A test that does not apply to the selected `MODEL`/`SIMULATION` pair now reports `MIMIC_RESULT: NA` (`TEST_NA_WITH` in C, `TestNotApplicable` and `result_na` in Python), which summary mode suppresses like PASS; SKIP keeps meaning "applies here but cannot run" and stays visible. Horizontal-only and vertical-only guards, fixture-package and default-baseline guards, and the `hod` and `sham` fixture cases under another simulation became NA; missing HDF5, data or fixtures, and a horizontal package with no committed fixture, stay SKIP. The harness helpers are renamed `not_applicable_if_selected_package_is_horizontal()` and `not_applicable_to_non_default_baseline()`, and every gate that must run its cases (`tests-horizontal-v3`, the snapshot-global battery, the distributed and disabled-mode identity gates, the CI horizontal-run check) now fails on NA as on SKIP. The never-runnable stub `test_unknown_module_error` is removed from `test_module_configuration.c` (the integration test covers it). Every test tier, including the converter, now ends with one per-case counts line (`passed`, `failed`, `skipped`, `n/a`); the converter's unittest suite joins the marker protocol through `tests/framework/unittest_runner.py`, and a failing pre-tier check is headed `=== CHECK FAILED: <check> ===`.

- **Test-suite changes.** `make tests-distributed` runs 264 live checks; `make tests-snapshot-global` runs 115 declared cases (45 + 12 + 27 + 31); the disabled-mode identity gate runs eight legs (`halos-only` and `sage16` on the vertical mini-Millennium and gapped version 3 fixtures, fixed and dynamic), and its comparator self-check logs and records how many injected-defect and control cases it ran instead of fixing a count. The `worked_ascii` fixtures of `micro-uchuu-ascii-horizontal` and `shin-uchuu` are rebuilt by thin `_tests/data/regenerate.sh` wrappers over `convert_worked_ascii.sh`, which converts the committed synthetic ASCII source and fails if the installed `snapshot_*.h5` files are not exactly the converted set. `ParityGate` threads a gate's named dataset through every stage (the Shin-Uchuu gate is a plain `ParityGate` and checks its pins without data), and `tests/framework/fs.py` provides the retrying `remove_tree` the gates use. The converter's writer tests live in `tests/test_hdf5_writer_v3.py`, and the version 2 reader's negative battery lives in `tests/unit/test_horizontal_v3_reader.c`.

## v1.2 (2026-09-30)

Mimic v1.2 adds a second processing driver and an input format for it. The **horizontal driver** processes merger trees one whole snapshot at a time, in increasing time order, alongside the original **vertical driver**, which processes one forest at a time. Horizontal input is a per-snapshot HDF5 format that Mimic reads through the `horizontal_hdf5` reader and that a new converter tool, `convert/mimic-convert/`, produces from the forest-ordered formats Mimic already reads. Both drivers share one processing model, one property system and one output writer, and the horizontal driver has been shown to reproduce the vertical driver's galaxy catalogue bit for bit on every route listed under Evidence below.

The release also carries a number of correctness fixes that change output relative to v1.0. Read "Changes that alter output" before comparing catalogues across versions.

This section records v1.2 as released. Version 2 of the horizontal format, `convert_ctrees.py` and `make check-horizontal-fixture` were retired in v1.5, and v1.5 supersedes the statements below that multi-rank horizontal execution and chunked slab streaming are not implemented.

### New capabilities

- **Horizontal processing.** `input.processing_order: horizontal` selects the horizontal driver; the default `vertical` is unchanged and every v1.0 run file still works. Startup validation rejects a reader and driver that do not match. Horizontal runs are HDF5-only, serial (`NTask == 1`) and do not support `--skip`; each restriction is rejected at configuration with a message that says so. See the User Guide, "Running Horizontal Input".
- **Horizontal HDF5 input format, versions 2 and 3.** The on-disk contract is `convert/mimic-convert/HORIZONTAL-HDF5-FORMAT.md`. Version 2 carries adjacent links only. Version 3 is lossless for any source Mimic reads: descendant links may skip snapshots, row indices are 64-bit, and each file's `/schema` group declares the source's native units and precision, which the reader checks against the simulation package at startup. Version 1 datasets are rejected outright (see below).
- **The merger-tree converter.** `convert/mimic-convert/convert_trees.py` converts L-Halo binary, Consistent-Trees forests-HDF5 and Consistent-Trees ASCII trees to version 3 through a package profile (`simulations/<package>/converter_columns.yaml`), with a read-only source inspector, a verified restartable pipeline, an independent producer validation battery and a conversion report. The legacy `convert_ctrees.py` still writes version 2 from Consistent-Trees ASCII. The manual is `convert/mimic-convert/README.md`, and the Developer Guide has a short orientation section.
- **Dynamic timestep scheme.** `TimestepScheme: dynamic` (default `fixed`, unchanged) sets the number of substeps per snapshot interval from the central halo's dynamical time, bounded by `MaxDynamicSubsteps` (default 200). Every HDF5 master file records `SubSteps` and `TimestepScheme` under `RunProperties`.
- **Galaxy identity across drivers.** `UniqueGalaxyID = halonr + multiplier × (forestnr_global + 1)`; the multiplier defaults to 10⁹ and can be raised per catalogue with `simulation.unique_galaxy_id_multiplier` for catalogues whose largest forest holds more than 10⁹ halos. Both drivers honour it and every HDF5 output file records the value used as `RunProperties/UniqueGalaxyIDMultiplier`.
- **Bounded retention for gapped input.** The horizontal driver keeps each snapshot's generation only until every later snapshot that one of its halos names as a descendant has been processed. The optional `input.retention_memory_ceiling_mb` stops a run before allocating a generation that would take the retained payload past the ceiling; it bounds admission, not process memory.
- **Eight new simulation packages.** Horizontal version 2: `micro-uchuu-horizontal`, `shin-uchuu`. Horizontal version 3: `mini-millennium-horizontal`, `micro-uchuu-lhalo-horizontal`, `micro-uchuu-hdf5-horizontal`, `millennium-horizontal`, `mini-uchuu-horizontal`. Vertical: `shin-uchuu-ascii`. Each package README gives its data provenance and, for a horizontal package, the conversion command that produced its dataset.
- **Memory profile.** The run memory profile reports peak RSS and the output-buffer, pool and galaxy terms; horizontal runs add the retention term.

### Changes that alter output

These change catalogue values or layout relative to v1.0. Each was deliberate, measured and baselined.

- **Eight core halo properties are double precision.** `Mvir`, `deltaMvir`, `CentralMvir`, `Rvir`, `Vvir`, `infallMvir`, `infallVvir` and `infallVmax` are written as float64 (float32 in v1.0). The change fixed a float comparison that froze an orphan galaxy's `Rvir` and `Vvir`, and two float locals in `sage16` reincorporation. The `sage16` physics baseline was regenerated; aggregate stellar, cold-gas, hot-gas, black-hole, cooling and heating totals on mini-Millennium agree with the v1.0 baseline to within 0.01 to 0.22 per cent.
- **`fix_flybys` removed from the Consistent-Trees ASCII reader.** The step demoted every FoF central except the most massive at each forest's final snapshot and merged unrelated groups; on Shin-Uchuu it put 33 per cent of z = 0 galaxies in one group. Runs over `consistent_trees_ascii` input change their z = 0 central and Type classification and agree with the `consistent_trees_hdf5` reader on population, Types and `MostBoundID` sets, as measured at z = 0 on micro-Uchuu when the fix landed. A pre-existing float32-level precision difference between the two readers (about 2 × 10⁻⁸ relative in `Mvir`) remains and is documented in the micro-Uchuu package READMEs.
- **Horizontal format version 1 rejected.** Version 1 datasets were written with `fix_flybys` applied. The reader accepts versions 2 and 3 only; any version 1 dataset must be regenerated.
- **Uchuu-family particle mass corrected** from 0.0325 to 0.0327 (10¹⁰ Msun/h) in `micro-uchuu`, `micro-uchuu-ascii`, `micro-uchuu-hdf5`, `mini-uchuu` and `uchuu` (the horizontal micro-Uchuu packages, new in this release, ship the corrected value). Mass-derived quantities (`Len`, the subhalo-mass fallback) shift by 0.6 per cent; topology is unchanged.
- **`Spin` is labelled as specific angular momentum** (`Mpc/h km/s`) in every package's metadata. Values are byte-identical to v1.0; only the label and its unit dimension changed.
- **HDF5 output layout.** `TotHalosPerSnap` is int64; `RunProperties/Version/hdf5_format_version` reads `1.2`. A horizontal run writes one partition file per requested output snapshot (`model_<snapnum>.hdf5`, zero-padded to three digits) plus the master, and its per-snapshot groups carry no `Ntrees` attribute or `TreeHalosPerSnap` dataset.
- **Unit checking.** Run-file scalar parameters whose declared units are dimensionally incompatible with the parameter's reference dimension are now rejected at startup.
- **Plot profiles.** List-form `xlim: [a, b]` overrides for the mass-function figures were silent no-ops in every shipped profile and are replaced by scalar `xmin`/`xmax`, so those figures' axes change. Evolution figures no longer skip when their first sampled snapshot is empty.

### Fixes

- The per-phase event buffer grows on demand; the fixed 4096-slot buffer aborted large runs.
- HDF5 detection in the Makefile works under GNU Make 4.x; `make` resolves Python from `mimic_venv` without activating it.
- Consistent-Trees readers stop with a clear error, instead of narrowing silently, when a forest or partition exceeds the `int` range.
- HDF5 version and run-property string attributes were written from literals shorter than their fixed 128- or 1024-byte string type, so the writer read past the end of each literal (an out-of-bounds read found by AddressSanitizer in every run; the bytes on disk were unaffected). Every fixed-width string attribute now goes through a zero-padded buffer. The unit-test build honours `EXTRA_CFLAGS` and `EXTRA_LDFLAGS`, so a sanitizer build instruments the C tests as well as the executable.

### New configuration surface

Run-file keys (all optional, defaults preserve v1.0 behaviour): `TimestepScheme`, `MaxDynamicSubsteps`, `input.processing_order`, `input.retention_memory_ceiling_mb`, `simulation.unique_galaxy_id_multiplier`. Make targets: `tests-converter`, `check-horizontal-fixture`, `tests-horizontal-v3`, `dump-ctrees-topology-tool`; `make tests` runs the first two. Build hooks: `EXTRA_CFLAGS` and `EXTRA_LDFLAGS` (see the Developer Guide for sanitizer builds). CI runs a second job over the committed version 3 fixtures on every push and pull request to `main`.

### Not claimed in v1.2

- Full Uchuu cannot be run: its largest snapshot cannot be held as a whole slab on any host this project has, and chunked slab streaming is not implemented.
- Nothing is claimed for whole-simulation Millennium or mini-Uchuu on the horizontal driver, and `sage16` is gated on the horizontal driver only for mini-Millennium and micro-Uchuu.
- No equality is claimed between packages built from different source formats of the same simulation.
- Multi-rank horizontal execution, `--skip` on horizontal runs, binary output from horizontal runs, snapshot-global physics modules and distributed snapshot processing are not implemented.
- No horizontal package runs the model-package test set: the `sage16` module tests read binary output, which a horizontal run cannot write, so a horizontal package's physics is covered by its parity gate instead. `micro-uchuu-hdf5-horizontal` has no committed test fixture yet, so its generic tiers skip (see `tests/README.md`).

### Developer-facing changes

- The converter lives at `convert/mimic-convert/`, parallel to `plot/mimic-plot/`, with its format specification beside it; `scripts/` holds build and developer tooling only.
- Source layout: `src/io/vertical/` (readers, formerly `src/io/tree/`), `src/io/horizontal/`, `src/core/vertical_driver.c` and `src/core/horizontal_driver.c`. `struct Halo.HaloNr` and the five tree-link roles are 64-bit through the input and driver seam.
- The property generator accepts `type: long long`; halo identity fields for horizontal input live on reader-owned slab arrays, outside the property system.
- Test framework helpers `tests/framework/parity_gate.py` and `tests/framework/schema_conformance.py` back every horizontal gate and schema test. The generic unit and integration tiers run on horizontal packages: `scripts/generate_test_inputs.py` shapes each generated run file by the package's declared `input.processing_order` (HDF5 output, no input file range), and a test that needs binary output, `--skip`, a file range or a vertical reader skips with a stated reason (`skip_if_selected_package_is_horizontal()` in `tests/framework/harness.py`; new tests take a run from `default_run_file()`). Six horizontal packages ship committed synthetic fixtures for this, each rebuilt by a `regenerate.sh` beside it: `mini-millennium-horizontal`, `millennium-horizontal`, `mini-uchuu-horizontal`, `micro-uchuu-lhalo-horizontal`, `micro-uchuu-horizontal` and `shin-uchuu`. `micro-uchuu-hdf5-horizontal` has none, and its run-file tests skip with the reason recorded in the generated manifest. Measured on the committed data, `make MODEL=halos-only SIMULATION=<package> tests-integration` gives 0 failures on all seven horizontal packages (39 to 42 before), skipping only the vertical-only tests; on the default pair the generated run files are byte-identical and the tier still gives 217 pass, 0 fail, 4 skip. CI's version 3 job also runs `make MODEL=halos-only SIMULATION=mini-millennium-horizontal tests-integration`.
- `docs/dev/` is Mimic's own development pathway; nothing outside it depends on it. The four documents in `docs/` remain the documentation of record.
