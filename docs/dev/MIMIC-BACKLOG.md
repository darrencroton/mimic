## Core

**Fixed-length array properties of any length (design; L).** The property generator's `TYPE_MAP` (`scripts/generate_properties.py`) has three-element vectors (`vec3_float`, `vec3_int`) and nothing of another length, so SAGE26's ten-bin per-substep star-formation histories became 60 scalar properties in `models/sage26/model_properties.yaml` (`SfrDiskBin0` to `SfrDiskBin9` and their metal and bulge companions). Generalising to `vecN` touches the C struct field, the HDF5 array type, the binary layout, the run-local `output_schema.json`, per-element `output_convert`, the plot readers and the `sage26` comparator's `field_map.yaml`; migrating `sage26` changes its output schema, so it is a versioned change. Waits for a second consumer: design it when the next ported model with histories arrives, not before.

**`output_convert` cannot express a left-associated unit chain (low value).** SAGE26 writes several rates through chains like `(x / UnitTime) * UnitMass / SEC_PER_YEAR` whose rounding differs from a single factor; `models/sage26` reproduces them with `sage26_finalize_cooling_heating`. An `output_convert` taking an ordered factor list would remove that module. Not worth doing unless another port needs it; recorded so nobody rediscovers the finalizer's reason.

**`MinDynamicSubsteps` is not an HDF5 `RunProperties` attribute.** `SubSteps`, `TimestepScheme` and `MaxDynamicSubsteps` are recorded there; the floor is not, because the reference-identity gate (`tests/framework/parity_gate.py`, `compare_attributes`) requires the attribute-name set to match the reference commit exactly, so adding one would fail every gate run against a pre-change commit. The run's `metadata/` copy of the run file records it. To add it: give the gate a named allowance for an attribute present only in the candidate (in the style of `VERSION_ATTRIBUTES`), record the attribute in `src/io/output/metadata_hdf5.c` beside `MaxDynamicSubsteps`, and extend `tests/integration/test_output_formats.py`. Worth doing with the next deliberate metadata addition.

**The micro-Uchuu cross-format gate excludes the schema's `source_md5` without binding it.** `SCHEMA_PROVENANCE_KEYS` in `simulations/micro-uchuu-ascii-horizontal/_tests/scientific/test_cross_format_identity.py` drops the key from its schema comparison, on the same reasoning as the standing rule in the gates' shared comparison (`schema_provenance_problem()` in `tests/framework/parity_gate.py`, which accepts a schema that differs in `source_md5` alone): the hash describes the generator and its inputs, not the schema. The shared rule also requires each side's value to be the digest its own build generated; this gate does not. To unify them: use the shared rule here when the gate is next re-anchored, and run it once on the real micro-Uchuu data (hours). Not urgent: the two agree on what is permitted, and differ only in that check.

**The shipped `sage26` run files and SAGE26's substep floor (decision).** SAGE26 floors its adaptive substep count at 10 and caps it at 30 (`N = min(30, max(10, ceil(10 dT / t_dyn)))`); the shipped `sage26` run files use the fixed scheme with `SubSteps: 10`, and that difference alone accounted for 180 failed thresholds against SAGE26 in the campaign's own-core comparison (item 04 of the core-alignment set, `tools/core-alignment/items.md` on the `sage26/import-tooling` branch). The run files can now express SAGE26's rule without a patch: `TimestepScheme: dynamic`, `SubSteps: 10`, `MinDynamicSubsteps: 10`, `MaxDynamicSubsteps: 30`. Switching them changes the package's written output, so it needs the baseline regenerated (the procedure in the docstring of `models/sage26/modules/_tests/test_scientific_sage26_physics_baseline.py`), a rerun of the SAGE26 comparison with the tooling on the `sage26/import-tooling` branch, and a CHANGELOG entry under *Changes that alter output*. Decide with a measurement; alignment item 04 can then be retired from the set.

**`create_test_param_file(first_file=, last_file=)` has no effect on the default run file.** The shipped run file carries an explicit `input: first_file / last_file`, which takes precedence over the range the harness writes into the simulation config (`tests/framework/harness.py`). `tests/integration/test_unique_galaxy_id_encoding.py` and `test_missing_input_files.py` each work around it by rewriting the run file's `input:` section. The fix is for the harness to write the range into the run file's `input:` section when either argument is given; check every caller that passes a range before changing it.

## Rate mode

**The implicit scheme is first order and experimental (design; L).** It is Patankar-Euler with a twice-filtered error estimate in `src/core/rate_integrator.c`. Its block solve is exact to rounding at production block sizes (the post-implementation review measured closure within 2.1% of its tolerance and the tracer bound within 4.6% on blocks of 6 to 40 reservoirs plus tracers), but a first-order scheme with per-step error control spends steps in proportion to 1/error. A second-order scheme on the same solve (a modified Patankar-Runge-Kutta 2,2 scheme, for example) is what would make it a stiff production option. Waits for a model that needs it: the fork of `sage16` onto the rate mode decides. Accept when a stiff case from the post-implementation review (`MIMIC-COUPLED-RATE-REVIEW-2026-11-14.md`, in `archive/dev-plans/` since 2026-11-14; `test_stiff_rates` in `tests/integration/test_rate_phase.py` carries the case) reaches its tolerance in a step count that does not grow as 1/error, with the unit and battery tiers green.

**Negative rounding residues from discrete modules: refuse or clamp (decision).** The gather (`load_row()` in `src/core/rate_assembly.c`) refuses a reservoir or tracer that is negative or not finite when a rate segment starts, naming the property and row; it never clamps, because clamping changes a conserved total. A SAGE-style discrete module (`x -= f * x`) can leave such a residue. Decide when the first model package puts discrete modules beside a rate phase: either the modules clamp their own residues (no core change), or the core clamps below a stated threshold and records the amount in the ledger. Accept with a test that leaves a residue of each sign beside a rate phase and shows the chosen behaviour.

**A yield-fed tracer that overtakes its parent is fatal by design (decision).** `tracer_bound` fails a tracer with sources of its own that ends above its parent, so a yield law must vanish as the pristine part of its parent is exhausted. The two schemes can differ in when a law that does not vanish fails: with the fixture's rates scaled by 1e5 the explicit scheme ended in `tracer_bound` on the yield where the implicit scheme completed. Revisit if a real metal-yield law makes this routine; the decision is whether such a tracer may legitimately pass its parent.

**Memory of a whole-group component is unbounded (measure).** With `to_record: central` or `reads_central` the whole FoF group is one component. For a model with 20 reservoirs and 20 tracers the review estimated about 1.5 GB of integrator scratch for a 100,000-row group under the explicit scheme and 2.7 GB under the implicit one, before the assembly's own tables, and nothing bounds it. Measure on the first real model and decide on a refusal or a bound; the per-segment rebuild of flux lists and blocks (250 to 300 ns per segment in the per-galaxy domain) is the matching cost lever (cache them per plan).

**The segment ledger loses sensitivity in rich groups (low value).** The closure tolerance's `L` is a component-wide maximum, so a central receiving one transfer per satellite has `L` of about the satellite count (documented in `src/core/rate_integrator.h`). A tighter valid form multiplies fan-in by the gross amount moved rather than by the total; it needs one accumulator per total and a proof. Only if ledger sensitivity in large groups comes to matter; accept with a planted imbalance detected in a 10,000-satellite group.

**`DeclaredDiscreteChanges` counts per total only (low value).** A row per (phase, unit, total) would say which declaration covered a change and still merge by integer sum. Worth doing with the first model that declares `changes_totals` in earnest; accept when the run's provenance names the declaring unit.

**The failure file does not carry the run-file path (low value).** It carries the build's version and commit, the phase, snapshot, substep, base time and redshift; the run-file path is a local in `src/core/main.c` and needs plumbing to reach the writer. Do it with the next change to the failure file; accept when a failure file written by a run names the run file it came from.

**The rate mode has not yet run in CI (check).** It was developed on macOS with Apple clang. On 2026-11-14 the three CI jobs were run by hand at `ef6899be` in an Ubuntu 24.04 container (gcc 13.3, Open MPI 4.1.6) and passed: on arm64 every step of all three jobs, and on emulated x86_64 the default and horizontal jobs without the converter and bench suites. The builds gave no compiler warning and the bit-exact unit tests agree on both architectures. A container run as root skips four permission-denial cases, which fails the two steps that require them; they pass as an unprivileged user, as on the CI runner (rerun on arm64 only). CI itself runs when the branch reaches `main`; watch the first run. Bit-identity is claimed per binary only. Accept when that CI run is green or each failure is explained.

## `sage26`

**Findings of the alignment experiments with no compared effect.** From the campaign's alignment work: the merger-clock event's `Age` is rebuilt by addition (`shared/sage_merger_clock.h`), `Mvir` is float-rounded there, `MergTime` is never compared by the instrument, and one unattributed radius difference remains at the R1 rung (halo 10233590, snapshot 63, 1.7e-4 relative). None reaches a compared property on mini-Millennium. Do nothing unless a later reference differs there; this paragraph is the record.

**The CGM-regime draw's key.** The package's draw is keyed on `(UniqueGalaxyID, snapshot, salt, ordinal)` (`shared/sage_keyed_draw.h`). If a future SAGE26 keys its own draw (the hand-back below asks for it), re-key the package to match so the two codes can be compared on Mimic's own core without the alignment set, then re-measure T1 unaligned.

**The Linux floor.** `sage26`'s scientific baseline reproduces on Linux to 5.5e-4 relative at worst (CGMgas at snapshot 63; Ubuntu 24.04, gcc 13, arm64, 2026-11-08), under CI's relaxed 1e-3 gate; recorded in the baseline test's docstring, the CHANGELOG's *Claims and limits* and the CI job's comment. If a Linux host becomes the owner's primary, measure the floor on x86-64 too and decide whether the package deserves its own committed Linux baseline instead of the relaxed gate.

**The import tooling lives on branches, not on `main`.** The function-level oracle (its mains, 1,044 fixtures and the 24 oracle unit tests), the galaxy-by-galaxy comparator with its field map and controls, and the ten-patch core-alignment series were removed from `main` in the v1.6 cleanup so the package is user-facing; they are kept whole on `sage26/import-tooling` (the pre-cleanup `main`, with `docs/dev/SAGE26-IMPORT-TOOLING.md` describing each piece) and the patches as commits on `sage26/core-alignment`, both pushed to `origin`. The oracle fixtures compare bit for bit only on the Apple clang build they were generated with; regenerating them on a new toolchain is described on that branch.

**SAGE26 v1.0.** When SAGE26 tags its v1.0, bring the package up to it: diff SAGE26 at the tag against the commit the package follows (`11b1ae8`), carry each physics change into the owning module with its tests, refresh the baseline, and re-measure agreement with the tooling on `sage26/import-tooling` (comparator against a SAGE26 v1.0 run on mini-Millennium; the alignment set, re-based on the new `main`, for the bit-for-bit check). Record the result under *Claims and limits* and in `models/sage26/README.md`, *Agreement with SAGE26*.
