# Mimic Chunked Slab Streaming Plan

**Status:** Concept note. Not scheduled. Captures the reasoning behind a generic, host-independent memory bound for the snapshot-ordered driver, raised by the Shin-Uchuu production run's P5 memory re-projection (2026-09-04), so it is not re-litigated or lost. Deliberately left unresolved until promoted to a requirements brief — no scope is committed here.

**Date:** 2026-09-04

---

## Goal

The snapshot-ordered driver's peak memory scales linearly with the halo count of its single largest per-snapshot slab, not with simulation depth or total halo count — `docs/VISION.md` Principle 5 states the latter as a deliberate design guarantee ("bounded by the current processing scope... regardless of simulation depth or total halo count"), and the driver delivers it: two live generations, no accumulation across forests processed. But neither the vision nor the shipped driver bounds the **size of a single slab itself**. `SHIN-UCHUU-CONVERSION-PLAN.md`'s own measured fit, `peak ≈ 1.221 GB + 1,340.6 B/halo × N`, is linear in N with no ceiling — N is set entirely by whatever the input simulation's own halo-count history happens to produce, and a single unusually large snapshot forces every generation touching it to be fully resident regardless of which physics modules are configured. This note captures the idea of processing a slab in bounded-size chunks instead of holding it whole, so peak memory becomes a function of a chosen chunk size that Mimic controls, not of the largest slab any given simulation happens to produce. The goal is a capability that is reusable across simulations and hosts, not a one-off fix sized to Shin-Uchuu.

## Motivation: the concrete case that raised this

Shin-Uchuu's production `sage16` run hit exactly this gap. `SHIN-UCHUU-CONVERSION-PLAN.md`'s P5 step re-projected the run's peak memory from the real production conversion report and found the largest slab — snapshot 34, 519,342,987 halos — is 46.5% above the pre-measurement projection the whole memory budget had been sized against, putting the peak at ≈639–697 GB against ≈540 GB available on the Mac Studio (M3 Ultra, 512 GB installed). The plan's own P5 branch names three unspecified levers for exactly this situation: "streaming the slab, splitting the largest snapshot, or a smaller retained generation" — none designed. The immediate resolution was to relocate this one run to a large-memory node on the Ngarrgu Tindebeek (NT) supercomputer, which needs no driver change at all. That is the right call for *this* run, but not a durable answer:

- **This Shin-Uchuu run is explicitly not a one-off.** `sage16` and future/new model packages are expected to run against Shin-Uchuu for years — today's run is a scientific verification that the conversion itself is sound, a stepping stone rather than a destination.
- **A local-machine run of Shin-Uchuu is wanted eventually.** Relying on NT bigmem-node access indefinitely is a dependency the owner does not want; the whole reason the rehearsal subset and the compact-previous-slab-projection mitigation exist is to keep a single workstation viable.
- **Larger future simulations are expected to have the same shape of problem, or worse.** A generic bound on per-slab memory is worth more the larger and lumpier the next simulation's halo-count history turns out to be — this is squarely a "scale" investment in the same sense as the pathway's own step 1 framing, not a Shin-Uchuu-specific patch.

A closely related, narrower mitigation already exists and was deliberately deferred rather than built: the **compact previous-slab projection** (`SHIN-UCHUU-CONVERSION-PLAN.md` → "Delegated obligation: the snapshot-driver memory fallback"), which replaces the retained previous generation's full raw slab with a `{int32_t Len, int32_t NextProgenitor}` projection — the only two fields ever read back from it. That mitigation was priced at the Shin-Uchuu production scale and found to save only ≈112 B/halo, closing at most ≈49 GB of the current gap — nowhere near enough on its own once the real (not projected) largest slab is used. It is a special case of the idea this note generalizes: reducing what must be resident **per halo**, rather than reducing how many halos of the *current* generation must be resident **at once**, which is the chunking/streaming idea below. The two are complementary, not alternatives.

## Design direction: bounding by chunk, not by slab

The candidate direction: instead of loading and holding an entire snapshot's slab (both the "current" generation being built and the retained "previous" generation) fully resident, process each slab in bounded-size row-range chunks, so peak resident memory for a generation is a function of the chosen chunk size rather than of N. The on-disk format already supports this access pattern without a format change — `SNAPSHOT-HDF5-FORMAT.md` specifies chunked, uncompressed SoA datasets (`chunks=(65536,)` for scalars, `chunks=(65536, 3)` for vectors) specifically for efficient slab reads — so the work is in the driver's in-memory handling, not the on-disk contract.

This is not free of real constraints, and none of them are resolved here:

- **Inheritance crosses the chunk boundary by construction.** A halo's properties at the current snapshot depend on its progenitor(s) in the retained previous generation, and a FoF group's members are not guaranteed to be contiguous in on-disk row order in a way that aligns with an arbitrary chunk boundary. Any chunking scheme must either guarantee chunk boundaries respect whatever locality the inheritance and FoF-workspace logic actually requires, or provide a mechanism for a chunk to reach across the boundary for the specific fields it needs (which is closer to what the compact previous-slab projection already does for the previous generation specifically).
- **This is snapshot-driver-specific, not a tree-driver concern.** The tree-ordered driver already bounds memory per-forest by design (Principle 5's other half); it has no analogous single-slab pathology because it never materializes a whole snapshot's population at once. Nothing here should be read as implying the tree driver needs equivalent work.
- **Interaction with the existing "two live generations" invariant.** Chunking should refine what "one generation resident" costs, not change the count of generations the driver reasons about — but that needs stating precisely once a design exists, since it is exactly the kind of architectural invariant `mimic-architecture-contract` exists to protect.
- **Interaction with output partitioning.** Each requested output snapshot already writes to its own HDF5 partition (`SNAPSHOT-OUTPUT-PARTITIONING-PLAN.md`, D5(a)); a chunked read/process path needs to keep producing the same per-partition output, just from smaller pieces assembled over time rather than one full in-memory pass.

## Candidate approaches (unevaluated)

Recorded as starting points for a future design pass, not as a decision between them:

1. **Stream the current generation in row-range chunks at read time**, holding one chunk resident while the retained previous generation stays at its existing (or the already-specified compact) footprint. Closest in spirit to the plan's own "streaming the slab" phrase.
2. **Split disproportionately large snapshots into sub-partitions** processed and reconciled sequentially, treating an oversized slab as several bounded ones rather than changing the read pattern of every slab uniformly.
3. **Extend the compact-previous-slab-projection idea to the current generation too**, keeping only the fields a later snapshot's inheritance will actually need resident at full population, with everything else re-read or recomputed on demand.

## Open questions

- **The forest/FoF-locality boundary constraint.** Must a chunk boundary never split a FoF group or an inheritance relationship mid-processing, and if so, does that require re-ordering on-disk row layout, an auxiliary index, or a different in-memory join strategy? This is the central unresolved question and likely determines which candidate approach above is even viable.
- **Whether chunk size is a run-file-configurable knob, auto-derived from available RAM at startup, or fixed.** Not designed.
- **Whether this should absorb the already-specified-but-deferred compact previous-slab projection**, making that mitigation a special case of a more general mechanism rather than a separate delegated obligation living in `SHIN-UCHUU-CONVERSION-PLAN.md`.
- **Whether a chunked read path changes anything about the cross-format identity gate or the snapshot-ordered driver's determinism guarantees** (`MIMIC-DEVELOPMENT-PATHWAY.md` → "Standing Constraints": output identity deterministic across MPI task counts and equivalent driver inputs). A chunking scheme that is purely an internal memory-management detail, invisible to output, would not need to touch this — but that needs demonstrating, not assuming.
- **Relationship to step 4 (Performance).** `OPTIMISATION-SPECTRUM.md` explicitly defers SoA and batched-dispatch work because the coupled-rate work "deletes state that SoA would transpose" — eight `output: false` transport-scratch properties that stop being galaxy state at all under that formulation. Whether chunked slab streaming interacts with that deferral, or is orthogonal to it (a memory-bound concern rather than a dispatch-throughput one), is unexamined here.
- **Whether this belongs in the numbered pathway at all, or stays a standing infrastructure concern.** Unlike `MIMIC-SNAPSHOT-GLOBAL-MODULES-PLAN.md` (step 2) and `MIMIC-DISTRIBUTED-SNAPSHOT-PLAN.md` (step 3), this note needs no prerequisite step to exist — it addresses raw driver memory bounding independent of which physics modules run or whether MPI is in play. See `MIMIC-DEVELOPMENT-PATHWAY.md` for how it is currently cross-referenced.
