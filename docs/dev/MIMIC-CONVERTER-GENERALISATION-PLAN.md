## Goal

The `scripts/convert/` ctrees-ASCII-to-horizontal-HDF5 converter was built and validated for one simulation family (Uchuu/Shin-Uchuu, via `consistent_trees_ascii`), and its owner intends to generalise it so it can convert other simulations. This note captures two things that surfaced while discussing that intent, using the completed Shin-Uchuu production run as a concrete worked example: (1) the converter's column selection is currently hardcoded rather than declared, which is both the generalisation's central design question and the reason a later "I want that column back" request is expensive today; and (2) a candidate cheaper mechanism for adding a column to an *already-converted* dataset without repeating the full multi-day pipeline. Neither is designed, built, or validated. This document exists so a future session promoting this work starts from the reasoning already done rather than rediscovering it.

## Motivation: the concrete case that raised this

Mimic's own property system already treats a simulation package's available fields as declared metadata (`simulations/<sim>/halo_properties.yaml`, `docs/dev/SHIN-UCHUU-CONVERSION-PLAN.md`, the `mimic-properties` skill) — but the converter that *produces* the on-disk data for that package does not work the same way. Its source-column selection is a single frozen struct, `RECORD_DTYPE` in `scripts/convert/ctrees_parser.py` (reflowed here for width; fields, order, dtypes and `align=False` are as in the file):

```python
RECORD_DTYPE = np.dtype([
    ("id", "<i8"), ("desc_id", "<i8"), ("desc_scale", "<f8"), ("pid", "<i8"), ("upid", "<i8"),
    ("snap", "<i4"), ("Mvir", "<f4"), ("X", "<f4"), ("Y", "<f4"), ("Z", "<f4"),
    ("VX", "<f4"), ("VY", "<f4"), ("VZ", "<f4"), ("Jx", "<f4"), ("Jy", "<f4"), ("Jz", "<f4"),
    ("vrms", "<f4"), ("vmax", "<f4"), ("tree_root_id", "<i8"), ("forest_id", "<i8"),
], align=False)
```

Those 20 stored fields are **18 retained source columns** out of the 61 the real Shin-Uchuu source data carries — confirmed directly from `tree_0_0_0.dat`'s own header line on `nt.swin.edu.au` during the production run (`head -c 4000 tree_0_0_0.dat`; the file's own indexed header names and numbers each one) — plus two fields that come from outside the halo row entirely (see "The trap this framing hides" under Design direction below). A nineteenth column, `scale`, is parsed and used for the snapshot/scale-factor agreement check without being stored. **So 42 columns, not the 43 this note originally claimed, are parsed past and discarded at the very first read** (shape parameters, tidal quantities, pseudo-evolution-corrected masses, multiple spin/energy diagnostics, internal Consistent-Trees bookkeeping IDs). Nothing downstream of that point — `scatter.py`'s worker scratch, `sort_index.py`'s sorted records, `fixups.py`'s fixed dtype, `links.py`'s identity/rank pass, `hdf5_writer.py`'s emitted HDF5 — ever sees them again, and on the production run none of the intermediates survived either: `--consume-intermediates` is off by default and irreversible, was mandatory for that run, and deletes each intermediate at the point its terminal consumer is finished with it.

The measured consequence, from the completed production run (`docs/dev/SHIN-UCHUU-CONVERSION-PLAN.md` → "Production run complete"): the source was 11.61 TB / 22,503,649,037 halos ≈ 516 bytes/halo as ctrees ASCII text; the emitted dataset is 2.2520 TB for the same halo count ≈ 100 bytes/halo as HDF5 — roughly a 5.2× reduction, dominated by (a) discarding those 42 unused columns, (b) ASCII-to-binary numeric encoding efficiency, and (c) replacing ctrees' large global tree-scope IDs with compact `int32` snapshot-local array indices during Phase 3's link remapping. The 100 B/halo is not an accident of compression: it is exactly what v2's field table sums to (five `int32` links, `Len`, `SnapNum`, `M_Crit200`, three `float32[3]` vectors, `VelDisp`, `Vmax`, and three `int64` identity fields = 100 B), which is why the measured 100.01 B/halo lands where it does.

**Corrected 2026-09-22 — these compression figures are v2's, and they do not survive the successor plan.** The proposed v3 layout widens all five topology links from `int32` to `int64`, adds three `int32` target-snapshot columns so gapped links can be expressed, and adds an `int64 SourceHaloID`: **+40 B on v2's 100, i.e. ≈140 B/halo**, which takes the source-to-output ratio from ≈5.2× to ≈3.7× and a Shin-Uchuu-sized v3 dataset to ≈3.15 TB *before* any restored column is added. Point (c) above is therefore partly reversed by the lossless-topology requirement. Read this section as the record of why the discard was acceptable under v2, not as a size budget for v3 — the implementation plan's C3 owns that.

No scientific content Mimic uses was lost — but if a future need calls for one of the 42 discarded columns, recovering it is real work rather than a config change. **Corrected 2026-09-22: this note originally said "five files" and then listed six, and the list was wrong in both directions.** Two hardcoded layouts actually need editing — `RECORD_DTYPE` in `ctrees_parser.py` and `HALO_DATASETS` in `hdf5_writer.py` — with their consumers (`scatter.py`, `sort_index.py`) checked; `fixups.py`'s `FIXED_RECORD_DTYPE` is *derived* from `RECORD_DTYPE.names` and follows automatically, and `links.py`'s `LINKS_RECORD_DTYPE` is topology-only and is unaffected by a payload column. Then bump `docs/dev/HORIZONTAL-HDF5-FORMAT.md`'s `format_version` ratchet, add the field to the simulation package's `halo_properties.yaml`, run `make generate`, and re-clear the micro-Uchuu acceptance gate (producer battery + topology cross-check) before trusting the rebuilt converter again.

**The code edits are the small part, and this note originally missed the large one.** `ctrees_parser.py`'s `DTYPE_TAG` records the scratch dtype's identity in every manifest, and the manifest refuses to resume across a dtype change — `SHIN-UCHUU-FLYBY-DEFECT-ADDENDUM.md`'s R9 charge requires "a fresh workdir (the manifest binds to its inputs and refuses to resume across a dtype change)". At Shin-Uchuu scale a restored column therefore costs a **full re-conversion from an empty workdir** — the v2 re-conversion measured 5d18h35m of pipeline plus ≈29h51m of source re-transfer — not an incremental rebuild. That, and not the number of files touched, is the real price of the frozen dtype, and it is the strongest argument for getting field selection declared before the next large conversion rather than after it.

## Design direction: declarative column mapping

Generalising the converter to a second simulation forces the same question a column-restoration request does: *which source columns exist, and which do we keep?* Different Consistent-Trees runs are not guaranteed to carry the same extended column set (some configurations track fewer of the shape/tidal/pseudo-evolution diagnostics than others), so the generalisation work already has to stop assuming one fixed, hardcoded layout.

The candidate direction: replace `RECORD_DTYPE` and its downstream propagation with a declared, per-simulation mapping — "these named source columns become these named output fields" — read from configuration rather than compiled into a Python literal. If that mechanism is built to be genuinely arbitrary (any recognised source column to any declared output field, not just a fixed list with a size knob), then both problems are solved by the same piece of work: a new simulation with a different available column set is a new mapping, and a later "keep this column too" request against an existing simulation is an edit to that simulation's mapping rather than surgery on the hardcoded layouts. Note what that does *not* buy, per the cost analysis above: declaring the mapping removes the code edits, but a changed field set still invalidates the manifest's dtype identity, so an existing dataset still has to be re-converted from a fresh workdir. Declarative selection makes the *next* conversion cheap to specify; it does not make an *already-converted* dataset cheap to amend — which is exactly what the top-up idea below was reaching for.

**The trap this framing hides (added 2026-09-22).** "Named source column → named output field" cannot express what the converter actually does, because two of the 20 stored scratch fields have no source column at all: `tree_root_id` is attributed by interval lookup over the `#tree` block-marker lines in `ctrees_parser.py` — *not* read from the `Tree_root_ID` column, whose values are among the 42 discarded — and `forest_id` is left as a `-1` placeholder there and filled from `forests.list` in `scatter.py`. The field name makes the first look like a column mapping when it is nothing of the kind. Any declarative design has to carry **attributed fields as a first-class kind** alongside mapped columns, and has to say where each attributed value comes from; a schema that only maps columns will either drop both fields or silently re-bind `tree_root_id` to the wrong source. Other input formats will widen this: an adapter reading L-Halo binary or forests-HDF5 has a different set of things it derives rather than reads.

This does **not** remove the Mimic-side step. A genuinely new output field still needs registering in the target model/simulation package's `halo_properties.yaml` (units, precision, range) and a `make generate` pass — that is inherent to the framework's metadata-as-structural-truth principle (`docs/VISION.md`) and is orthogonal to whatever the converter's own column-selection mechanism looks like.

## A candidate cheaper path: topping up an already-converted dataset

A separate question came up: if a column is wanted for a simulation that has *already* been fully converted (as Shin-Uchuu now has), must the whole multi-day pipeline be repeated, or is there something cheaper?

**The naive version does not scale.** The obvious-sounding approach — for each of the dataset's halos, locate its row in the raw ctrees source and copy the wanted field across — fails if implemented as one independent lookup per halo. At Shin-Uchuu's measured production scale (22,503,649,037 halos) even an optimistic ~1 ms of per-lookup overhead (network/filesystem seek, dispatch) totals over 260 days before any useful data is read; in practice, scattered small random reads at that volume would plausibly cost months to years, particularly over a network mount. This is very much in the territory the person raising the idea was themselves worried about.

**The tractable version keeps the same idea but changes the granularity.** Instead of one lookup per halo, do one sequential pass per source file (mirroring the existing converter's own Phase 1 `scatter.py` pattern, but extracting only `id` plus the wanted new field — far less parsing per row than the full record), then a single bulk join against the *existing* output using an id-indexed structure built from the much smaller emitted dataset (2.2520 TB versus 11.61 TB). **The join key already exists, and naming it matters** (added 2026-09-22): `/halos/MostBoundID` is specified as the source-catalog Consistent-Trees `id` (`docs/dev/HORIZONTAL-HDF5-FORMAT.md` → Halo Datasets), which is what makes this idea viable at all. Note it is only dependable from v2 onwards — under v1 the flyby demotion negated it for demoted centrals, so the same sketch run against a v1 dataset would have silently mis-joined exactly the rows that were already wrong. This reuses the same class of technique `links.py`'s rank pass already implements through the external-merge core in `rank_sort.py`, applied here to something narrower: no tree topology is being rebuilt, so `finalize`/`sort`/`fixups`/`links` are not needed at all — only a lighter extraction pass and a join.

**Rough character, not a measurement.** Reading all 11.61 TB of source at least once is unavoidable regardless of approach, since nothing already-computed retains the discarded columns; this dominates the cost and would plausibly land in the same order of magnitude as this run's own measured transfer-plus-scatter time (a few days, per the production run's own record cited above), not the full ~5.76-day P1+P2 wall clock, since the topology-rebuilding stages are skipped entirely.

**The peak-memory claim this note originally made was wrong three ways, and is withdrawn (2026-09-22).** It read "much lower than `links`' measured ~225-300 GB, since there is no identity/rank-sort mechanic involved". First, nothing there was measured: peak RSS was never captured at production scale for any stage of either run — `SHIN-UCHUU-FLYBY-DEFECT-ADDENDUM.md` records that the only observations are two ad-hoc spot checks of `links` (4.8 GB at start, 30.8 GB at snapshot 31/70) against an unverified projection, and the v2 re-conversion did not wrap its stages either. Second, the projection's binding term is the link stage's **per-snapshot window**, not its identity/rank pass; the external-merge core bounded that pass to a measured 9.76–10.01 GB on 2026-08-28, so removing it buys ~10 GB, not ~200. Third, the projection is stale in the unsafe direction: ≈225–235 GB was fitted at an assumed largest slab of ≈3.546 × 10⁸ halos, and P5 then measured the real largest slab at **519,342,987** (snapshot 34), which on the same ≈620–650 B per largest-slab-halo fit above a ≈4.2 GB floor gives **≈326–342 GB**. `SHIN-UCHUU-CONVERSION-PLAN.md`'s standing instruction to re-derive that window from the production report's own per-snapshot counts has never been discharged, and this note should not be read as having discharged it.

**What can honestly be said about the top-up's memory:** nothing yet. It is an id-keyed sort-merge over 22.5 × 10⁹ rows — the same external-merge class of mechanic as the rank pass, as the paragraph above says — so its working set has to be budgeted under an explicit memory bound, exactly as `rank_sort.py` already does, rather than assumed small because the topology stages are skipped. Whether it is the kind of job that can run at low priority in the background is an open question, not a property it has been shown to have. None of this is measured or built; it is a design sketch, not a plan.

## Open questions

- **~~Exact scope of "generalise."~~ ANSWERED 2026-09-22 by the implementation plan.** This note only examined column selection. The other Shin-Uchuu-specific assumptions it listed as unexamined — the two supported header dialects, the `snap_idx`/`snap_num` duality, the frozen scratch/fixed/links dtypes' byte layouts — are now in scope there, together with input adapters, a general topology representation, wider links and a distinct stable row identity. The batch-mode transfer machinery is explicitly *not* in that plan's scope (it authorises no remote transfer), so that part remains genuinely open.
- **CARRIED FORWARD, and now owned elsewhere:** the worker scratch writer in `scatter.py` opens one write handle per snapshot with Python's default buffering, which some filesystems (Lustre stripes, some APFS temp volumes) report a large `st_blksize` for — inflating each handle's buffer well beyond what "bounded by snapshot count" implies, up to `n_snapshots` concurrent handles. `crosscheck.py`'s `TopologyDumpPartition._handle()` had the identical defect, fixed 2026-09-17 with an explicit `buffering=8192` while chasing a converter-test memory regression; the scatter writer was left with only a `TODO` at the `open()` call (`scatter.py:778`, TODO comment at `:772-777`) because it was out of scope that day. It is real production exposure at Shin-Uchuu's own scale (up to 70 concurrent handles), not test-tuning noise. **This item is no longer owned here:** the implementation plan carries it with a concrete requirement this note never stated — "Scratch writer buffering is explicitly 8192 bytes" — and an acceptance checkbox for pooled execution. Fix it there, not from this note; the code `TODO` was repointed at the implementation plan on 2026-09-22.
