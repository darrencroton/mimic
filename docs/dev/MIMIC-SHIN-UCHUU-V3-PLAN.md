## Why this brief exists

Three facts set the problem, each already on record:

1. **The production Shin-Uchuu dataset is version 2** (`simulations/shin-uchuu/README.md` → "How the production dataset was made"), so neither distribution (step 3) nor chunked slab streaming can touch it: both need a forest-blocked dataset, and the Consistent-Trees ASCII route of the version 3 converter does not emit one today (`convert/mimic-convert/HORIZONTAL-HDF5-FORMAT.md`, the non-normative note under "V3 Ordering Contracts"; measured on a scratch micro-Uchuu ASCII conversion: 4,707 `ForestIndex` descents per slab).
2. **One forest holds most of every slab.** Forest `26551468179`, the percolation super-forest, contains 104,845,278 tree roots (33% of all trees; `simulations/shin-uchuu-ascii/README.md`) and, measured over the whole production dataset on 2026-10-07 (below), 12,646,607,901 of its 22,503,649,037 halos (56.20%), peaking at 333,663,215 of snapshot 31's 507,798,774 halos (65.7%). A forest is never split by either memory lever, so on this conversion no task count and no chunk count brings Shin-Uchuu below that forest's rows. The only lever that lifts the floor is changing what the dataset calls a forest.
3. **Retiring version 2 is wanted** (one contract, one reader, one converter: the vision's "format-agnostic I/O" with no legacy path) and is about 12 to 14 thousand lines, three quarters of them tests, fixtures and prose. It has preconditions that only a forest-blocked Shin-Uchuu dataset and a gated ASCII route satisfy.

## Decisions recorded 2026-10-07 (binding)

The owner decided the following on 2026-10-07. Everything after this section is shaped by them.

1. **No compute on the supercomputer.** The owner's NT login may no longer be used by an assistant, the login node is for light, short work only, and the Slurm queue is unreliable (this is why the version 1 and version 2 conversions were run on the Mac Studio). NT is touched only for data transfers the owner performs with `scp` or `rsync`, in either direction: downloads of small index files, and uploads of finished, checksummed files for cold storage in the oz214 project space (about 20 TB free). No stage below may assume any remote computation, census or extraction.
2. **All work runs on the Mac Studio** (512 GB RAM, 32 cores, macOS). Storage to plan against is exactly one of two scenarios: **(a)** one 8 TB LaCie (7.3 TiB, 7.71 TB measured free when empty), or **(b)** two such drives. `Internal` takes no conversion scratch or dataset; its about 1.0 TB of free space may hold one run output at a time (a full-box `sage16` output is about 0.55 TB) and small artefacts. The version 2 Shin-Uchuu dataset (2,251,984,563,372 bytes, 71 files; a second copy on NT at `/fred/oz214/dcroton/shin-uchuu/snapshot-trees-v2`) and the 197 GB `shin-uchuu-subset-ascii` are already on the LaCie at `/Volumes/LaCie/data/uchuu/`; they are the starting point of both workflows.
3. **Time is not the constraint**; the version 2 production conversion took 6 days and that was fine. Workflows are optimised for time within the storage bounds, never the other way round.
4. **End state.** (i) Both version 2 datasets, `micro-uchuu-ascii-horizontal` and `shin-uchuu`, are converted to version 3 and those datasets replace the version 2 ones; (ii) every piece of version 2 code, fixture, test and documentation is removed, leaving no dead or stale code or prose; (iii) the Shin-Uchuu version 3 dataset has been cut so that its forests run through the horizontal driver with chunked slab streaming (`input.forest_chunks`) on a "normal" laptop, 16, 32 or 64 GB of RAM, the exact class to be settled once the trees have been explored (Stage B).
5. **The decision criterion.** The format's rules exist to serve the project's purpose, and decisions are not made "by rules that have forgotten the greater purpose". The vision's single source of truth weighs heavily: a `format_version 4` would leave two live versions with duplicate reader, converter, test and documentation paths until version 3 was retired too, and the owner rejects that. The original Shin-Uchuu ASCII trees will never be used again after this work, since no available machine can run them vertically with Mimic or any SAM, which is why they are being converted; the converted dataset therefore need not be **technically** exact with respect to the source (the same identity numbers, an inversion to a source row) but must be **scientifically** exact: every galaxy property the model produces must be byte-identical to what the version 2 dataset, or a vertical run over the ASCII trees, produces for the same galaxies. `UniqueGalaxyID` is a catalogue label and is never compared between catalogues. The cut breaks exactness for the affected galaxies to a measured extent, which is accepted as necessary.
6. **Other choices:** the owner accepts this brief's recommendations provided the end state is reached. The recommendations taken are marked **(R)** below; the open questions at the end are the ones the owner still has to answer.

## Scientific identity, operationalised

A dataset D′ is scientifically identical to a reference D for a model M under a named run configuration when, running Mimic over both with that configuration, the set of galaxies is the same and every galaxy property is byte-identical for matched galaxies. Galaxies carried from the trees are matched by `UniqueGalaxyID` where the forest enumeration, ranks and multiplier are unchanged (which the existing comparator `scripts/compare_cross_format_identity.py` already does), and otherwise by the catalogue's halo id (`MostBoundID`, always positive here) with its snapshot; galaxies a module creates (HOD satellites) copy their host's `MostBoundID` and carry a position-dependent negative id, so they are matched by birth lineage, the host's key plus the creation ordinal, which the comparator must learn (today it excludes created records by default). The acceptance matrix names its configurations: `halos-only` and `sage16` under both drivers, both timestep schemes, serial, chunked and `mpirun`; SHAM and HOD horizontally only, since snapshot modules cannot run vertically or chunked, and a floating-point snapshot sum is allowed by the vision to differ in its last bits with MPI reduction order (no shipped module uses one; SHAM and HOD use ranks and agreement only). What the model consumes: the payload columns, the FoF chains in chain order, the progenitor chains in chain order (which decide the main progenitor), the descendant links, and the identities through `UniqueGalaxyID`. Row order within a slab is storage order; the driver visits FoF groups in the order their centrals are first met in the slab (`src/core/horizontal_driver.c:2166`) and the vision requires physics to be deterministic given a halo's own data regardless of traversal order, with the created-record id as the declared exception. The empirical precedent exists: the version 2 horizontal dataset, sorted by `MostBoundID`, is per-`UniqueGalaxyID` byte-identical to the vertical ASCII path under `halos-only` and `sage16`, both schemes (`simulations/micro-uchuu-ascii-horizontal/README.md`), and five version 3 packages are gated the same way.

## The format ratchet: version 3 by owner ruling

The format's ratchet rule (`HORIZONTAL-HDF5-FORMAT.md` → "Versioning", "V3 Versioning Policy") bumps `format_version` for any change to the meaning, layout, ordering or validation of files on disk; errata record corrections that change what the document says, not which files conform, plus one owner carve-out of 2026-09-29 for a producer storage-layout relaxation that no consumer could observe. Against that rule, a forest-blocked ASCII route **is a bump by the document's letter**: the "V3 Source Identity" sentence fixes the declared total order as ascending source file ordinal then within-file unit ordinal, with `SourceHaloID` inverting to a physical source row, and forest blocking needs the forest order and the storage order to agree, which that order does not give. Three ways of resolving it were examined by the panel:

- **A `format_version 4`** would let the ASCII identity be defined from the data with no ruling, but leaves two live versions with duplicate code and documents until version 3 is retired too. Rejected by the owner (decision 5).
- **Staying in version 3 by the letter**, with a declared forest table renumbered to inventory order so that the dense enumeration follows file order, fails on two counts: a forest that spans files can never be made contiguous in file-ordered identities by any renumbering (an inventory sequence F, G, F stays non-monotone), and renumbering `ForestIndex` changes `UniqueGalaxyID`, which changes HOD realisations and SHAM tie order, so it is not scientifically identical even before a cut. It would also have kept a full read of the 11.61 TB source for exact identities. Rejected.
- **Staying in version 3 by an owner ruling (R).** The format owner records, under the format's errata as an explicit second carve-out and not as a correction, a change to the `consistent_trees_ascii` row of the V3 Source Identity table: the unit is the whole forest; units are ordered by ascending source forest id, which is ascending `ForestIndex`; within a unit the row ordinal is `HaloRankInForest`. `SourceHaloID` for this route is then one plus the halo's position in the complete (`ForestIndex`, `HaloRankInForest`) order, exactly the convention the producer battery already enforces for the two prelinked routes (`validate_v3.py:1332-1346`), and every slab is forest-blocked by construction. It no longer inverts to a physical source row; it inverts to (`ForestIndex`, `HaloRankInForest`). Unchanged: `ForestIndex` (the dense enumeration of the catalogue's forest ids, the same as the vertical reader's), `HaloRankInForest`, `UniqueGalaxyID`, every payload and link value and chain order, the header attribute set, the object set, every invariant, and the sidecar, whose `ForestID` is the source forest id and whose file and unit ordinals give a single-file forest's file and first-marker position or −1,−1 for a forest spanning files. `format_version` stays 3.

**What the ruling must say, honestly.** It is a conformance change, not a repair of inaccurate wording: a version 3 ASCII dataset written before the ruling (by `convert_trees.py`, which shipped in release v1.2) is recognisable from the data alone, its `SourceHaloID` is not its (`ForestIndex`, rank) position, fails the producer battery and must be reconverted, although Mimic's run-time physics reads none of the changed values and its output is identical; an old ASCII workdir must not resume under the new rule. None of this repository's committed fixtures or shipped packages is affected (the two committed ASCII-horizontal fixtures are version 2; the route has no V3 Runtime Support row). The reasons the row gives: the physical inversion's only consumers were the converter's own acceptance tools, which are revised to check this route through `ForestIndex`, `HaloRankInForest` and the catalogue id (the `compare-extras` leg of `run_generalisation_acceptance.py` joins extras on `SourceHaloID` today and must join on the catalogue id; `tests/tools/unit_ordinals.py` never reads `SourceHaloID` and is unchanged); a bump would keep duplicate paths for one route's identity convention, against the vision's single source of truth; and the only production source of this route is being retired, so the owner relinquishes the physical-row inversion for it. The ruling does not lean on the 2026-09-29 precedent, which preserved conformance, and does not extend to any other route. Both panelists supplied verbatim errata and identity-table text; the Stage A implementation plan takes the Claude text as its base and the Codex text's sampling sentence (the ASCII route does not sample; an ASCII subset is a separate catalogue with its own enumeration).

**What the ruling removes.** The planned Stage S (a streaming read of the 11.61 TB source for exact identities) disappears entirely: no source transfer, no scan tool, no 0.8 TB of records. The rewriter computes `SourceHaloID` from columns the version 2 dataset carries. The only downloads left are the production `forests.list` (7.56 GB) and `locations.dat` (about 13 GB), which supply the sidecar's file and first-marker ordinals for single-file forests (the version 2 sidecar has only `ForestID`), so that the sidecar keeps its stated meaning rather than writing −1 to mean "unknown". A per-tree inventory built from them and from the census's terminal-root labels (root id, file, marker order, forest, row count) is kept permanently; it supports a conservation check against the production report's per-file row counts and any later, optional read of the source for interpretation.

**Why the cut stays inside version 3.** The cut is expressed as a declared **transformed source**: the original inventory, the original forest table, a **cut forest table** (a `forests.list` with the same tree roots and new forest ids: pieces of a cut forest receive fresh ids above the catalogue's maximum except the largest piece, which keeps the original id so that every untouched forest keeps its `ForestIndex`) and one deterministic host transformation: hosts are resolved under the **original** partition (the post-fix-up central the version 2 dataset records), the cut table is then installed, and every halo whose resolved central lies in another forest of the table becomes a central (`upid = id`, `pid = −1`); no host relation is ever invented. Under that declared source, sidecar `ForestID` is truthfully the source forest id, `ForestIndex` is the dense enumeration of the table, `SourceHaloID` follows from the recomputed ranks, FoF, progenitor and descendant links stay inside each forest, chains are cycle-free, and `n_forests_total` and the sidecar describe the new census; a piece's trees come from many files, so its sidecar ordinals are −1,−1, which is their stated meaning. The table's md5 and the transformation's definition go where the production conversion's provenance already goes: the conversion report and manifest, and the package README's "How the production dataset was made". The ruling's errata row states the transformation as the ASCII route's rule for a declared cut table; without a table the route refuses a cross-forest host, as it does today. The identity multiplier is **pinned at 2 × 10¹⁰** for every Shin-Uchuu dataset (the worst case, 166,547,771 forests plus 104,845,277 extra pieces, is 271,392,048, inside the 461,168,601 the multiplier admits), so untouched forests keep their `UniqueGalaxyID` across the cut and the cut's identity-dependent effects are confined to the super-forest's halos.

## Stage A: a forest-blocked ASCII route, gated at micro-Uchuu scale

**Goal.** The `consistent_trees_ascii` adapter of `convert_trees.py` emits version 3 datasets under the ruling's identity convention, so that every slab is forest-blocked and the distributed driver and a chunked sweep accept them.

**Scope.** The ruling's text (the errata row, the identity-table row, the assignment and consequence paragraphs, the sampling sentence, the non-normative note, which now says the ASCII route is forest-blocked); the adapter's unit model and identity (`convert/mimic-convert/adapters/ctrees_ascii.py`: `_build_inventory`, `_source_ids`, `iter_forests`; `adapters/base.py`'s inventory contract, which orders physical (file, unit) coordinates and rejects negative ordinals, gets a route-declared canonical unit so that physical coordinates are retained only for the sidecar; `pipeline.py` and `conversion_manifest.py` bind the identity scheme so that an old ASCII workdir cannot resume); the producer battery, where the ASCII route joins the (`ForestIndex`, rank) position check for complete datasets while the per-file sidecar inventory check stays with the two prelinked routes (the current `_V3_UNIT_FORESTS` tuple gates both and must be split, since spanning forests carry −1), with the ASCII route refusing sampling, and a cheap explicit per-slab `ForestIndex` non-decreasing check; the acceptance harness (`tests/run_generalisation_acceptance.py`: the C-dump identity check gains the ASCII route, `compare-extras` joins on the catalogue id); the stale statements that the ASCII route is not forest-blocked (`report.py`, `convert_trees.py`, the converter manual, the user and developer guides, `CHANGELOG.md`'s unreleased notes, the `mimic-run-and-operate`, `mimic-simulations-and-readers`, `mimic-debugging-playbook`, `mimic-docs-and-writing` and `mimic-validation-and-qa` skills, the package READMEs); a conversion of the local `micro-uchuu-ascii` trees; `simulations/micro-uchuu-ascii-horizontal` moved to that dataset **in place (R)** (the end state is replacement, and every consumer of its version 2 fixture is slated for deletion at Stage D; during the A to D window the version 2 fixture moves to one legacy location under `tests/data/` with the three consumers that still need it, the `make tests-distributed` refusal check, the SHAM and HOD snapshot-global batteries until they are retargeted to the version 3 dataset, and the version 2 C reader tests; the package's `halo_properties.yaml` topology types become `long long`); the package's schema-conformance test; and its cross-format identity gate against `micro-uchuu-ascii` read vertically, inheriting the version 2 gate's role including its vertical-path preservation stage (`tests/framework/parity_gate.py`, whose sidecar check infers the source inventory from the file ordinals and must instead prove it from the conversion manifest, because spanning forests carry −1). Acceptance is the gate's: per-`UniqueGalaxyID` byte identity under `halos-only` and `sage16`, both timestep schemes, plus identity of the new dataset through the distributed comparator at `mpirun -np 4` **and** a serial chunked leg (the distributed gate today runs only the mini-Millennium fixture, so this is a new leg), with the forest-blocking check passing at startup.

**Why first.** Without it no Shin-Uchuu dataset can be distributed or chunked, whatever Stage B decides, and the micro-Uchuu scale (561,266 trees) is where the route is cheap to get right and gate. It depends on nothing else in this brief, and it is the reference every later gate compares against.

## Stage B: the super-forest decision, by measurement, on the version 2 dataset

**The question.** A forest is a connected component under FoF co-membership and descendant links, so the super-forest cannot be made smaller without cutting links, and every cut changes physics: a cut FoF link turns a satellite into a central, and for HOD and SHAM the recomputed ranks change the ids their draws and tie-breaks key on for every halo of the super-forest's pieces (56% of all halos). Cutting is defensible if the super-forest is held together by a small number of bridging links, such as brief flyby co-memberships that Consistent-Trees' forest linking propagates across the whole box, and costly if it is densely connected at this resolution. Which of the two it is has never been measured. The owner's end state requires a cut; the measurement decides **which** cut, at **what physics cost**, and whether the laptop class the owner wants is reachable at an acceptable cost.

**The measurement, entirely local, before any rewrite.** The version 2 production dataset carries everything the census needs: `Descendant`, `FirstHaloInFOFgroup`, `ForestIndex`, `MostBoundID`, the masses for edge weights, plus the production `forests.list` and `locations.dat` (transferred by the owner). Tree membership is recovered by a backward pass from the last slab labelling every halo with its terminal root (a root wherever `Descendant == −1`, in any slab, which the reference reader accepts; the root set is checked against the forests.list tree roots and any root not at z=0 is reported); two slabs are resident at a time (519,342,987 × 8 B = 4.2 GB each). These units are **effective descendant trees**: descendant links are never rewritten, so they are indivisible histories by construction, but their equality with Consistent-Trees' physical `#tree` blocks is not established by any committed check (the converter's closure guard checks forests, not tree attribution) and the record says so; the conservation check of per-file row counts through `locations.dat` against the production report is necessary, not sufficient. Then per slab, every FoF link between halos of different trees is a co-membership edge of the **effective** graph (post-fix-up, the topology Mimic consumes), weighted by distinct snapshots, halos involved and mass, aggregated with a bounded representation (streamed per-slab edge lists merged by key; a dense tree × snapshot occupancy matrix would be 88 GB at int32 and is not built); the raw `pid`/`upid` graph, which would explain **why** links bridge, is not available without reading the source and is recorded as an optional later measurement, not a dependency. Outputs: per-tree and per-forest occupancy per slab and over all slabs (the forest half is the 2026-10-07 census above), including the largest indivisible tree; the super-forest's tree graph (104,845,278 trees) and its component sizes under candidate rules (duration or weight thresholds, minimum cuts), with a deterministic piece-naming and tie rule; for each candidate rule the severed relations, the central promotions per output snapshot, the progenitor-order changes, the halos re-labelled and the identity-dependent effects on HOD and SHAM; and a simulation of the driver's two-level partition (`horizontal_partition_cut`: tasks by greedy packing of widest-slab weights, then chunks within each task, applied as fixed forest ranges to every slab, `src/core/horizontal_partition.c`) for candidate task and chunk counts, giving the widest chunk in every slab, which is the memory-relevant quantity. The same census and candidate rules run on micro-Uchuu's dataset first, as the method rehearsal, where the vertical driver can run `sage16` and the rules' effect on output is seen directly.

**The decision gate.** The owner decides on the census and the record is kept as standing evidence under `docs/dev/`: the graph definition, the root correspondence, the edge weighting, the candidate thresholds, the largest individual tree, all-slab piece and chunk maxima, severed relations and promotions, the predicted science differences per model, the chosen rule, and the chosen laptop class with its implied F. Three outcomes are possible: a rule reaching the wanted class at an acceptable cost; a rule reaching a larger class only (the owner picks the class; a class above 64 GB revises the end state); or no defensible rule, in which case the owner decides between accepting the cost and settling for the uncut dataset on the Mac Studio (then the end state's item (iii) is not reached, and the brief says so). A tree larger than the class's working set cannot be overcome by any whole-tree cut.

## Stage R: the dataset rewriter

**Goal.** One tool that reads a horizontal dataset slab by slab and writes a version 3 dataset under a forest table, with explicit multi-pass memory ownership. Scope is **Consistent-Trees-derived datasets with adjacent links** (`links_adjacent` 1, the only kind this brief produces); any other input is refused, and the general gapped case is recorded as out of scope rather than approximated. Pass 0 reads headers, the sidecar, the two forest tables, the index files and the per-tree inventory; pass 1 per slab computes the new row permutation and writes it with (`ForestIndex`, `HaloRankInForest`, `SourceHaloID`) per row to a remap store (32 B/halo); because the reference rank orders a forest's halos by descending snapshot first, the two passes interleave in descending snapshot order with a per-forest running count (166,547,771 × 8 B = 1.3 GB) supplying each slab's rank base, pass 2 trailing pass 1 by one slab, so a slab's remap entry is needed only by slabs N−1, N and N+1 and about 50 GB of the store is resident; pass 2 per slab rewrites the payload and remaps every link through the target slab's permutation (`Descendant` at N+1, `FirstProgenitor` at N−1, `NextProgenitor` and the FoF links at N; each companion `*Snapshot` column is −1 iff its link is −1, else N+1, N−1 and N respectively), carries the input's `/schema` through unchanged for a version 3 input and builds it from the package's `converter_columns.yaml` profile for a version 2 input, writes the header attributes and the sidecar, verifies each slab, and records checksums, immutable input identity and restart state in a **manifest of the shape the producer battery binds to** (a complete `write` stage with per-artifact SHA-256, the pinned a_list, an inventory whose totals and per-snapshot counts come from the input dataset or the cut table and which declares no physical units, and the embedded schema), since the battery without a manifest skips its binding and conservation checks. Three operations: **(M) migration**, version 2 to version 3, identities computed from the version 2 columns, expected to emit exactly the datasets the Stage A route would emit from the same source; **(C) cut**, version 3 to version 3 under a cut forest table, resolving hosts under the original partition, applying the severance rule, recomputing FoF chains, `HaloRankInForest` and the progenitor chains (`FirstProgenitor`/`NextProgenitor` order from the reference incremental-insertion loop over the new reference encounter order, ties included, as `links.py` implements it, in int64 throughout) for every forest the table changes, reproducing payload and topology exactly for untouched forests (whose `ForestIndex` and, with the pinned multiplier, whose `UniqueGalaxyID` are unchanged), and never changing a descendant edge (verified); **(N) no-op**, version 3 to version 3 under the identity table, which must reproduce its input exactly in every dataset value, dtype and metadata item (whole-file byte equality additionally depends on HDF5 layout and is checked where the writer's layout is deterministic) and is a permanent self-test. The version 2 input path is deleted at Stage D; (C) and (N) remain as the supported way to produce any future cut dataset, Shin-Uchuu's or Uchuu's. The ASCII route's fix-up stage gets the same severance rule behind a declared cut table, so that (C) is testable against a real conversion. Scratch and outputs are placed on the external volume explicitly; the gate harness's default of the repository's `output/` is overridden.

**Gates, all at scales that fit the Mac Studio.** Before the first gate, `simulations/shin-uchuu`'s package is prepared for version 3 (`long long` topology, `/schema`-matching `halo_properties.yaml`), since the reader rejects `int` link declarations. A conversion of the local subset through the Stage A route (197 GB source, about 60 GB output, about 0.5 TB of transient workdir, the rehearsal the 2026-10-06 brief already required, now also the reference); a version 2 dataset of the same subset regenerated locally with `convert_ctrees.py` (which exists until Stage D). G3: (M) of the version 2 subset ≡ the Stage A conversion of the subset in every `/halos` column, the header, the `/schema` group and the sidecar (which proves the sidecar ordinals derived from `locations.dat`). G3b: (N) is the identity. G3c: (C) of the subset under a test table ≡ the Stage A conversion of the subset declared with the same transformed source, plus adversarial fixtures (a table that changes nothing; a severed satellite; a group whose central leaves while its members stay together; a piece that initially holds no central; a tie in progenitor order), plus an **independent reference leg (R)**: small transformed ASCII fixtures whose host columns are canonicalised to the original resolved centrals and then severed, read by the unmodified C reference reader (`src/io/vertical/ctrees/ctrees_utils.c`) through the vertical driver, so that the cut's reconstruction is checked against code that shares nothing with the rewriter. G4: the scientific-identity gate of the migrated subset against `shin-uchuu-ascii` read vertically, over the acceptance matrix above, with the comparator extended to created-record lineage so that HOD's satellites are compared too. Cut datasets are additionally gated serial versus chunked versus `mpirun` through the distributed comparator. Deterministic re-run and resume checks. The subset excludes the super-forest, so the extreme case is covered only by the production validation and the science checks of Stage C, and the brief says so.

## Stage C: the Shin-Uchuu production datasets

Preconditions: Stages A, B and R gated. Scope: the production rewrites with the multiplier pinned at 2 × 10¹⁰, the producer battery, the `sage16` runs on the Mac Studio with chunked slab streaming, the science checks step 1 used (the baryon fraction, the z=0 Type 0 count, the halo mass function) compared with the version 2 production run's recorded values, with every difference attributed to the cut rule using Stage B's predictions, and the package README's provenance section rewritten. In both scenarios the **uncut** version 3 dataset is produced first by (M), run under `sage16`, and compared galaxy by galaxy against a retained version 2 run whose build, modules, parameters, timestep scheme, output fields and snapshot coverage are reconciled with the new run's (the recorded production run is usable only if they match; otherwise the version 2 dataset is re-run once, locally, before it is deleted), which isolates the format change from the cut; then the **cut** dataset is produced from it by (C). **Laptop acceptance (R):** memory per resident halo is calibrated on this executable on the Mac Studio with `MallocLargeCache=0` at the task and chunk counts the chosen class implies, on the cut dataset, under `sage16`, with the build configuration and the class's reserved budget recorded; the predicate is measured peak RSS under that budget with the sweep completing; without a run on an actual laptop of the class the result is a Mac-measured proxy and is labelled as such, and a laptop run, if one is available, is the final acceptance. Nothing is derived from the old pool ratio.

**Validator storage.** The version 3 producer battery (`validate_v3.py`) spills whole-dataset external-sort streams, about 195 B/halo on the large L-Halo examples (`convert/mimic-convert/README.md` → "Restart, cleanup and memory"), an extrapolated 4.4 TB at this scale. The subset rehearsal measures the battery's spill and RSS at 406,668,896 halos. A **validator scale slice** is **mandatory in scenario (a)** and advised in (b): it enumerates every obligation of the battery (manifest binding, source conservation, every invariant, progenitor closure through the target-snapshot columns, chain membership, FoF integrity, `SourceHaloID` uniqueness and order, identity density, `/schema` agreement), gives each a bounded replacement with a stated storage ceiling (independently indexed one-bit-per-halo passes for uniqueness and for density, which are separate properties; per-snapshot and per-target-snapshot work for the rest; no whole-snapshot resident array, so the contract's bounded-read rule still holds above `INT32_MAX` rows), and compares old and new verdicts on representative valid and adversarial datasets before it is trusted on production.

## The two workflows

Both run the five stages in the same order on the Mac Studio and both materialise the uncut and the cut datasets; they differ in slack and in what depends on NT's storage. Decimal TB; the output budget is 3.25 TB per dataset; "usable" is 7.71 TB, the measured free space on the empty drive. The owner's 0.72 TB of unrelated files currently on the LaCie must move off it first in either scenario. Every term has a stated lifetime; the subset rehearsal (Stage R) re-measures the transient ones (the rewriter's per-slab temporary of about 0.07 TB for the widest slab, the bounded battery's spill, the census aggregates) before production.

### Workflow (b): two 8 TB LaCies

Drive 1 holds the datasets exactly as in (a); drive 2 holds the version 2 dataset until Stage D if the owner prefers not to depend on the NT copy, both run outputs, the battery's spill if the validator slice is not built (4.4 TB), and slack. Nothing is uploaded to NT. The second drive buys independence from NT's storage and the option of skipping the validator slice; it does not change the workflow. A compressed local copy of the ASCII source no longer has a purpose under the ruling and is not planned.

### Time

The only downloads are the two index files. The rewriter's production passes read about 2.25 TB and write about 3.25 TB per operation; the census reads the 70 `ForestIndex`, `Descendant` and `FirstHaloInFOFgroup` columns (about 540 GB); the `sage16` runs are of the order of the corrected version 2 run (9 h 35 m on the Mac Studio for the uncut dataset). None of it approaches the version 2 conversion's 6 days.
