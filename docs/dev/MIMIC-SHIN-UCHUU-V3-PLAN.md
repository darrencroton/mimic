# Mimic Shin-Uchuu Version 3 Plan: the ASCII route, the super-forest and retiring version 2

**Status:** Requirements brief, staged (2026-10-06). Not scheduled; no implementation plan exists yet. Four stages in a fixed order, with one measured decision gate (Stage B) whose outcome decides the shape of the two stages after it. Stage A and Stage B are specified well enough here to be promoted to implementation plans now; Stages C and D are stated as scope with their preconditions, to be frozen only once Stage B has reported. Independent of [chunked slab streaming](MIMIC-CHUNKED-SLAB-STREAMING-IMPLEMENTATION-PLAN.md), which runs first as the current focus; nothing here waits on it, and Stage A can run beside it.

**Date:** 2026-10-06

## Why this brief exists

Three facts set the problem, each already on record:

1. **The production Shin-Uchuu dataset is version 2** (`simulations/shin-uchuu/README.md` → "How the production dataset was made"), so neither distribution (step 3) nor chunked slab streaming can touch it: both need a forest-blocked version 3 dataset, and the Consistent-Trees ASCII route of the version 3 converter does not emit one today (`convert/mimic-convert/HORIZONTAL-HDF5-FORMAT.md`, the non-normative note under "V3 Ordering Contracts"; measured on a scratch micro-Uchuu ASCII conversion: 4,707 `ForestIndex` descents per slab).
2. **One forest holds most of the widest slab.** Forest `26551468179`, the percolation super-forest, contains 104,845,278 tree roots (33% of all trees; `simulations/shin-uchuu-ascii/README.md`) and 321,253,424 of the widest slab's 519,342,987 halos (61.86%, measured 2026-10-05 and recorded in [`MIMIC-DISTRIBUTED-SNAPSHOT-ACCEPTANCE.md`](MIMIC-DISTRIBUTED-SNAPSHOT-ACCEPTANCE.md)). A forest is never split by either memory lever, so on this conversion no task count and no chunk count brings Shin-Uchuu below that forest's rows. The pathway's earlier wording, that distribution serves Shin-Uchuu "in combination with chunked slab streaming", was wrong on this point and is corrected: the only lever that lifts the floor is changing what the dataset calls a forest.
3. **Retiring version 2 is wanted** (one contract, one reader, one converter: the vision's "format-agnostic I/O" with no legacy path) and is about 12 to 14 thousand lines, three quarters of them tests, fixtures and prose. It has preconditions that only a version 3 Shin-Uchuu dataset and a gated ASCII route satisfy.

The order below is forced by dependencies, not preference: the ASCII route must be forest-blocked before any Shin-Uchuu conversion is worth running; the super-forest decision must be made on measurement before that conversion, because it changes the dataset's forest census and so its identity; the conversion must exist before version 2 can go.

## What stays version 3, and what would not

The format's ratchet rule (`HORIZONTAL-HDF5-FORMAT.md` → "Versioning") bumps `format_version` for any change to the meaning, layout, ordering or validation of files on disk, and for any additive attribute or dataset, because a version's consumers may assume its exact object set. It does not govern which halos a producer places in which forest: `ForestIndex`, `HaloRankInForest` and the sidecar `ForestID` "retain the selected source representation's identity convention", and the ASCII route's `ForestIndex` is a dense enumeration the converter assigns ("V3 Source Identity"). Therefore:

- **Emitting forest-blocked rows from the ASCII route is a producer change inside version 3**, as the non-normative note already anticipates. The per-file units a file-spanning forest is split into today (sidecar ordinals −1) become one unit per forest; `SourceHaloID` stays a prefix sum over the adapter's declared total order, which the adapter may declare per forest. One check Stage A's implementation plan must make before freezing: the format's "V3 Source Identity" sentence orders units by source file ordinal and then within-file unit ordinal while naming "an ASCII forest" as the unit, and a forest that spans files has no single file ordinal (the sidecar's −1 ordinals are the format's own provision for that case); if that sentence needs to say that the ASCII unit is the whole forest, with its rows ordered by the forest's files, that is a wording correction recorded under the format's errata, not a version bump, provided every conforming file keeps its meaning.
- **Cutting the super-forest at conversion is a data change inside version 3**, provided every version 3 invariant still holds for the forests it yields: FoF, progenitor and descendant links stay inside each forest (the producer obligation `convert/mimic-convert/links.py` enforces for descendants and the unit-forest contiguity check in `validate_v3.py` enforces for rows), chains are cycle-free, `ForestIndex` is non-decreasing along every slab and `n_forests_total` and the sidecar describe the new census. Nothing on disk means anything different.
- **Recording the treatment as a new header attribute would be a format change** (version 3 validates the exact header attribute set), and so would any new dataset or sidecar column. Provenance of a cut goes where the production conversion's provenance already goes: the conversion report and manifest, and the package README's "How the production dataset was made". A version 4 is not needed for anything in this brief, and introducing one would desynchronise Shin-Uchuu from the five version 3 packages for no gain.

## Stage A: a forest-blocked ASCII route, gated at micro-Uchuu scale

**Goal.** The `consistent_trees_ascii` adapter of `convert_trees.py` emits version 3 datasets whose rows are grouped by forest in ascending `ForestIndex` in every slab, with one inventory unit per forest, so that the distributed driver and a chunked sweep accept them.

**Scope.** The adapter's unit model (one unit per forest, forests spanning files included, with the sidecar ordinals the format permits); `validate_v3.py`'s unit-forest contiguity check extended to the ASCII route; a version 3 conversion of the local `micro-uchuu-ascii` trees; `simulations/micro-uchuu-ascii-horizontal` moved to that dataset in place (its version 2 dataset and fixture are kept until Stage D, because `make tests-distributed`'s version 2 refusal check and the version 2 reader tests still need them); the package's schema-conformance test; and its cross-format identity gate against `micro-uchuu-ascii` read vertically, inheriting the version 2 gate's role including its vertical-path preservation stage. Acceptance is the gate's: per-`UniqueGalaxyID` byte identity under `halos-only` and `sage16`, both timestep schemes, plus `mpirun -np 4` identity of the new dataset through the distributed comparator and the forest-blocking check passing at startup. No format text changes.

**Why first.** Without it no Shin-Uchuu version 3 conversion can be distributed or chunked, whatever Stage B decides, and the micro-Uchuu scale (561,266 trees) is where the route is cheap to get right and gate. It depends on nothing else in this brief or in chunked slab streaming.

## Stage B: the super-forest decision, by measurement

**The question.** A forest is a connected component under FoF co-membership and descendant links, so the super-forest cannot be made smaller without cutting links, and every cut changes physics: a cut FoF link turns a satellite into a central, a cut descendant link breaks a mass history. Cutting is defensible only if the super-forest is held together by a small number of bridging links, such as brief flyby co-memberships that Consistent-Trees' forest linking propagates across the whole box, and not if it is densely connected at this resolution. Which of the two it is has never been measured; the conversion plan's "almost certainly a ctrees linking artifact" was a judgement, not evidence.

**The measurement.** On the host that holds the full catalogue (`/fred/oz214/simulations/uchuu/shinuchuu/mergertrees` on Ngarrgu Tindebeek; the local 406,668,896-halo subset deliberately excludes the super-forest, so it cannot serve): take the super-forest's trees from `forests.list`, and from their `tree_*.dat` rows build the tree-level graph in which two trees are joined whenever a halo of one has its `pid` or `upid` host in the other (the columns `ctrees_parser.py` already reads), weighting each edge by the number of snapshots the co-membership lasts and the halos it involves. Report: the component size distribution after removing edges below a duration threshold, for several thresholds; the minimum cuts that detach the largest components; and for each candidate cut rule, the number of halos re-labelled, the galaxies it would move between Type 0 and Type 1 at the output snapshots, and the mass histories it would break (zero, if the rule cuts FoF links only). The pass also measures the same census on micro-Uchuu's largest forests, where the vertical driver can run, so a candidate rule's effect on `sage16` output can be seen on a box that fits.

**The decision gate.** The owner decides on the census, and the record is kept as standing evidence under `docs/dev/`. Three outcomes are possible and the brief does not prejudge them: a cut rule with a physical justification (then Stage C applies it at conversion as a converter stage with its own report); no defensible cut (then Shin-Uchuu stays NT-class memory under every driver until a sub-forest decomposition exists, which is a different plan and was costed and rejected by step 3); or a partial answer that reduces the floor without removing it, recorded with its new share of the widest slab.

## Stage C: the Shin-Uchuu version 3 conversion

Preconditions: Stage A gated; Stage B decided. Scope: a `converter_columns.yaml` profile beside the ASCII subset package, a Shin-Uchuu version 3 package (`halo_properties.yaml` matching the dataset's `/schema`, cosmology and a_list carried over, the identity multiplier re-derived from the new census), the storage envelope re-derived from a rehearsal on the local subset (the pathway's current figures: one to two weeks, about 10 TB of workdir without consumptive deletion, about 3.2 TB of output, plus the 11.61 TB source copy), the production conversion with any Stage B cut applied as a reported converter stage, and the package README's provenance section rewritten for it. Gating: the schema-conformance test; a cross-format identity gate at subset scale (a version 3 conversion of the subset the `shin-uchuu-ascii` package already runs, against that package read vertically), because the full box can never run vertically; and the `sage16` science checks step 1 used (the baryon fraction, the z=0 Type 0 count, the halo mass function) re-run on the new dataset and compared with the version 2 production run's recorded values, with any difference attributed to the cut rule. Memory: until a Stage B cut lands, plan for NT-class memory under every driver, since both memory levers share the super-forest floor.

## Stage D: retire version 2

Preconditions, unchanged from the pathway: a Shin-Uchuu version 3 dataset (Stage C); a gated ASCII-source version 3 route that inherits the version 2 gate's role (Stage A); the version 2 reader's negative battery mapped onto `tests/unit/test_horizontal_v3_reader.c`. Scope: the version 2 reader path, `convert_ctrees.py`, the version 2 fixtures and packages, the format document's version 2 text frozen as history, and the two remaining consumers of version 2 artefacts, `make tests-distributed`'s version 2 refusal check (which becomes the reader's unknown-version rejection) and the version 2 reference in the cross-format gate harness. About 12 to 14 thousand lines; the format ratchet is untouched (version 2 files become unreadable, which the ratchet already permits for unsupported versions).

## Out of scope, recorded

Full Uchuu (storage-bound before it is memory-bound: about 37 TB of source and 26 TB of output against 8.4 TB free; it needs this brief's Stage A route and would meet its own super-forest question); any sub-forest decomposition in the driver; any `format_version 4`; chunked slab streaming (its own plan); the vertical driver on the full Shin-Uchuu box (impossible by the super-forest's tree count, whatever Stage B decides, because the ASCII reader preallocates per tree).

## Open questions for the owner

- Whether Stage A should move `micro-uchuu-ascii-horizontal` to version 3 in place or add a version 3 sibling package until Stage D; in place is less code but leaves the version 2 fixture package-less until retirement.
- Whether the Stage B census is worth running on micro-Uchuu first as a method rehearsal (cheap, local, vertical runs possible) before the NT pass.
- Whether a Stage B cut rule, if one is found, should be exposed as a converter option with a report, or applied once by hand and recorded; the brief assumes the former, since the rule will be re-run on any future Shin-Uchuu or Uchuu conversion.
