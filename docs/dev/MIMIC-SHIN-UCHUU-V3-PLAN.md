## Why this brief exists

Three facts set the problem, each already on record:

1. **The production Shin-Uchuu dataset is version 2** (`simulations/shin-uchuu/README.md` → "How the production dataset was made"), so neither distribution (step 3) nor chunked slab streaming can touch it: both need a forest-blocked dataset, and the Consistent-Trees ASCII route of the version 3 converter does not emit one today (`convert/mimic-convert/HORIZONTAL-HDF5-FORMAT.md`, the non-normative note under "V3 Ordering Contracts"; measured on a scratch micro-Uchuu ASCII conversion: 4,707 `ForestIndex` descents per slab).
2. **One forest holds most of every slab.** Forest `26551468179`, the percolation super-forest, contains 104,845,278 tree roots (33% of all trees; `simulations/shin-uchuu-ascii/README.md`) and, measured over the whole production dataset on 2026-10-07 (below), 12,646,607,901 of its 22,503,649,037 halos (56.20%), peaking at 333,663,215 of snapshot 31's 507,798,774 halos (65.7%). A forest is never split by either memory lever, so on this conversion no task count and no chunk count brings Shin-Uchuu below that forest's rows. The only lever that lifts the floor is changing what the dataset calls a forest.
3. **Retiring version 2 is wanted** (one contract, one reader, one converter: the vision's "format-agnostic I/O" with no legacy path) and is about 12 to 14 thousand lines, three quarters of them tests, fixtures and prose. It has preconditions that only a forest-blocked Shin-Uchuu dataset and a gated ASCII route satisfy.

## Decisions recorded 2026-10-07 (binding)

The owner decided the following on 2026-10-07. Everything after this section is shaped by them.

1. **No compute on the supercomputer.** The owner's NT login may no longer be used by an assistant, the login node is for light, short work only, and the Slurm queue is unreliable (this is why the version 1 and version 2 conversions were run on the Mac Studio). NT is touched only for data transfers the owner performs with `scp` or `rsync` from NT to the Mac Studio. No stage below may assume any remote computation, census or extraction.
2. **All work runs on the Mac Studio** (512 GB RAM, 32 cores, macOS). Storage to plan against is exactly one of two scenarios, with no other disk assumed: **(a)** one 8 TB LaCie (7.3 TiB, 7.71 TB measured free when empty), or **(b)** two such drives. `Internal` keeps hosting only what it already hosts (the micro-Uchuu sources and datasets, mini-Uchuu, Millennium); nothing new goes there except the transient re-emission workdirs of open question 1, which fit its present free space for Millennium (0.58 TB peak) but not for mini-Uchuu (1.1 TB, which uses the LaCie before Stage S). The version 2 Shin-Uchuu dataset (2,251,984,563,372 bytes, 71 files) and the 197 GB `shin-uchuu-subset-ascii` are already on the LaCie at `/Volumes/LaCie/data/uchuu/`; the drive is not emptied first, they are the starting point of both workflows.
3. **Time is not the constraint**; the version 2 production conversion took 6 days and that was fine. Workflows are optimised for time within the storage bounds, never the other way round.
4. **End state.** (i) Both version 2 datasets, `micro-uchuu-ascii-horizontal` and `shin-uchuu`, are converted to the current format version and those datasets replace the version 2 ones; (ii) every piece of version 2 code, fixture, test and documentation is removed, leaving no dead or stale code or prose; (iii) the Shin-Uchuu dataset has been cut so that its forests run through the horizontal driver with chunked slab streaming (`input.forest_chunks`) on a "normal" laptop, 16, 32 or 64 GB of RAM, the exact class to be settled once the trees have been explored (Stage B). The owner wrote "version 3" for (i); open question 1 asks whether that means the number or the single current version, because the forest-blocked ASCII route is a format bump by the document's own rules.
5. **Other choices:** the owner accepts this brief's recommendations provided the end state is reached. The recommendations taken are marked **(R)** below; the open questions at the end are the ones the owner still has to answer.

## The format ratchet: what changes and what it costs

The format's ratchet rule (`HORIZONTAL-HDF5-FORMAT.md` → "Versioning", "V3 Versioning Policy") bumps `format_version` for any change to the meaning, layout, ordering or validation of files on disk, and for any additive attribute or dataset outside a conforming declared `/schema` extra; errata record corrections that change what the document says, not which files conform. Against that rule, the pieces of this brief fall as follows.

- **A forest-blocked ASCII route is a format bump.** The "V3 Source Identity" sentence fixes the declared total order as ascending source file ordinal, then ascending within-file unit ordinal, and `SourceHaloID` "inverts exactly" to that source coordinate; `adapters/base.py` enforces it. A forest-blocked route must order its units by forest (ascending source forest id, which is ascending `ForestIndex`; `ForestIndex` itself must not change, because the vertical reader enumerates forests the same way and `UniqueGalaxyID` parity depends on it), and that is a different total order even for non-spanning forests. The 2026-10-06 brief read this as a wording correction because the sentence already names "an ASCII forest" as the unit and the sidecar already provides −1 ordinals for spanning forests; the independent critique (both rounds) holds that this exposes an inconsistency in the text but does not authorise replacing the explicit order, and that a change to which files conform is a bump whether or not any dataset was shipped. **Recommendation (R), reversing the 2026-10-06 position: bump to `format_version 4`.** The ratchet is the project's own discipline and the document's words are unambiguous; ruling otherwise would weaken every future reading of it. A rank-derived `SourceHaloID` (a prefix over forests with `HaloRankInForest` as the row ordinal, which would have let version 2 be upgraded without reading the source) was considered and rejected for the same reason, and because it discards the inversion to a source row.
- **What version 4 changes, and what it does not.** The ASCII route's declared order (units are whole forests in ascending source forest id; within a forest, rows in source order: inventory file order, tree order within the file, physical row order within the tree; sidecar ordinals the owning file and within-file unit ordinal for a non-spanning forest, −1,−1 for a spanning one), stated so that the forest-blocked property becomes a stated property of the route; a per-forest `SourceHaloID` interval check for that route in the producer battery (the existing unit-forest check requires `SourceHaloID` to equal the `(ForestIndex, HaloRankInForest)` position, which is a different ordering from physical source order, so the ASCII route cannot simply join `_V3_UNIT_FORESTS`); the severance rule and the transformed-source provenance of a cut (below). The L-Halo and forests-HDF5 routes are unchanged in every byte except the header's version. The format's policy forbids mixed versions within a dataset, not across packages, so re-emitting the five version 3 packages is not forced by the format; it **is** forced by the end state's "no legacy path" (R): the reader supports one version, and the five datasets are re-emitted locally from their sources (Millennium 760,667,000 halos, 0.58 TB transpose peak; mini-Uchuu 1,451,359,554 halos, 1.1 TB peak; the three micro ones in minutes), the committed version 3 fixtures regenerated, and the format document's version 3 text frozen as history beside version 2's. Cost: a few days of mechanical churn, no new science, and it lands inside Stage A.
- **Cutting the super-forest is a data change inside the current version** when the cut is expressed as a declared **transformed source**: the original ASCII inventory, the original `forests.list`, a **cut forest table** (a `forests.list` with the same tree roots and new forest ids: pieces of a cut forest receive fresh ids above the catalogue's maximum except the largest piece, which keeps the original id so that the dense `ForestIndex` of every untouched forest is unchanged) and one deterministic host transformation: hosts are resolved under the **original** partition (the post-fix-up central the version 2 dataset already records, or `fix_upid` run against the original table), the cut table is then installed, and every halo whose resolved central lies in another forest of the table becomes a central (`upid = id`, `pid = −1`); no host relation is ever invented. Under that declared source, sidecar `ForestID` is truthfully the source forest id, `ForestIndex` is the dense enumeration of the table, `SourceHaloID` is the prefix over the table's forests in the declared order, FoF, progenitor and descendant links stay inside each forest, chains are cycle-free, and `n_forests_total` and the sidecar describe the new census. The table's md5 and the transformation's definition go where the production conversion's provenance already goes: the conversion report and manifest, and the package README's "How the production dataset was made". The transformation is stated in the version 4 text as the ASCII route's rule for a declared cut table; without a table the route refuses a cross-forest host, as it does today.
- **Recording the treatment as a new header attribute would be a further format change** (the exact header attribute set is validated), and so would any new dataset or sidecar column. Nothing in this brief needs one.

## Stage A: a forest-blocked ASCII route, gated at micro-Uchuu scale

**Goal.** The `consistent_trees_ascii` adapter of `convert_trees.py` emits datasets whose rows are grouped by forest in ascending `ForestIndex` in every slab, with one inventory unit per forest in the declared order above, so that the distributed driver and a chunked sweep accept them.

**Scope.** The format bump of open question 1 (the version 4 text, the reader's version constant and tables, the validators, the re-emission of the five packages and their fixtures, the version 3 text frozen as history); the adapter's unit model (`convert/mimic-convert/adapters/ctrees_ascii.py`: `_build_inventory`, `_source_ids`, `iter_forests`; the per-file unit sidecars `units_src_N.npy` written by `scatter.py` already carry each file's (forest, count) pairs, from which the per-forest prefix over files follows without re-reading sources); the producer battery's per-forest `SourceHaloID` interval check for the ASCII route, independent rank-density validation kept, and a per-slab check that `ForestIndex` is non-decreasing for that route (no such check exists today anywhere in the battery), with counterexample fixtures; a conversion of the local `micro-uchuu-ascii` trees; `simulations/micro-uchuu-ascii-horizontal` moved to that dataset **in place (R)** (the end state is replacement, and every consumer of its version 2 fixture is slated for deletion at Stage D; during the A to D window the version 2 fixture moves to one legacy location under `tests/data/` with the three consumers that still need it, the `make tests-distributed` refusal check, the SHAM and HOD snapshot-global batteries until they are retargeted to the new dataset, and the version 2 C reader tests; the package's `halo_properties.yaml` topology types become `long long`, as the reader requires for int64 links); the package's schema-conformance test; and its cross-format identity gate against `micro-uchuu-ascii` read vertically, inheriting the version 2 gate's role including its vertical-path preservation stage (`tests/framework/parity_gate.py`, whose sidecar check derives the source inventory from the file ordinals and must instead prove the inventory from the conversion manifest, because the ASCII route's spanning forests carry −1). Acceptance is the gate's: per-`UniqueGalaxyID` byte identity under `halos-only` and `sage16`, both timestep schemes, plus identity of the new dataset through the distributed comparator at `mpirun -np 4` **and** a serial chunked leg (the distributed gate today runs only the mini-Millennium fixture, so this is a new leg), with the forest-blocking check passing at startup.

**Why first.** Without it no Shin-Uchuu dataset can be distributed or chunked, whatever Stage B decides, and the micro-Uchuu scale (561,266 trees) is where the route is cheap to get right and gate. It depends on nothing else in this brief, and it is the reference every later gate compares against.

## Stage B: the super-forest decision, by measurement, on the version 2 dataset

**The question.** A forest is a connected component under FoF co-membership and descendant links, so the super-forest cannot be made smaller without cutting links, and every cut changes physics: a cut FoF link turns a satellite into a central. Cutting is defensible if the super-forest is held together by a small number of bridging links, such as brief flyby co-memberships that Consistent-Trees' forest linking propagates across the whole box, and costly if it is densely connected at this resolution. Which of the two it is has never been measured. The owner's end state requires a cut; the measurement decides **which** cut, at **what physics cost**, and whether the laptop class the owner wants is reachable at an acceptable cost.

**The measurement, entirely local, before any rewrite.** The version 2 production dataset carries everything the census needs: `Descendant`, `FirstHaloInFOFgroup`, `ForestIndex`, `MostBoundID`, the masses for edge weights, plus the production `forests.list` (7.56 GB, transferred by the owner). Tree membership is recovered by a backward pass from the last slab labelling every halo with its terminal root (a root wherever `Descendant == −1`, in any slab, which the reference reader accepts; the root set is checked against the forests.list tree roots and any root not at z=0 is reported; per-halo correspondence with the physical `#tree` attribution is verified later against Stage S's per-tree inventory, since root-set equality alone does not prove it); two slabs are resident at a time (519,342,987 × 8 B = 4.2 GB each). Then per slab, every FoF link between halos of different trees is a co-membership edge of the **effective** graph (post-fix-up, the topology Mimic consumes), weighted by distinct snapshots, halos involved and mass, aggregated with a bounded representation (streamed per-slab edge lists merged by key; a dense tree × snapshot occupancy matrix would be 88 GB at int32 and is not built); the raw `pid`/`upid` graph can be added from Stage S's records later if the physical explanation is wanted. Outputs: per-tree and per-forest occupancy per slab and over all slabs (the forest half is the 2026-10-07 census above), including the largest indivisible tree; the super-forest's tree graph (104,845,278 trees) and its component sizes under candidate rules (duration or weight thresholds, minimum cuts); for each candidate rule the severed relations, the central promotions per output snapshot, the progenitor-order changes and the halos re-labelled; and a simulation of the driver's two-level partition (`horizontal_partition_cut`: tasks by greedy packing of widest-slab weights, then chunks within each task, applied as fixed forest ranges to every slab, `src/core/horizontal_partition.c`) for candidate task and chunk counts, giving the widest chunk in every slab, which is the memory-relevant quantity, not the largest forest alone. The same census and candidate rules run on micro-Uchuu's dataset first, as the method rehearsal, where the vertical driver can run `sage16` and the rules' effect on output is seen directly.

**The decision gate.** The owner decides on the census and the record is kept as standing evidence under `docs/dev/`: the graph definition, the root correspondence, the edge weighting, the candidate thresholds, the largest individual tree, all-slab piece and chunk maxima, severed relations and promotions, the predicted science differences, the chosen rule, and the chosen laptop class with its implied F. Three outcomes are possible: a rule reaching the wanted class at an acceptable cost; a rule reaching a larger class only (the owner picks the class; a class above 64 GB revises the end state); or no defensible rule, in which case the owner decides between accepting the cost and settling for the uncut dataset on the Mac Studio (then the end state's item (iii) is not reached, and the brief says so). A tree larger than the class's working set cannot be overcome by any whole-tree cut.

## Stage S: the source identity pass (owner transfers, Mac reads)

**Goal.** Exact `SourceHaloID` under Stage A's declared order for every one of the 22,503,649,037 halos, and a compact per-tree inventory, without a conversion.

**Scope.** A read-only converter tool that scans each `tree_*.dat` in one fused pass (md5, `#tree` markers and the id, pid, upid and snapshot columns together; the existing prescan followed by a parse would read the file twice), verifies the file's md5 and halo-row count against the production conversion manifest (which records both; it records no per-file tree count), and writes two things: a **per-tree inventory** (root id, file ordinal, marker order within the file, row count, forest id from the original table; 315,004,242 trees, about 8 GB) that is kept permanently, since with it any later `SourceHaloID` inverts to its tree and row without the per-halo store; and per halo a packed record (`SnapNum` int16, id int64, file ordinal int16, tree ordinal within the file int32, row ordinal within the tree int32, optionally raw pid and upid int64) with overflow checks, 20 B/halo = 0.45 TB, or 36 B/halo = 0.81 TB with the raw hosts. The owner transfers the 11.61 TB source in batches that fit the drive (scenario (a): four batches of at most 3.0 TB; scenario (b): larger), the pass consumes each batch, and the owner deletes it (in scenario (b) the owner may first compress it with zstd, measured 2.95× to 3.4× on one file, keeping an archive of about 3.4 to 3.9 TB for future re-cuts; during compression the raw batch and the growing archive coexist on drive 2). After all files: `forests.list`, `locations.dat` (whose filenames and offsets are checked against the inventory's marker order) and the inventory give forest bases and per-(forest, file, tree) prefixes, so `SourceHaloID` is exact for every halo, spanning forests included; the per-halo records are then bucketed by snapshot and each bucket sorted by id (the converter's external merge sort, `rank_sort.py`, takes int64 keys only, so the key is the id within a snapshot bucket), with the sort's spill budgeted at the records' own size. Duplicate or missing join keys are refused. Cost: one 29 h transfer by the owner in batches, a local streaming scan pooled across the cores and bounded by the drive's read rate, 0.5 to 0.8 TB of records plus their sort spill. No scatter, fix-ups, links, transpose or conversion spill.

## Stage R: the dataset rewriter

**Goal.** One tool that reads a horizontal dataset slab by slab and writes a current-format dataset under a forest table and a row order, with explicit multi-pass memory ownership. Scope is **Consistent-Trees-derived datasets with adjacent links** (`links_adjacent` 1, the only kind this brief produces); any other input is refused, and the general gapped case (stored target-snapshot columns, `NextProgenitor` targets earlier, equal or later than the owner) is recorded as out of scope rather than approximated. Pass 0 reads headers, the sidecar, the two forest tables and the identity records' bounds; pass 1 per slab computes the new row permutation and writes it with (`ForestIndex`, `HaloRankInForest`, `SourceHaloID`) per row to a remap store (32 B/halo, 0.72 TB if kept whole); because the reference rank orders a forest's halos by descending snapshot first, the two passes interleave in descending snapshot order with a per-forest running count (166,547,771 × 8 B = 1.3 GB) supplying each slab's rank base, pass 2 trailing pass 1 by one slab, so a slab's remap entry is needed only by slabs N−1, N and N+1 and about 50 GB of the store is resident; pass 2 per slab rewrites the payload and remaps every link through the target slab's permutation (`Descendant` at N+1, `FirstProgenitor` at N−1, `NextProgenitor` and the FoF links at N; each companion `*Snapshot` column is −1 iff its link is −1, else N+1, N−1 and N respectively), carries the input's `/schema` through unchanged for a current-format input and builds it from the package's `converter_columns.yaml` profile only for a version 2 input, writes the header attributes and the sidecar, verifies each slab, and records checksums, immutable input identity and restart state in a manifest. Three operations: **(M) migration**, version 2 to the current format with identity from Stage S, expected to emit exactly the datasets the Stage A route would emit from the same source; **(C) cut**, current format (or version 2 plus Stage S identity, in one pass) to current format under a cut forest table, resolving hosts under the original partition, applying the severance rule, recomputing FoF chains, `HaloRankInForest` and the progenitor chains (`FirstProgenitor`/`NextProgenitor` order from the reference incremental-insertion loop over the new reference encounter order, ties included, as `links.py` implements it, in int64 throughout) for every forest the table changes, reproducing payload and topology exactly for untouched forests (whose `ForestIndex` and, with the identity multiplier pinned to the uncut reference, whose `UniqueGalaxyID` are unchanged because the largest piece keeps the cut forest's id), and never changing a descendant edge (verified); **(N) no-op**, current format to current format under the identity table, which must reproduce its input exactly in every dataset value, dtype and metadata item (whole-file byte equality additionally depends on HDF5 layout and is checked where the writer's layout is deterministic) and is a permanent self-test. The version 2 input path is deleted at Stage D; (C) and (N) remain as the supported way to produce any future cut dataset, Shin-Uchuu's or Uchuu's. Scratch and outputs are placed on the external volume explicitly; the gate harness's default of the repository's `output/` is overridden.

**Gates, all at scales that fit the Mac Studio.** Before the first gate, `simulations/shin-uchuu`'s package is prepared for the current format (`long long` topology, `/schema`-matching `halo_properties.yaml`), since the reader rejects `int` link declarations. A conversion of the local subset through the Stage A route (197 GB source, about 60 GB output, about 0.5 TB of transient workdir, the rehearsal the 2026-10-06 brief already required, now also the reference); a version 2 dataset of the same subset regenerated locally with `convert_ctrees.py` (which exists until Stage D). G3: (M) of the version 2 subset ≡ the Stage A conversion of the subset in every `/halos` column, the header, the `/schema` group and the sidecar. G3b: (N) is the identity. G3c: (C) of the subset under a test table ≡ the Stage A conversion of the subset declared with the same transformed source (the fix-up stage resolving hosts under the original table, then installing the cut table and severing), plus adversarial fixtures (a table that changes nothing; a severed satellite; a group whose central leaves while its members stay together; a piece that initially holds no central; a tie in progenitor order), plus an **independent reference leg (R)**: small transformed ASCII fixtures whose host columns are canonicalised to the original resolved centrals and then severed, read by the unmodified C reference reader (`src/io/vertical/ctrees/ctrees_utils.c`) through the vertical driver, so that the cut's reconstruction is checked against code that shares nothing with the rewriter. G4: the cross-format identity gate of the migrated subset against `shin-uchuu-ascii` read vertically, under `sage16` and `halos-only`. Cut datasets are additionally gated serial versus chunked versus `mpirun` through the distributed comparator. Deterministic re-run and resume checks. The subset excludes the super-forest, so the extreme case is covered only by the production validation and the science checks of Stage C, and the brief says so.

## Stage C: the Shin-Uchuu production datasets

Preconditions: Stages A, B, S and R gated. Scope: the production rewrite(s) with the identity multiplier re-derived from the new census and recorded, the producer battery, the `sage16` run(s) on the Mac Studio with chunked slab streaming, the science checks step 1 used (the baryon fraction, the z=0 Type 0 count, the halo mass function) compared with the version 2 production run's recorded values, with every difference attributed to the cut rule using Stage B's predicted promotions, and the package README's provenance section rewritten. **Scenario (a)** produces the cut dataset directly from the version 2 dataset in one (C) pass and never materialises the uncut production dataset. **Scenario (b)** produces the uncut dataset first, runs `sage16` on it (uncut floor 333,663,215 halos, about 350 GB at 1 KB per halo, inside 512 GB) and compares per `UniqueGalaxyID` against a retained version 2 run, which isolates the format change from the cut, then produces the cut dataset. **Laptop acceptance (R):** memory per resident halo is calibrated on this executable on the Mac Studio with `MallocLargeCache=0` at the task and chunk counts the chosen class implies, on the cut dataset, under `sage16`, with the build configuration and the class's reserved budget recorded; the predicate is measured peak RSS under that budget with the sweep completing; without a run on an actual laptop of the class the result is a Mac-measured proxy and is labelled as such, and a laptop run, if one is available, is the final acceptance. Nothing is derived from the old pool ratio.

**Validator storage.** The producer battery (`validate_v3.py`) spills whole-dataset external-sort streams, about 195 B/halo on the large L-Halo examples (`convert/mimic-convert/README.md` → "Restart, cleanup and memory"), an extrapolated 4.4 TB at this scale. The subset rehearsal measures the battery's spill and RSS at 406,668,896 halos. A **validator scale slice** is **mandatory in scenario (a)** and required in (b) whenever the source archive is kept: it enumerates every obligation of the battery (manifest binding, source conservation, every invariant, progenitor closure through the target-snapshot columns, chain membership, FoF integrity, `SourceHaloID` uniqueness and order, identity density, `/schema` agreement), gives each a bounded replacement with a stated storage ceiling (independently indexed one-bit-per-halo passes for uniqueness and for density, which are separate properties; per-snapshot and per-target-snapshot work for the rest; no whole-snapshot resident array, so the contract's bounded-read rule still holds above `INT32_MAX` rows), and compares old and new verdicts on representative valid and adversarial datasets before it is trusted on production.

### Time

Both workflows are bounded by the owner's transfers (29 h in total for the source, in four or fewer batches, each followed by a local scan of some hours) and by the Mac Studio's drive bandwidth. The rewriter's production passes read about 2.25 TB and write about 3.25 TB per operation plus the remap store; the census reads the 70 `ForestIndex`, `Descendant` and `FirstHaloInFOFgroup` columns (about 540 GB); the `sage16` runs are of the order of the corrected version 2 run (9 h 35 m on the Mac Studio for the uncut dataset). None of it approaches the version 2 conversion's 6 days, and none of it is on the critical path of the owner's time except the transfers.
