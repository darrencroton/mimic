### 1.4 The deferred behaviour gap: `convert_unit_scalar()` never checks dimensions

`src/core/read_parameter_file.c:591-611` computes `factor = source_cgs / target_cgs` with no comparison of dimensions, unlike the generator-side `_linear_conversion_expr()` which rejects a dimension mismatch. Its callers are `simulation.box_size` against reference `Mpc/h` and `simulation.particle_mass` against `1e10 Msun/h`.

This is **pre-existing and label-agnostic** — the PM confirmed `convert_unit_scalar` is byte-identical at the pre-D8 commit, and today `box_size: {value: 62.5, units: "1e10 Msun/h"}` is already accepted and silently mis-scaled by ~6.4e18. D8 did not introduce the class; it added one more label (`Mpc/h km/s`) to a registry of thirty that all share the hole, and that label is the most plausible one an author would reach for by mistake on a length scalar because it embeds the literal string `Mpc/h`.

Both independent code reviewers raised it, converged on its severity (P2-class on its own), and converged on the same fix direction, which this plan adopts: emit a `mimic_unit_label_dimension()` companion from `generate_unit_registry_h()` and compare source dimension against reference dimension in `convert_unit_scalar()`.

`docs/DEVELOPER-GUIDE.md:635-642` additionally documents `reference_units` as a four-row table; it has had five entries since `612f83da`, and `:646` documents `units` as "a label from the unit registry" without restricting it to the field's dimension — which §1.4's fix makes true rather than aspirational.

**The fifth entry is a composite, not a fifth basis element**, and the documentation must keep that distinction. Mass, length, velocity and derived time remain the complete four-dimensional basis; `specific_angular_momentum` is a derived composite (length × velocity) that exists so a property can declare it. `.agents/skills/mimic-properties/SKILL.md:78` already words it this way deliberately, and the Developer Guide edit must match rather than presenting a five-element basis.

## 2. Design

### 2.1 Format-version expectation (Slice 1)

Change both `assert_hdf5_schema_layout()` calls at `test_output_formats.py:607-608` from `"1.1"` to `"1.2"`, and rewrite the comment above them to state the durable fact: the tracked baselines are regenerated whenever a schema-affecting change lands, so they carry the current format version, and this expectation moves with `hdf5_format_version`. Correct `data_loader.py:361-364`'s docstring the same way — it must no longer claim tracked baselines are `"1.1"`, while keeping its actual load-bearing instruction (that every call site states the version it expects, because there is no safe default).

**This is a test-expectation correction, not a weakening.** The assertion still pins an exact version and still fails on drift; only the pinned value moves, to match the files the repository actually tracks. Do not relax it to a range, do not make it optional, and do not give it a default.

**No `hdf5_format_version` ratchet moves.** The version is already `1.2` in the current build (`src/io/output/metadata_hdf5.c:136`, `const char *hdf5_format_version = "1.2";`, guarded by the comment at `:135` instructing that it be incremented when the output schema changes) and `1.2` in the committed baselines. This plan changes no structural byte layout, so that literal must not be touched.

### 2.2 Dimension validation (Slice 2)

In `generate_unit_registry_h()` (`scripts/generate_properties.py:852-887`), emit a **fourth** accessor alongside the three that already exist (`mimic_unit_label_cgs`, `mimic_unit_label_carried`, `mimic_unit_label_h_convention`), following their exact established shape:

```c
static inline const char *mimic_unit_label_dimension(const char *label);
```

returning the registry `dimension` string for each label in `sorted(UNIT_REGISTRY)` order and `NULL` for an unknown label — mirroring how `mimic_unit_label_h_convention()` already returns `NULL`.

In `convert_unit_scalar()` (`src/core/read_parameter_file.c`), before computing the factor, compare the source label's dimension against the reference label's dimension and `FATAL_ERROR` on mismatch, following the existing `unit_label_cgs()`/`unit_label_h_convention()` helper pattern and their error wording. Reuse the existing `FATAL_ERROR` idiom; add no new error machinery, no new logging, no new configuration.

**Why a runtime check and not a generator-time one:** run files supply arbitrary `units` strings at load time, so the generator cannot see them. The generator already rejects dimension mismatches for *property* declarations; this closes the same hole for *parameter* scalars, making the two paths consistent.

**Vision alignment.** `docs/VISION.md` Principle 3 makes metadata the source of structural truth, and the vision statement asks that hidden assumptions be harder to introduce. A units label that is accepted and silently mis-scaled is precisely a hidden assumption; rejecting it loudly at load time is the vision-aligned behaviour. The check adds no configuration axis and no new concept — it enforces a rule the registry already encodes.

**Accepted behaviour change, stated plainly:** run files that today pass a dimensionally-wrong unit for `simulation.box_size` or `simulation.particle_mass` and receive a silently mis-scaled value will now fail at load with a clear message. No run file in the repository does this (Slice 2 must verify that), so no shipped configuration changes behaviour.
