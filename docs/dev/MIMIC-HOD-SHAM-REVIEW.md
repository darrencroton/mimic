# HOD and SHAM models: scientific review and Mimic design context

**Status (2026-10-04):** design context, superseded on every decision by [`MIMIC-HOD-SHAM-IMPLEMENTATION-PLAN.md`](MIMIC-HOD-SHAM-IMPLEMENTATION-PLAN.md), whose Frozen Decisions table records the owner's choices; where this review and the plan differ, the plan governs. This file is kept as the literature and design rationale behind those choices.

This review summarizes the main scientific ideas behind halo occupation distribution (HOD) and subhalo abundance matching (SHAM) models, compares widely used formulations, and recommends a deliberately small, modern starting point for Mimic. It is design context for a later implementation plan; it does not prescribe work slices or claim that either model has been implemented. The literature list is selective rather than exhaustive, and every bibliographic record below was checked against the arXiv listing and the publisher's Crossref metadata.

The project context was anchored in the active [Mimic development pathway](MIMIC-DEVELOPMENT-PATHWAY.md), the completed [snapshot-global modules plan](../../archive/dev-plans/snapshot-global-modules/MIMIC-SNAPSHOT-GLOBAL-MODULES-PLAN.md), and its [archived handoff](../../archive/handoffs/HANDOFF-snapshot-global-pm-run-2026-10-03.md). Those planning records locate the new capability and known boundary; current source and metadata remain the authority for what Mimic does.

## Recommendations at a glance

For a new HOD package, start with a threshold sample using the five-parameter central-plus-satellite form of Zheng et al. (2005). Draw a Bernoulli central and, conditional on its presence, a Poisson satellite count; put the central at the host center and satellites in a documented radial and velocity model. Calibrate the parameters for the chosen sample and redshift against an explicit halo mass function, usually outside the run; record the calibration and report realized counts separately from the expected occupation. A proper HOD also needs a way to create galaxy records. Mimic's current `post_snapshot` callback only receives borrowed existing records and can update their properties in place, so it cannot append rows. The simpler durable direction is to preserve the inherited Type 0/1 tree scaffold, mark HOD sample membership with a model-owned flag, retire carried Type 2 rows each snapshot, and add newly drawn Type 2 HOD satellites to their host's output segment through one generic core record-creation/append operation. This keeps ordinary schema, output, and inheritance machinery while keeping the model-specific occupation in the HOD package. A separate external catalogue and writer remains an option only if a future use case needs a physically separate product.

Replace the current demonstrator SHAM target with a global snapshot rank match to a named, tabulated or parameterized observed stellar-mass function (SMF), using `Vpeak` as the default proxy where its history is adequately available. Rank a **resolved-only** candidate population, centrals plus resolved subhalos, above an explicit completeness floor; treat inclusion of carried-forward orphans as an optional, more complex mode that needs a calibrated disruption or lifetime prescription. Initially keep scatter off for an auditable rank match; then offer intrinsic scatter only with scatter-aware rematching so the output SMF remains the stated target. This is a stronger scientific baseline than the present analytic power-law target and adds modest complexity. Keep the target sample, stellar-mass convention, halo mass/proxy convention, volume, candidate population, orphan policy, and scatter meaning explicit in parameters and output provenance.

Keep SHAM in its existing model package and replace `sham_global_rank` with the calibrated rank model; put HOD in a separate new model package because it has a different population law, sample flag, and synthetic-record requirements. This follows Mimic's one-model-package-per-build boundary and keeps each model's run configuration and properties coherent.


## 1. Scientific review

### 1.1 Halo occupation distribution

An HOD describes the probability that a dark-matter halo of specified properties hosts a specified galaxy population. In the classic mass-only formulation, the central quantity is the conditional distribution `P(N | M)`, supplemented by the galaxies' spatial and velocity distributions inside the halo. The HOD is a statistical population model: its mean occupation is not itself a catalogue of galaxies. Its attraction is that it separates halo abundance and clustering, measured or predicted from dark matter, from a compact set of galaxy–halo parameters. Berlind & Weinberg (2002) established this language and showed why both occupation and within-halo placement matter for galaxy clustering ([ApJ 575, 587](https://doi.org/10.1086/341469); [arXiv:astro-ph/0109001](https://arxiv.org/abs/astro-ph/0109001)). A separate companion paper, Berlind et al. (2003), connected the HOD to the predictions of semi-analytic and hydrodynamic galaxy-formation models ([ApJ 593, 1](https://doi.org/10.1086/376517); [arXiv:astro-ph/0212357](https://arxiv.org/abs/astro-ph/0212357)); the two are often conflated and must be cited separately.

For a luminosity- or stellar-mass-threshold sample, a widely used five-parameter form combines the central error-function transition and satellite power law introduced by Zheng et al. (2005) with the central-gated satellite mean written explicitly by Zheng, Coil & Zehavi (2007):

```text
<N_cen(M)> = 1/2 [1 + erf((log10 M - log10 M_min) / sigma_logM)]
<N_sat(M)> = <N_cen(M)> [(M - M_0) / M_1']^alpha,  M > M_0
```

and zero satellite mean below `M_0`. Zheng et al. (2005) give the central form in equation 1, the satellite power law in equation 3, and state that `N_sat = 0` by definition when `N_cen = 0`; the explicit `⟨N_cen⟩` prefactor is equation 5 of Zheng, Coil & Zehavi (2007). Here `M_min` and `sigma_logM` describe the central transition, `M_0` is a satellite cutoff, `M_1'` sets satellite abundance, and `alpha` is its high-mass slope. Note that with this form `M_1'` is not the mass at which a halo hosts one satellite on average. This central/satellite split captures the qualitative effect of a central luminosity relation with scatter and an approximately power-law satellite population. Zheng et al. (2005; [ApJ 633, 791](https://doi.org/10.1086/466510); [arXiv:astro-ph/0408564](https://arxiv.org/abs/astro-ph/0408564)) developed the five-parameter fit, which Zheng, Coil & Zehavi (2007; [ApJ 667, 760](https://doi.org/10.1086/521074); [arXiv:astro-ph/0703457](https://arxiv.org/abs/astro-ph/0703457)) applied to SDSS and DEEP2 clustering. It is an empirical parameterization, not a first-principles law.

The mean satellite occupation does not fully specify the joint distribution. A common and recommended convention is to draw `N_cen ~ Bernoulli(⟨N_cen⟩)`, then draw `N_sat ~ Poisson(lambda_sat)` only if `N_cen = 1`, with `lambda_sat = [(M-M_0)/M_1']^alpha`. This makes the displayed unconditional mean satellite count equal to `⟨N_cen⟩ lambda_sat`; Zheng et al. (2005) state this central gating explicitly. Poisson satellite counts are a useful simple baseline: Zheng et al. find the satellite distribution close to Poisson over substantial mean-occupation ranges, while the low-occupation moments in Berlind et al. (2003) show that Poisson is not universal. Another convention draws satellites independently, without requiring a central. These two choices agree at high mass where centrals are nearly certain, but differ near the central threshold and must not be conflated. The conditional convention suppresses satellites in halos that failed to draw a central; the ungated convention can produce satellite-only systems. Both occur in the literature and in software, so a report or parameter file should state the joint law, not only the two means.

#### Normalization against the halo mass function

The HOD parameters are tied to a number density only through the halo mass function (HMF) of the simulation they are applied to. For a mass-only HOD the mean galaxy number density, satellite fraction, and galaxy bias are

```text
n_gal   = Int dM  (dn/dM)(M)  [ <N_cen(M)> + <N_sat(M)> ]
f_sat   = Int dM  (dn/dM)(M)  <N_sat(M)>  /  n_gal
b_gal   = Int dM  (dn/dM)(M)  b_h(M) [ <N_cen(M)> + <N_sat(M)> ]  /  n_gal
```

where `dn/dM` is the differential number density of distinct host halos per unit mass in the same mass definition as the occupation law, and `b_h(M)` is the halo bias. In a simulation the integral is a sum over the host catalogue above the completeness limit. The usual practice when fitting a threshold sample is to fix the *expected* `n_gal` to the observed value and solve for `M_min` given the other four parameters. A finite mock still has stochastic count fluctuations because centrals and satellites are drawn; do not force the realized count to the expectation unless a separate fixed-count sampling model is intended. A mock that adopts literature parameters without re-solving this integral on its own HMF, mass definition, and cosmology will generally not reproduce the intended *mean* number density. The HMF below the simulation's completeness limit contributes to `n_gal` whenever `⟨N_cen⟩` is non-negligible there, so a defensible completeness criterion is `log10(M_lim) < log10(M_min) - 2 sigma_logM`, or the missing contribution must be quantified and reported.

Basic HOD parameters generally describe a threshold-selected sample. They do not, alone, provide a continuous stellar mass or luminosity for each generated galaxy. A conditional luminosity function (CLF), or conditional stellar-mass function (CSMF), extends the model to a distribution `Phi(L | M)` or `Phi(M_* | M)`, whose integral above a threshold gives an occupation. It can be fit to the luminosity/mass function and clustering for several selections at once. Yang, Mo & van den Bosch (2003) present a foundational CLF framework ([MNRAS 339, 1057](https://doi.org/10.1046/j.1365-8711.2003.06254.x); [arXiv:astro-ph/0207019](https://arxiv.org/abs/astro-ph/0207019)). CLF/CSMF adds flexibility and data requirements; it should be chosen when Mimic needs galaxy masses across a range rather than one threshold mock.

The conventional mass-only HOD assumes occupation depends only on halo mass. It therefore cannot express assembly bias: at fixed mass, occupation may correlate with formation history, concentration, environment, or another secondary property, changing clustering while preserving the mean occupation. A decorated HOD adds a secondary halo property and redistributes occupation at fixed mass under constraints that preserve the chosen mass-only mean. Hearin et al. (2016) formulate a compact decorated HOD and quantify its effect on predicted clustering and lensing ([MNRAS 460, 2552](https://doi.org/10.1093/mnras/stw840); [arXiv:1512.03050](https://arxiv.org/abs/1512.03050)). This is a meaningful modern extension, but it requires a well-defined secondary halo property, calibration data, and enough complete halos to constrain it. It is not an automatic upgrade if the input catalog lacks that property.

#### Spatial, velocity, and sample assumptions

A mock HOD also needs a phase-space prescription. The recommended simple baseline places the central at the host potential minimum (or catalog center) with the host bulk velocity and no central velocity bias. Draw satellite radii from a truncated NFW profile using an explicit concentration–mass relation, sample directions isotropically, offset from the host center, and wrap positions at the periodic boundary. Derive `V_vir` from host mass at that snapshot, redshift, cosmology, and mass definition. Draw each satellite's three velocity-offset components independently from a zero-mean Gaussian with one-dimensional dispersion `sigma_1D = V_vir / sqrt(2)`, the isothermal-sphere virial approximation, then add the host bulk velocity; use a validated catalog velocity dispersion only if its convention matches, and set satellite velocity bias to unity. This is a deliberately simple prescription, not a claim that the velocity distribution is exactly Gaussian or that the isothermal approximation captures an NFW Jeans solution. An NFW Jeans model or central/satellite velocity-bias parameters are later refinements that require calibration data. Position units, periodic-box wrapping, velocity units, halo boundary, and whether output is in real or redshift space must be defined. Using resolved subhalo positions instead of a synthetic profile produces a useful hybrid, but its satellite abundance and phase-space distribution remain limited by subhalo completeness and it is no longer a conventional subhalo-independent HOD placement model.

The mass in the occupation law must match the calibration: e.g., spherical-overdensity `M_200c`, `M_200m`, or FoF mass are not interchangeable. The threshold, redshift, cosmology, observational stellar-mass or luminosity definition, and number density must also be tied to the data being fit. An HOD fit to one threshold does not imply a correct SMF at all masses. Intrinsic scatter in central stellar mass, satellite stellar mass, or occupation at fixed halo mass are distinct modeling choices and should be stated separately.

#### Significant HOD implementations

Three influential choices illustrate the range without treating software packages as physical models. The Zheng et al. five-parameter HOD is a compact threshold model and remains a practical baseline; it is popular because it captures the central transition and satellite power law with interpretable parameters. CLF/CSMF models such as Yang et al. (2003) are more informative when the target includes the abundance distribution over luminosity or stellar mass, at the cost of more parameters and calibration. Decorated HOD models such as Hearin et al. (2016) are appropriate when assembly bias and secondary-property dependence are supported by input data and observations.

Halotools is an open-source framework for constructing mock galaxy catalogues from halo catalogues. It implements multiple HOD, CLF, and abundance-matching models, along with spatial and velocity profiles; it is a software framework rather than one HOD prescription ([Hearin et al. 2017, AJ 154, 190](https://doi.org/10.3847/1538-3881/aa859f); [arXiv:1606.04106](https://arxiv.org/abs/1606.04106)). AbacusHOD is a high-throughput, extended multi-tracer HOD implementation useful for large simulation suites and parameter exploration ([Yuan et al. 2022, MNRAS 510, 3301](https://doi.org/10.1093/mnras/stab3355); [arXiv:2110.11412](https://arxiv.org/abs/2110.11412)). These implementations are evidence that mock-generation details and computational performance matter; they do not remove the need to state the chosen occupation and phase-space laws.

### 1.2 Subhalo abundance matching

Abundance matching assigns a galaxy observable to a halo or subhalo proxy by matching cumulative number densities of two **different** variables. In its simplest zero-scatter, monotonic form,

```text
n_gal(> M_*)  =  n_h(> X),        X = M_peak, V_peak, V_max, or another proxy
```

where `n_gal(> M_*)` is the cumulative comoving number density of galaxies above stellar mass `M_*`, from the observed SMF, and `n_h(> X)` is the cumulative comoving number density of candidates above proxy value `X`, counted over distinct host halos plus, for subhalo-based matching, the surviving subhalos. The two sides are densities of unlike quantities; the equation does not say that any galaxy value equals any halo value. It defines a monotonic map by inverting the galaxy side,

```text
M_*(X) = n_gal^{-1}( n_h(> X) ),
```

so the candidate with proxy `X` receives the stellar mass at which the galaxy population is exactly as abundant as candidates at or above `X`. In a finite box this is the rank recipe: sort candidates by descending `X` and map candidate rank `r` to the target inverse cumulative abundance at `(r + 1/2) / V_box`. If the target is supplied as a finite ordered mass list rather than an analytic or tabulated cumulative function, pairing the two sorted lists at equal ranks is the discrete special case. The proxy is a scientific assumption: present-day subhalo mass can be stripped after infall, so many SHAM analyses use a peak proxy such as `M_peak` or `V_peak`. Peak circular velocity often correlates more closely with the depth of the pre-infall potential and is less sensitive to stripping than current mass, while `M_peak` can be more directly tied to accumulated growth. Neither proxy is universally best; the choice depends on the simulation, sample, and calibration.

The classic SHAM idea was made influential by Conroy, Wechsler & Kravtsov (2006), who matched galaxy luminosity to halo `V_max` and, for subhalos, used maximum circular velocity at the epoch of accretion; the resulting mocks reproduced clustering across scales ([ApJ 647, 201](https://doi.org/10.1086/503602); [arXiv:astro-ph/0512234](https://arxiv.org/abs/astro-ph/0512234)). Vale & Ostriker (2006) developed a related halo/subhalo hierarchy approach ([MNRAS 371, 1173](https://doi.org/10.1111/j.1365-2966.2006.10605.x); [arXiv:astro-ph/0511816](https://arxiv.org/abs/astro-ph/0511816)). SHAM is economical and empirical: it needs a halo catalog with a suitable proxy and a target galaxy abundance function. It does not by itself model gas, star formation, or the time evolution of stellar mass.

Intrinsic scatter is important. If one first matches a zero-scatter proxy relation and then adds independent lognormal stellar-mass scatter, the resulting stellar-mass function generally no longer equals the target, especially near the steep high-mass tail. Scatter must have a defined meaning, for example `sigma_logMstar|X` in dex at fixed proxy, and the mapping must be rematched or deconvolved so that its forward-scattered population reproduces the target SMF. This is a moderate numerical feature, not a free upgrade: an implementation needs a positive, monotonic intrinsic relation, a convergent solver, boundary handling, and validation of the forward-convolved SMF. Behroozi, Conroy & Wechsler (2010) quantified how scatter and uncertainties in data and halo abundances affect inferred stellar-to-halo relations ([ApJ 717, 379](https://doi.org/10.1088/0004-637X/717/1/379); [arXiv:1001.0015](https://arxiv.org/abs/1001.0015)). Reddick et al. (2013) iteratively inferred a relation including scatter and found that `V_peak` with `0.20 ± 0.03` dex intrinsic scatter in stellar mass at fixed `V_peak` fit their clustering and group conditional stellar-mass constraints; the quoted ±0.03 is their 95% interval, with ±0.02 at 68%. This is a result for their sample and calibration, not a universal constant ([ApJ 771, 30](https://doi.org/10.1088/0004-637X/771/1/30); [arXiv:1207.2160](https://arxiv.org/abs/1207.2160)).

Reddick et al. also examined satellite **disruption**, which is distinct from orphan modeling. They introduced a cut `mu_cut`: a subhalo whose present mass has fallen below `mu_cut M_peak` is treated as disrupted and excluded from the matching, effectively receiving zero stellar mass, with `mu_cut` explored from 0 to 0.15 (a value of 0.1 removed about 4% of their subhalos). Their best fit is `mu_cut = 0.03`, with upper limits 0.07 at 68% and 0.11 at 95%. They state explicitly that they do not include orphan galaxies, that they cannot rule such models out, and that their lowest stellar-mass sample shows a slight deficit of galaxies in the innermost regions of groups; they discuss whether this could reflect orphans. The lesson for Mimic is that the candidate population is itself a model choice: a disruption cut removes tracked subhalos, an orphan population adds untracked ones, and each changes both the rank mapping and the observables.

Scatter is sometimes implemented as noise added to `log X` before ranking. This preserves the target mass list by construction, but the scatter parameter then describes rank perturbation in proxy space, not intrinsic lognormal stellar-mass scatter at fixed proxy. These conventions can yield similar mocks but are not scientifically identical. A model must name the convention and validate the output SMF. If temporal coherence of scatter matters, independent per-snapshot random draws can make stellar masses jump along a branch. A stable branch identifier and a correlated stochastic process are needed for correlated history; a snapshot identity is enough only for deterministic reruns at that snapshot.

#### Secondary-property matching: the concentration-dependent proxy

At fixed halo mass, occupation or proxy may depend on assembly history or concentration. The cleanest primary-source example of a secondary-property SHAM is the concentration-dependent proxy of Lehmann et al. (2017; [ApJ 834, 37](https://doi.org/10.3847/1538-4357/834/1/37); [arXiv:1510.05651](https://arxiv.org/abs/1510.05651)), equation 1:

```text
v_alpha = v_vir (v_max / v_vir)^alpha,     equivalently  log v_alpha = alpha log v_max + (1 - alpha) log v_vir
```

with both velocities evaluated at the epoch of peak mass. `v_vir` is derivable from a halo mass definition, cosmology, and redshift; it does not require a pre-existing `R_vir` field. The required `v_max` is its value at the epoch of `M_peak`, which is not necessarily the historical maximum `V_peak` (often reached during a major merger). At fixed redshift and mass convention, `v_vir` is set by halo mass while `v_max / v_vir` rises with concentration, so `alpha` dials in how strongly the proxy, and hence the assigned galaxy mass, depends on concentration at fixed mass. The end points recover the two conventional proxies: `alpha = 0` is mass-like and resembles `M_peak` matching, while `alpha = 1` is `v_max` at the `M_peak` epoch, not necessarily `V_peak`. Fitting SDSS projected clustering over four luminosity thresholds on the DarkSky-400 simulation, Lehmann et al. found `alpha = 0.57 (+0.20/-0.27)` with `0.17 (+0.03/-0.05)` dex scatter, and excluded both `alpha = 0` and `alpha = 1` and zero scatter at `p < 0.001`. They did not require a `mu_cut` with this proxy. What this family adds is a controlled amount of galaxy assembly bias through one interpretable parameter. What it costs is an extra peak-epoch `V_max` history value (not a field present in the inspected horizontal inputs or tracked by the current SHAM module), plus a parameter degenerate with scatter and **not** constrained by the SMF alone, so it needs clustering or satellite-fraction data to calibrate; its physical meaning also changes with `alpha`, which complicates comparison with other SHAM results. It is not the recommended Mimic default because Mimic currently has no clustering validation path and the gain is a second-order clustering correction on top of a baseline that does not yet exist.

A more elaborate member of the same family is SHAMe, the "SHAM extended" model of Contreras, Angulo & Zennaro (2021a, b). It adds a tunable assembly-bias amplitude by preferentially selecting subhalos of equal internal property but different large-scale bias ([MNRAS 504, 5205](https://doi.org/10.1093/mnras/stab1170); [arXiv:2005.03672](https://arxiv.org/abs/2005.03672)), and in its full form also includes orphan tracking, a tidal-disruption parameter, and a star-formation-rate prescription tied to dark-matter accretion, calibrated on a low-resolution gravity-only run against TNG300 clustering in redshift space ([MNRAS 508, 175](https://doi.org/10.1093/mnras/stab2560); [arXiv:2012.06596](https://arxiv.org/abs/2012.06596)). It is a useful reference for what a complete modern SHAM contains, and its parameter count shows the cost.

A broader approach is UniverseMachine (Behroozi et al. 2019), which assigns star-formation rates using halo growth-history features including `v_Mpeak` and correlations with recent `Δv_max` history, then integrates star formation over time to predict stellar mass; it fits multiple observables across redshift ([MNRAS 488, 3143](https://doi.org/10.1093/mnras/stz1182); [arXiv:1806.07893](https://arxiv.org/abs/1806.07893); [official code and data](https://www.peterbehroozi.com/code.html)). It is an empirical galaxy-evolution model with an abundance-matching heritage, not a simple snapshot SHAM recipe, and substantially expands the state and inference problem. It is retained here as a boundary and possible future direction, not a proposed replacement for the simple cross-sectional rank model.

#### Significant SHAM approaches

The three useful families for this review are: (1) deterministic monotonic matching to `M_peak` or `V_peak`, the cleanest and cheapest baseline, exemplified by Conroy et al. (2006) and Vale & Ostriker (2006); (2) scatter-aware matching, in which a target SMF is convolved/deconvolved consistently with intrinsic scatter and proxies are tested against clustering and conditional mass data, exemplified by Behroozi et al. (2010) and Reddick et al. (2013); and (3) secondary-property or assembly-bias-aware matching, exemplified by the `v_alpha` proxy of Lehmann et al. (2017) and by SHAMe, which can fit assembly-dependent clustering but costs additional halo histories, clustering calibration data, and parameter interpretation. UniverseMachine sits outside all three as a boundary case.

### 1.3 What makes a comparison meaningful

HOD and SHAM are empirical galaxy–halo assignments, but they answer different questions. HOD specifies a conditional population distribution as a function of host properties and explicitly samples central/satellite counts and phase space. SHAM orders individual halo/subhalo candidates and assigns observables by rank. A threshold HOD can generate satellites in halos with no resolved subhalo; a conventional subhalo SHAM cannot unless it adds an orphan or synthetic candidate population. HOD can be calibrated from number densities, clustering, lensing, and group data; SHAM often uses the SMF plus clustering/conditional stellar-mass constraints to choose proxy and scatter. Comparing their outputs requires the same cosmology, redshift, mass definition, galaxy selection, volume, observational mass/luminosity convention, and treatment of orphans. Neither is a semi-analytic model, and neither should be described as a first-principles prediction.

## 2. Recommended Mimic implementation context

### 2.1 Global-snapshot capability and HOD population construction

Mimic's `process_snapshot` callback runs after all FoF groups in a horizontal snapshot have been marshalled into the current generation, before that generation is published for inheritance or written. It receives a borrowed `const Halo *` array, so halo topology and the array itself cannot be changed; the pointed-to `GalaxyData` properties may be updated in place and those writes flow to both later inheritance and current-snapshot output. The driver makes no callback copy (`src/core/horizontal_driver.c`, lines 1248–1276); the callback also runs for an empty snapshot. It cannot safely append records, delete them, reorder the population, or change halo/galaxy relationships. This matches the physics-agnostic core boundary in [`docs/VISION.md`](../VISION.md) and the snapshot callback contract in `src/core/module_interface.h`.

The callback limitation does not require a separate output catalogue. HOD occupation and placement are local to one FoF host once its calibrated parameters are fixed, so the existing `post_timestep` phase can construct the realization after the host's tree processing. The recommendation is an in-place population scaffold: retain all inherited Type 0/1 rows, including tree centrals and resolved satellites, but mark them as outside the HOD sample by default using a model-owned Boolean such as `HODGhost`. Do not overload global `Type` to mean HOD selection. Core inheritance can demote non-main Type 0/1 progenitors to Type 2 while assembling the current FoF workspace; `horizontal_driver.c` gathers inheritance before `process_halo_evolution`, which then runs the module pipeline (`src/core/horizontal_driver.c`, lines 604–659; `src/core/inheritance.c`, lines 162–194). In `pre_timestep`, reset `HODGhost=true`, clear HOD-assigned fields, and mark every Type 2 row Type 3 on every processed snapshot. The demoted or carried Type 2 rows are therefore removed before that snapshot's rows are marshalled, while the Type 0/1 anchor remains. The pre-step reset runs even on snapshots not selected for output, preventing stale assignments when output cadence changes. Core already omits Type 3 from marshalled output (`src/core/output_buffer.c`, lines 38–43); retaining Type 0/1 scaffold preserves the ordinary central anchor required by tree inheritance.

On output snapshots only, `post_timestep` evaluates the central Bernoulli for each eligible Type 0 host. If selected, set that host's HODGhost false, draw a conditional Poisson satellite count, create those satellites as Type 2 rows with HODGhost false, and leave Type 1 scaffold rows ghosted. The new satellites are linked into the host's halo segment and may be inherited into a later descendant workspace (or have no descendant); whenever inherited, the next pre-step retires them before that workspace is marshalled, so no old synthetic satellite survives in a later output and this baseline has no persistent satellite history. Existing tree Type 2 orphans are also excluded by this resolved-host baseline. Snapshot choice is configured in the run file as `output.snapshot_list` (stored internally as `NOUT`/`ListOutputSnaps`); an empty list selects every snapshot. The same output selection gates global SHAM ranking and mass assignment, but proxy-history accumulation and selection-state reset still happen on every processed snapshot. Keeping scaffold rows in standard output means HOD consumers must filter on HODGhost, while existing consumers can continue to use Mimic's normal tree population and Type semantics. These newly generated Type 2 rows represent analytic HOD satellites with no resolved subhalo and no merger clock; the HODGhost flag, not Type alone, identifies sample membership. Record this mixed-output contract in the model metadata and output documentation.

One generic core record-creation/append operation is the necessary extension. It should initialize generated properties, assign collision-safe identity, copy or set host linkage, and preserve the raw input halo's contiguous `FirstHalo`/`NHalos` slice used by marshalling and future progenitor gathering. Appending blindly to the workspace end and merely increasing a host count would corrupt that mapping when rows for other source halos lie between. The API also needs a safe append point that does not invalidate pointers or counts cached by the per-FoF dispatcher; a queued-per-host append flushed during marshalling is one possible design, not a requirement to freeze now. Core should own generic allocation, property defaults, ID allocation, and segment bookkeeping, while the HOD package owns its sample flag, occupation law, and phase-space values. This is a smaller extension than a second catalogue, writer, schema, and output lifecycle, and it preserves the existing output and inheritance paths. Add HOD records only at the existing mutable `post_timestep` commit boundary, after the host's physics substeps; do not add a new callback mode or create rows from a future coupled-rate right-hand-side evaluation, which must remain pure. Prefer stable indices/handles for segment linkage over exposed mutable arrays or pointers retained across growth. Seed stochastic draws and allocate synthetic IDs from stable host identity, snapshot, and per-host ordinal so results do not depend on traversal order or eventual MPI rank assignment.

#### The HOD model itself

The new HOD package should begin with one explicitly selected threshold sample and a conventional mass-only Zheng-style law. The model should operate on one distinct host per FoF group (the Type 0 central host), not independently on every subhalo as a host. For each host of the selected mass definition, evaluate `<N_cen>` and `lambda_sat`; draw a central Bernoulli and, only if present, a conditional Poisson satellite count. This central-gated convention is the recommended baseline because it is well-defined and common, but it must appear in the configuration and provenance. Supply calibrated five-parameter values for each target sample/redshift, using the Section 1.1 abundance integral and an appropriate complete host mass function during offline calibration. For every output snapshot, require a matching calibrated parameter set or an explicit validity window; fail or mask output outside that range instead of extrapolating silently. Do not add an in-run global `M_min` solve to the first module: per-FoF draws do not see a complete snapshot HMF, and such a solve would require another global preparation pass. Report the selected parameter set and realized `n_gal`/`f_sat`; an expected-density or occupation diagnostic can be reconstructed from the written scaffold or a later analysis tool. Bernoulli and Poisson draws give stochastic realization-to-realization count scatter; do not imply that normalizing the expectation forces each mock to contain exactly the observed target count. Do not infer a continuous stellar mass for each generated object from threshold-only parameters. If a continuous stellar-mass output is required in the first release, use a separately specified conditional stellar-mass function and state its calibration rather than quietly treating threshold occupation as a mass relation.

For placement, use the catalog host center and bulk velocity for the central, with zero central velocity bias. For satellites, draw radii from a truncated NFW profile using an explicit concentration–mass relation, sample directions isotropically, offset from the host center, and wrap positions at the periodic boundary. Derive `V_vir` from host mass at that snapshot, redshift, cosmology, and mass definition. Draw the three velocity-offset components independently from a zero-mean Gaussian with one-dimensional dispersion `sigma_1D = V_vir / sqrt(2)`, the isothermal-sphere virial approximation, then add the host bulk velocity; use a validated catalog velocity dispersion only if its convention matches, and set satellite velocity bias to unity. This is a clear inexpensive baseline, not a claim that the distribution is exactly Gaussian or that the isothermal approximation captures an NFW Jeans solution. NFW Jeans velocities and fitted central/satellite velocity-bias parameters are later refinements requiring calibration data. The inspected horizontal packages do not supply a common concentration field, so the concentration–mass relation remains an explicit model assumption. Using input subhalo phase-space locations is a plausible optional hybrid, but its incompleteness and satellite selection must be measured. Do not add orphan trajectories or track satellites over time in the initial mass-only HOD: a per-snapshot statistical mock does not require temporal identity matching. If later science requires cross-snapshot synthetic tracks, that is a separate feature with explicit matching and ID semantics.

### 2.2 New HOD data, units, reproducibility, and limits

Before any HOD mock is scientifically interpretable, choose the halo mass definition to which the parameters were calibrated; convert consistently where the catalog differs. Current horizontal packages expose host mass and positions/velocities, but their fields and conventions differ. For example, the micro-Uchuu ASCII horizontal metadata documents `M_Crit200` as carrying the native Consistent-Trees `Mvir` in `Msun/h`, which the package describes as M200c (the dataset name and the Rockstar definition should be confirmed against the Uchuu catalog documentation before calibration), positions in `Mpc/h`, and a producer-derived `Len` ([`halo_properties.yaml`](../../simulations/micro-uchuu-ascii-horizontal/halo_properties.yaml), lines 9–16 and 67–80). Other packages must be checked individually. The parameters `M_min`, `M_0`, and `M_1'` must use the same mass units and definition as the host field. State whether the observational threshold is in physical `M_sun` or `M_sun/h`, whether the stellar masses assume a particular IMF/aperture, and how `h` is applied. Convert the comoving box side to one consistent length unit before computing `V_box`; use the simulation's actual box volume and completeness rather than a fixture's nominal size.

The output records need explicit identity and provenance. A deterministic counter-based random draw keyed by configured seed, snapshot, host identity, and draw index makes counts and positions reproducible independent of iteration order, in keeping with the vision document's rule that stochastic modules seed from stable per-halo keys rather than a traversal-ordered stream. Satellite identity can then be derived from that tuple with collision checking. `UniqueGalaxyID` is assigned when a galaxy is born and copied unchanged when that galaxy is inherited, so it is a persistent object key along its surviving history; a Type 3 retirement followed by a new birth gets a new key (`src/core/inheritance.c`, lines 23–34 and 97–107; core property metadata calls it a persistent run-scoped ID). In horizontal inputs, its components are source `ForestIndex` and `HaloRankInForest`, rather than a traversal or MPI-task counter (`src/core/horizontal_driver.c`, lines 535–551), so it is stable for a fixed input identity across traversal and partitioning. It can seed reproducible per-object draws, but does not prescribe a temporal scatter model or preserve identity across retirement/rebirth. Synthetic records need collision-safe IDs allocated by the generic creation operation; a host ID plus snapshot and per-host ordinal is one possible input tuple, with encoding owned by core. Store or stamp the sample definition, halo-mass convention, parameters, seed, profile/velocity prescription, unit conventions, source snapshot, and model version in output metadata. Cap or validate unusually large satellite counts and report halo/sample completeness, but do not silently clip a draw and distort the specified Poisson model.

The baseline HOD is mass-only and snapshot-local. Its main limitations should be stated: central/satellite occupation and profile parameters need calibration; small halos can be incomplete; the assumed profile and velocity distribution affect small-scale clustering; a mass-only model omits assembly bias; and one threshold sample does not guarantee a correct stellar-mass distribution or multi-tracer correlations. Halotools or AbacusHOD can serve as scientific comparison implementations, but agreement should be assessed on a common complete catalog with matching units, random seed treatment, and occupation convention.

### 2.3 SHAM replacement

The existing `sham_global_rank` module is a global snapshot demonstration, not a calibrated SHAM model. It ranks eligible Type 0/1/2 entries with positive `ShamVpeak` by descending proxy, breaking exact ties with `UniqueGalaxyID`, and assigns the analytic cumulative power-law target `n(>M) = n0 (M/M0)^(-alpha)` evaluated at rank density `(r + 0.5)/BoxSize^3`. It has no scientific completeness floor, no scatter, and explicitly disclaims observational realism (the module's README, `models/sham/modules/sham_global_rank/README.md` at the time of this review, lines 3 and 21–25; the implementation plan removes that module). The fixture's three synthetic forests are not a complete cosmological volume (same README, line 47), so its assigned masses do not calibrate a physical relation. Update the peak proxy on every processed snapshot in temporal order, independent of output selection, so intermediate snapshots contribute to `Vpeak`/`Mpeak`. Perform the global rank and assign the target `StellarMass` only on configured output snapshots; in `pre_timestep`, reset `ShamGhost=true` and zero the assigned mass fields on every processed snapshot, while preserving accumulated peak-history fields. Validate the target SMF's redshift range only when assigning an output snapshot: a high-redshift intermediate snapshot may update proxy history without requiring a low-redshift SMF to be extrapolated there.

#### Target stellar-mass function

Replace the power-law target with a named observed cumulative SMF `n_gal(> M_*)` or a documented parameterization. The standard low-redshift parameterization is the double-Schechter function with a single break mass,

```text
Phi(M_*) dM_*  =  exp(-M_*/M_s) [ phi_1 (M_*/M_s)^alpha_1 + phi_2 (M_*/M_s)^alpha_2 ] dM_*/M_s
n_gal(> M_*)   =  Int_{M_*}^{inf} Phi(M') dM'
```

Here `Phi(M_*)` is differential per unit *linear* stellar mass, so `phi_1` and `phi_2` have number-density units. If a source table gives `phi(log10 M_*)` per dex, convert using `d log10 M_* = dM_*/(M_* ln 10)`; omitting this Jacobian changes the normalization and shape interpretation.

A concrete, fully specified instance is the GAMA z < 0.06 fit of Baldry et al. (2012; equation 6; [MNRAS 421, 621](https://doi.org/10.1111/j.1365-2966.2012.20340.x); [arXiv:1111.5707](https://arxiv.org/abs/1111.5707)):

| Quantity | Value | Convention |
|---|---|---|
| `log10 (M_s / M_sun)` | 10.66 | physical `M_sun`, `H_0 = 70 km/s/Mpc` |
| `phi_1` | `3.96e-3 Mpc^-3` | physical `Mpc^-3`, `H_0 = 70` |
| `alpha_1` | −0.35 | |
| `phi_2` | `0.79e-3 Mpc^-3` | physical `Mpc^-3`, `H_0 = 70` |
| `alpha_2` | −1.47 | |
| IMF | Chabrier (2003) | Chabrier masses are about 0.6 times Salpeter |
| Stated validity range | `10^8` to `10^11.5 M_sun` | range over which the paper reports the function is well described |
| Fit-bin range | `10^8` to `10^11.8 M_sun` | binned observations used in the fit |
| Redshift | z < 0.06 | low-redshift sample only |

Any such target must be carried into Mimic with its convention stated and converted once, explicitly. Baldry's masses are physical `M_sun` at `h = 0.7` and densities are physical `Mpc^-3`; Mimic's internal `StellarMass` is `1e10 M_sun/h` and its box volume is `(Mpc/h)^3`. Either convert the candidate rank density `(r + 1/2)/V_box` from `(Mpc/h)^-3` to physical `Mpc^-3` by multiplying by `h^3` and convert the resulting `M_*` from physical `M_sun` to internal units by multiplying by `h / 1e10`, or do the reverse on the table, but never mix. This is a unit conversion between catalog-internal and physical quantities, not a cosmology rescaling of the observations: stellar masses inferred from flux can scale approximately as `h^-2`, and the observed volume depends on the fiducial cosmology. If the simulation cosmology differs from the observational analysis, explicitly transform the SMF under its distance/volume conventions or choose a matched-cosmology target; an internal `h` conversion alone is insufficient. A tabulated target (columns `log10 M_*`, `n(> M_*)`) with the same explicit convention is an equally valid alternative and is preferable when the published function is not Schechter-like. In both cases the source, redshift, IMF and stellar-mass definition, completeness range, units, and normalization must be parameters or explicit model metadata.

The Baldry z < 0.06 target is not valid at every snapshot in Mimic's multi-snapshot runs. Every output snapshot receiving SHAM stellar-mass assignments needs a redshift-indexed SMF (a per-snapshot table or documented evolving parameterization) or an explicit validity window; outside that window the model must fail or mask the assignment rather than silently applying a local-universe target. Higher-redshift snapshots processed only to accumulate proxy history do not require extrapolating the target SMF. Compute candidate number density from the full comoving volume represented by the snapshot population being ranked, not merely the nominal `BoxSize`: the current horizontal callback sees the loaded snapshot generation across its FoF groups, so `BoxSize^3` is the right denominator only when the run contains the complete periodic volume. An arbitrary forest/file subset is not itself a valid spatial subvolume and generally has no known selection function; the scientifically sound default is to require a complete periodic box and fail or label subset output diagnostic-only. A subvolume or weighted estimate is an alternative only when its geometry, selection function, and effective volume are independently validated. A future distributed snapshot path would need a global candidate count/rank across partitions; the current horizontal driver has no MPI-wide rank/reduction path. With zero scatter, candidate rank `r` maps to `n_gal^{-1}((r + 1/2)/V_eff)`. State what happens when the candidate abundance exceeds the target's calibrated range (ranks that would need `M_* < 10^8 M_sun` for the Baldry fit) and fail or explicitly mask rather than extrapolating silently; the current module's fail-rather-than-clip behaviour is the right precedent. Conversions at analysis/output must be defined so comparison to an observational SMF in physical `M_sun` does not introduce a hidden `h` factor.

#### Ranking proxy

Use `Vpeak` as the default ranking proxy for compatibility with the current code and common SHAM practice, but describe precisely how it is formed. The current global module updates peaks from `Vmax`/`Mvir` on Type 0/1 records encountered by the run and lets Type 2 records inherit their stored peaks (README line 21). Thus its `Vpeak` is the maximum over snapshots that were actually processed, not guaranteed full-history peak if a run starts late, omits intermediate snapshots, or uses incomplete history. Require a run that starts at the first relevant snapshot and walks the intended complete sequence for a history-based proxy; provenance should include that range. Alternatively, allow an explicitly supplied precomputed peak proxy when validated. Horizontal catalogs inspected here expose present halo/subhalo quantities such as `M_Crit200`, `Len`, `Vmax`, `VelDisp`, and velocities/positions, but not a universal precomputed `V_peak`, `M_peak`, concentration, `R_vir`, or formation-time field. The module's inherited `ShamVpeak`/`ShamMpeak` properties are accumulated values, not reader-provided catalog fields. `M_peak` can be an optional proxy if its definition, float precision, history, and scientific calibration are checked; do not rank by current host `Mvir` while claiming it is a peak-mass model. A `v_alpha`-style proxy is out of scope until the input or snapshot-history accumulator can provide `Vmax` at the epoch of `Mpeak` and a clustering calibration exists; `Vvir` can be derived from that epoch's mass, redshift, cosmology, and mass definition.

#### Scatter

Keep the initial replacement deterministic with scatter disabled; deterministic ties use an explicitly stable ordering key within a snapshot. This assigns target-SMF quantiles to selected candidate ranks by construction, subject to finite candidate counts, represented volume, and the target table's range; it does not create an exact realization of an observed catalogue. A modest modernization is a scatter-enabled mode whose parameter is intrinsic `sigma_log10(M_* | V_peak)` in dex. Implement scatter by solving or iterating for the intrinsic relation that, after scatter, reproduces the named target SMF, as in Behroozi et al. (2010) and Reddick et al. (2013). Do not simply add random mass noise after a zero-scatter match and continue to describe the target as exact. A proxy-perturbation/rank-scatter mode could preserve the target list exactly but should be a separately named alternative, because its sigma is not intrinsic stellar-mass scatter at fixed proxy.

For reproducibility, derive pseudo-random draws from a configured seed and stable per-snapshot candidate identity, so changing traversal order does not change the result. This guarantees repeatability at fixed snapshot, but not correlated scatter over time. `UniqueGalaxyID` persists along the inherited galaxy object and is a valid stable key for repeatable draws while that object survives; it does not choose the desired temporal correlation model, and retirement/rebirth creates a new key. If correlated scatter across that boundary is required, define explicit progenitor/rebirth semantics rather than assuming the ID alone supplies them. Independent snapshot abundance matching intentionally assigns cross-sectional stellar masses and can produce non-monotonic stellar mass along a branch. That behavior is acceptable for a cross-sectional SHAM mock and should not be sold as a time-integrated galaxy evolution model.

#### Candidate population: resolved-only baseline, orphans optional

Define the candidate population explicitly, because it is part of the model. The recommended baseline is **resolved-only**: current Type 0 centrals plus Type 1 resolved subhalos, each with a valid positive proxy, above an explicit completeness floor. The floor should be stated in the proxy itself (a minimum `V_peak`, or a minimum peak particle count converted through the package's particle mass) and chosen so that the candidate count above the floor is complete for the simulation; any candidate below it is masked, not ranked. Use one model-owned per-record Boolean such as `ShamGhost` for selection, not a redundant Selected-plus-Ghost pair. In `pre_timestep` reset it to true and clear only SHAM-assigned fields on every processed snapshot; preserve `ShamVpeak`/`ShamMpeak` history. Core may demote non-main Type 0/1 progenitors to Type 2 during inheritance before this module phase. In the resolved-only baseline, retire every Type 2 row to Type 3 during this mutable pre-step, while retaining the Type 0/1 scaffold; this excludes newly demoted and carried orphans before marshalling instead of letting an unused orphan population accumulate. After global ranking on an output snapshot, set `ShamGhost=false` only for eligible matched Type 0/1 candidates. Clear stale mass assignments for unselected or masked records, and have consumers filter on `ShamGhost`. Preserve accumulated `ShamVpeak` and `ShamMpeak` histories independently of current selection: a halo excluded at an early snapshot may still need its peak history to become a valid later candidate. This avoids stale assignment fields when an object was selected in an earlier snapshot and is now excluded. The global `post_snapshot` callback still only updates borrowed properties; any Type2 retirement belongs in the existing mutable pre-step. In the optional calibrated orphan-inclusive mode, keep Type2 candidates and their histories, assign the selection flag only where they pass the stated orphan rule, and do not retire them under the resolved-only policy. Type1 resolved satellites remain in both modes. The baseline is auditable, and its inputs are catalog quantities whose completeness can be measured.

The trade-off is a bias/completeness tension that must be stated rather than hidden. Resolved-only matching is incomplete in satellites, most severely near the centres of massive hosts where subhalos are stripped or lost by the halo finder. Because rank matching conserves total abundance, every missing satellite pushes the surviving candidates to higher assigned stellar mass, so the inferred relation is biased as well as the satellite fraction and small-scale clustering being low; Reddick et al. discuss exactly this effect of prematurely disrupted subhalos. Including the Type 2 orphan records that Mimic's core carries forward when a subhalo is lost restores some of that satellite population, but at a cost: the candidate list then depends on the orphan lifetime and merger prescription of the tree/SAM layer, on inherited peak values that are frozen at loss time, and on a position that is no longer measured. Without a calibrated disruption or survival criterion (a `mu_cut`-style threshold, a dynamical-friction lifetime, or a tracked-particle position) the orphan contribution is an uncalibrated model input that silently reshapes the mapping. For that reason the orphan-inclusive mode is presented as an **optional, more complex model** with its own named parameters and its own validation against satellite fractions or clustering, not as the unqualified default. A run that enables it must record the criterion and the resulting orphan fraction in provenance.

The snapshot callback cannot retire Type 2 records or implement an age-based removal by changing `Type`; the resolved-only SHAM cleanup uses the existing mutable `pre_timestep` phase instead. An age-based orphan model would need its own calibrated pre-step policy and should not be inherited accidentally from the legacy module. The legacy module `sham_assign_stellar_mass.c` includes a Type 2 age-based Type 3 retirement and a fixed analytic Moster-style stellar-mass relation with identity-keyed scatter and a baryon-fraction cap (see source lines 82–131, 146–182, and 222–233); those behaviours do not transfer unchanged to a topology-immutable snapshot callback. Its `sham_min_mpeak`/`sham_min_vpeak` proxy floors (line 153) are, however, a precedent for the explicit completeness floor recommended above. Keep the replacement's rank assignment separate from those legacy rules unless a future model explicitly adopts and validates them.

#### Memory and diagnostics

The global rank requires memory proportional to the selected snapshot population. Production-scale rank memory has not been measured; the current fixture is not a scale test. The current module already uses module-owned scratch records and releases them before callback return (README line 9); preserve that ownership pattern and report memory cost, then measure representative full-snapshot populations before claiming production suitability. Do not allocate a volume-wide array across all snapshots or mutate the borrowed population to sort it. An approximate streaming rank is a different algorithm that can alter ties and abundance mapping; use it only if measured snapshots exceed practical memory. Include input completeness, candidate count, masked count, and (if enabled) orphan count in output diagnostics so results at the resolution limit are not interpreted as a complete SMF.

### 2.4 Snapshot SHAM versus history-based galaxy evolution

The SHAM replacement is cross-sectional at its assignment snapshots: it gives a defined stellar-mass sample there, but it is not a time-integrated galaxy-growth model and stellar mass need not increase monotonically along a tree branch. The proxy may be instantaneous or history-based; using a peak proxy does not turn abundance matching into an evolving stellar-mass model. A full empirical evolution model such as UniverseMachine instead predicts star formation from halo histories, integrates it to stellar mass, and fits observables over redshift, so it needs state, time stepping, and calibration data beyond snapshot ranking. Keep that as a separate future model choice rather than silently mixing its assumptions into SHAM.

| Model scope | What is assigned and when | Additional requirement | Recommendation |
|---|---|---|---|
| Instantaneous SHAM | Rank current `M_vir` or `V_max` candidates at requested output snapshots | No accumulated proxy history; validate the weaker treatment of stripped satellites and target range | Simplest stateless alternative, not the preferred proxy |
| Peak-proxy cross-sectional SHAM | Rank `V_peak` (recommended) or validated `M_peak` candidates at requested output snapshots | Accumulate halo proxy history on every processed snapshot, or supply a validated precomputed peak; target SMF must cover assignment redshifts | Recommended replacement; still assigns snapshot samples, not stellar-mass histories |
| Empirical galaxy evolution (UniverseMachine class) | Predict SFR over time and integrate to stellar mass across snapshots | Time-resolved halo properties, additional latent state/parameters, and multi-redshift calibration | Distinct later model, outside the first SHAM replacement |

### 2.5 Fit with the documented roadmap

The development pathway selects correct HOD and SHAM models as the next focus, says HOD may be FoF-local or snapshot-wide, and records distributed snapshots, performance, chunked streaming, the emulator, the model builder, coupled-rate processing, and the optional embedded engine as later work. This recommendation uses existing horizontal lifecycle phases: per-FoF HOD construction and full-snapshot SHAM ranking. It does not require another processing mode or a separate output framework.

### 2.6 Shared design, validation, and boundaries

HOD and SHAM should remain distinct packages because one samples an occupation distribution and phase space while the other ranks existing halo/subhalo candidates. They may share a physics-neutral deterministic random-number utility, a unit/`h` conversion helper, or a validated SMF table reader only if it is genuinely useful to several modules and lives at a neutral layer (`src/util/` or a model-neutral shared header), never in one model's `shared/` directory imported by another. Current `src/util/` does not provide a shared RNG or SMF-table service, so initially keep any necessary implementation private to the model package; promote a helper only when a second genuine consumer appears. Avoid HOD calling SHAM helpers or creating an abstraction simply because both need random numbers. Keep HOD and SHAM parameters, scientific defaults, output provenance, and calibration logic package-local. Physics equations and prescriptions belong in the model packages; the core extension discussed for HOD should know only generic record construction, property defaults, identity, memory ownership, host-segment bookkeeping, and output.

For SHAM, meaningful evidence includes rank-to-mass reference calculations, tie behavior, determinism under traversal changes, target-SMF recovery with zero scatter, target-SMF recovery after intrinsic scatter, behavior at mass-function limits, incomplete histories, empty snapshots, invalid candidate proxies, completeness-floor masking, and memory scaling. Compare selected outputs with the existing stellar-mass-function observation overlays (including Baldry et al. 2008 already used by the SHAM plotting figure) or state why a different, redshift-matched calibration target is preferred; the GAMA z < 0.06 Baldry et al. 2012 table here is a precise low-redshift example, not a universal target. For HOD, verify the central Bernoulli frequency and conditional satellite Poisson law over many seeded hosts; check the imposed central-gating convention; check selected counts against the calibrated expected occupation while allowing Bernoulli/Poisson realization scatter; confirm host selection avoids treating subhalos as independent hosts; validate profile/velocity units and periodic boundaries; verify every new satellite is linked to its host segment, any inherited copy retains a Type 0/1 anchor, and every carried Type 2 is retired before that workspace is marshalled; confirm scaffold resets and HOD selection are independent of output cadence; measure occupation and clustering against a trusted implementation on the same complete halo catalog. A fixture can verify mechanisms but cannot establish a calibrated model or cosmological parity. Later science validation should compare SMFs or threshold abundances and clustering/group statistics against the exact observational calibration dataset and clearly state its redshift, cosmology, selection, uncertainties, and covariance.

### 2.7 Optional features judged by complexity cost

The table sorts the optional features discussed above by what each costs in code, data, and calibration. "Cheap now" means it needs only existing catalog fields and no new calibration data; "needs calibration/data" means the physics is simple but the inputs or the fit are not yet available in Mimic; "later extension" means it needs new core capability or a validation path that does not exist.

| Feature | Model | Cost class | Why |
|---|---|---|---|
| Named double-Schechter or tabulated SMF target | SHAM | Cheap now | One parameter block plus one `h` conversion; removes the demonstrator power law |
| Explicit completeness floor and masking | SHAM | Cheap now | Uses `Len`/particle mass or a `V_peak` threshold already in hand |
| Resolved-only candidate population and Type 2 cleanup | SHAM | Cheap now | Keep Type 0/1; retire Type 2 in the mutable `pre_timestep` phase before output marshalling |
| Deterministic, traversal-independent seeding | both | Cheap now | Required by the vision document anyway |
| External calibration of five HOD parameters against a complete host HMF | HOD | Calibration work | Keeps the per-FoF module simple; an in-run global solve would require an extra preparation pass |
| Intrinsic scatter with rematching | SHAM | Needs calibration | Requires a numerically stable intrinsic-relation solver, range/boundary handling, convergence checks, and a fitted scatter value (0.17–0.20 dex in the cited work); modestly more code than deterministic ranking |
| Orphan-inclusive candidates with disruption criterion | SHAM | Needs calibration | Requires a `mu_cut`-style or lifetime parameter and satellite-fraction or clustering data to set it |
| NFW satellite placement with a concentration–mass relation | HOD | Needs calibration | Simple code; the relation is an external assumption that must match the mass definition |
| Continuous stellar masses via CSMF | HOD | Needs calibration | Many more parameters and a multi-threshold fit |
| `v_alpha` or other secondary-property proxy | SHAM | Later extension | Needs `Vmax` tracked at the epoch of `Mpeak` plus a clustering calibration path; `Vvir` can be derived from matched mass, epoch, cosmology, and mass definition |
| Decorated HOD / assembly bias | HOD | Later extension | Needs a secondary halo property the inputs do not carry and clustering data |
| Generic record creation/append with host-segment marshalling and collision-safe identity | core | Required HOD support | Enables proper HOD rows while reusing the standard output/inheritance path; needs focused architecture review before implementation |
| Branch-correlated scatter | both | Later extension | Uses persistent `UniqueGalaxyID` while inherited; correlation/rebirth semantics still need a model |
| Cross-snapshot synthetic satellite tracks | HOD | Later extension | Separate feature with explicit matching and ID semantics |

## Decisions that remain open

1. Which HOD sample is the first target: a luminosity threshold, stellar-mass threshold, or a continuous conditional stellar-mass function? Which survey, redshift, IMF, and selection define it?
2. The one unavoidable HOD architecture question is how a generic creation operation safely adds records to each source halo's contiguous marshal segment without invalidating workspace references. The operation should own generated defaults, collision-safe IDs, host linkage, and segment bookkeeping; a separate catalogue/writer is not required by the scientific model.
3. Which host mass definition and conversion are supported for the first HOD calibration? Which horizontal package is complete enough for that use, and is the inspected package's `M_Crit200` field, which carries Consistent-Trees `Mvir`, really a 200c mass as its description states?
4. Should the first HOD use a concentration relation for NFW satellite placement or use resolved subhalo phase space as an explicitly hybrid option? What velocity bias, if any, is supported by the calibration?
5. For SHAM, which named observed SMF, redshift, stellar-mass convention, and calibrated completeness range should replace the demonstration power law? Baldry et al. (2012) is the concrete candidate given here; is its z < 0.06, Chabrier, `h = 0.7` convention acceptable for the simulations Mimic targets?
6. What completeness floor (in `V_peak` or peak particle count) is appropriate for each simulation package, and how is it validated?
7. Is the orphan-inclusive SHAM mode wanted at all in the first release, and if so, which disruption or survival criterion and which satellite-fraction or clustering data will calibrate it? A snapshot module cannot apply the legacy Type 2 retirement behavior itself.
8. Is snapshot-repeatable random scatter sufficient, or is branch-correlated scatter required? `UniqueGalaxyID` is persistent along inherited objects, but the desired scatter correlation across retirement/rebirth and input history gaps still needs a defined model.
9. Which halo completeness and volume policy should cause hard failure, warning, or masking when the simulation cannot support the target sample or its high-mass tail?
