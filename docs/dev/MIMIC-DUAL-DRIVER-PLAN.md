## Purpose

This document defines the architecture and migration path for letting Mimic process merger data through two input orderings: tree-ordered and snapshot-ordered. The existing tree-ordered behaviour remains the first driver. The snapshot-ordered driver is added as a second front end over shared inheritance, physics execution, output, metadata, and validation services.

The purpose is not to rewrite Mimic or introduce new physics. The purpose is to separate driver-specific ordering and buffering from the shared physics-agnostic core so Mimic can support per-history physics and snapshot-synchronous methods without duplicating scientific behaviour.

---

## Motivation

The single structural fact that gates Mimic's method coverage is that the core processes one FoF workspace at a time in depth-first tree order, with per-forest bounded memory. That ordering is ideal for per-history physics, but it structurally cannot express operations that need a whole snapshot's halo population co-resident: global abundance matching (true SHAM), HOD-style statistical population, a synchronous reionization radiation field, environment-dependent physics, and on-the-fly lightcone assembly. These methods are the established reason snapshot-synchronised codes exist (L-Galaxies, UniverseMachine, and EMERGE are all snapshot-ordered).

There is also a hard capacity motivation: **Shin-Uchuu cannot be processed tree-ordered at all.** Its Consistent-Trees output contains a percolation super-forest (forest `26551468179`) holding 33% of all tree roots — billions of halos that no per-forest memory model can load as a unit, and that also rules out the uchuutools forests-HDF5 packaging. Snapshot ordering, whose working set is one snapshot's population, is the only way Mimic runs this simulation. See `SHIN-UCHUU-CONVERSION-PLAN.md`.

Rather than bolt a global stage onto the tree driver, the input ordering, the driver, and the memory model become a single coherent choice: a tree-ordered file feeds the tree driver with per-forest memory; a snapshot-ordered file feeds the snapshot driver with per-snapshot memory, making a snapshot's population co-resident and global operations natural. Producing the snapshot ordering is the job of an external converter, not Mimic.

## Architectural Decisions

### Driver Selection

Mimic reads exactly one input ordering per run, declared in the input YAML:

```yaml
input:
  processing_order: tree_ordered      # or: snapshot_ordered
```

Startup validation must fail fast if the declared ordering, reader, and selected driver do not match. There is no internal auto-detection and no internal conversion. `input.tree_type` stays the reader-format selector; `input.processing_order` stays the driver selector.

### Adjacency Invariant (replaces the former phantom-insertion contract)

Snapshot-ordered input has **strictly adjacent links as a validated format invariant**: every non-null descendant link points exactly one snapshot forward, and therefore every progenitor of a snap-N halo lives at snap N−1. Nobody inserts phantom or bridge halos:

- Consistent-Trees already writes interpolated phantom halos into its tree data, so all ctrees-derived input (Shin-Uchuu, micro-Uchuu) is adjacent by construction. The tree driver already processes these phantoms today as ordinary halos with no special treatment — the snapshot driver inherits the same property for free.
- The converter asserts adjacency and aborts on violation; for ctrees input a violation means corrupt data, not a policy choice. The snapshot reader re-validates cheaply at load.
- Gap-ful sources (L-Halo trees skip snapshots) are simply never converted. The identity fixture is `micro-uchuu-ascii` (local, already a registered package), where identity can be exact because phantoms are native. If a gap-ful source ever genuinely needs snapshot conversion, phantom synthesis becomes that converter front-end's problem, with documented interpolation science and no identity claim against the tree driver.

Consequence for Mimic: the snapshot driver keeps exactly **two generations** of processed state (previous and current snapshot). No lookback window, no per-halo gap handling, and memory bounds that scale with one snapshot regardless of simulation size.

### Shared Engine

Both drivers call the same shared services:

- **Inheritance and tracking service** (`src/core/inheritance.c`): turns already-processed progenitor galaxies plus descendant halo properties into the inherited FoF workspace. It owns type transitions, orphan handling, infall capture, merger-clock handling, accumulator reset, and local central selection.
- **Physics execution engine** (`execute_module_pipeline` in `src/core/module_registry.c`): format-neutral module execution over `(ctx, halos, ngal)` using the current configured module lifecycle.
- **Output-buffer marshalling** (`marshal_workspace_to_output_buffer` in `src/core/output_buffer.c`): driver-neutral workspace → output-buffer transfer.
- **Core services:** configuration, units, cosmology/time tables, memory, logging, module registry, generated property metadata, HDF5 writers, and output provenance.

### Driver Responsibilities

| Responsibility | Tree driver | Snapshot driver |
|---|---|---|
| Input ordering | Forests stored contiguously across snapshots | Halos grouped by snapshot with adjacent-snapshot links |
| Traversal | Depth-first per forest | Increasing-time snapshot loop |
| Progenitor lookup | Tree links within the current forest | `FirstProgenitor`/`NextProgenitor` links into the previous snapshot slab |
| Working set | One forest | Current input slab + two generations of processed state |
| Output buffering | Per forest/tree-compatible buffer | Per snapshot buffer, written per snapshot |
| Output formats | Binary and HDF5 | HDF5 only (see Output Contract) |
| Galaxy memory | Per-unit pool, bulk reset per forest | Two pools, ping-pong bulk reset per snapshot |
| Natural methods | Per-history physics | Global ranking, HOD, environment, radiation-field, and lightcone workflows |

### Module ABI Stability

The physics-module ABI is frozen for this work. Do not change `process(struct ModuleContext *ctx, struct Halo *halos, int ngal)`, the `Module` registration contract, or the YAML-to-C property and metadata generation contracts.

### Reader Interface

The snapshot reader gets its own small `struct SnapshotReader` vtable and registry, not a widening of `struct TreeReader`. The tree vtable is deeply partition/unit-shaped (**12** function-pointer hooks: partition enumeration, per-file paths, unit counts and costs, unit loading, plus four data fields); the snapshot shape is open-run → enumerate snapshots → load slab → close. Two disjoint hook sets in one struct would defeat the `REQUIRE_READER_HOOK` fail-fast checks.

`input.tree_type` still selects the reader (e.g. `snapshot_hdf5`), from a single resolution site. **As implemented in Phase 4b, resolution is registry-first, not order-driven:** `tree_reader_lookup()` is tried first and `snapshot_reader_lookup()` second, on **disjoint** name sets, so the order fixes only which registry answers first and never which reader a name resolves to. The configured `processing_order` is not consulted during lookup; instead the resolved reader declares the one driver it feeds, and validation rejects a mismatch in either direction. Exactly one of `MimicConfig.reader` / `MimicConfig.snapshot_reader` is non-`NULL` afterwards, and `TreeExtension` is set only for tree readers — so `MimicConfig.reader` is legitimately `NULL` for a snapshot configuration.

### Determinism and Galaxy Identity

Cross-format identity depends on deterministic per-FoF physics. Future stochastic modules must seed from stable per-halo or per-FoF keys, never from a global RNG stream consumed in traversal order.

Identity is also an encoding contract. `UniqueGalaxyID = halonr + multiplier × (forestnr_global + 1)`, and the compile-time `TREE_MUL_FAC = 10⁹` **cannot represent the Shin-Uchuu super-forest**, whose within-forest halo ranks plausibly reach 5–9 billion. Decision D9: the multiplier becomes per-simulation metadata (`simulation.unique_galaxy_id_multiplier`, legal in `simulation_info.yaml` and the run file, default `TREE_MUL_FAC`). Shin-Uchuu sets 10¹⁰, confirmed against the measured super-forest halo count from the conversion report.

That was false: every helper in `src/include/galaxy_id.h` — `mimic_unique_galaxy_id_max_forests`, `mimic_unique_galaxy_id_total_forests_valid`, `mimic_unique_galaxy_id_components_valid`, and `mimic_encode_unique_galaxy_id` — uses the compile-time `TREE_MUL_FAC` directly and takes no configured multiplier. What Phase 4b actually landed is a **header-bounds validator specific to the snapshot input**: `snapshot_identity_bounds_valid(info, multiplier)` (`src/io/snapshot/reader.h`, implemented in `src/io/snapshot/interface.c`), called from the reader's `open_run` before run metadata is published. The snapshot input carries a dense run-scoped `ForestIndex` and `HaloRankInForest` per halo — the index enumeration replicates the ASCII reader's forest ordering and ranks are in the reference tree-driver order — so both drivers compute identical IDs from identical components with no runtime id mapping.

### Output Contract

Both drivers emit the same generated output **field layout** and provenance model. (Not the same schema *file*: `source_md5` hashes the selected package's YAML paths and contents, and the two micro-Uchuu packages differ in prose descriptions, so their `output_schema.json` files differ in those fields while the field layout is identical.) Snapshot-ordered runs are **HDF5-only** and fail fast on `output_format: binary`: the binary writer's per-tree count header assumes per-tree contiguity, which snapshot-major emission over id-sorted slabs cannot honour (and a Shin-Uchuu header would carry 166M entries per file). The tree driver keeps both output formats unchanged, save for the four enumerated deltas in the Definition of Done; its binary galaxy records stay byte-identical. Snapshot runs use a single output partition and are not `--skip`-resumable in v1. **Specified 2026-08-04 rather than left as a limitation:** a snapshot-ordered configuration **rejects `--skip` during configuration validation** with a message saying resume is not supported for snapshot-ordered runs, rather than accepting the flag and silently ignoring it. Incomplete-output cleanup is currently tree-driver-specific (`src/core/tree_driver.c:41`, `:58`), so the snapshot driver needs its own equivalent: a snapshot run's output is all-or-nothing and a failed run must not leave a partial file that a later run would mistake for complete.

**Superseded by D5(a), 2026-08-13.** The two claims above — "a single output partition" and "output is all-or-nothing" — describe the design this section specified before D5(a). What shipped instead: a snapshot-ordered run writes one HDF5 partition file per requested output snapshot (named by that snapshot's number) plus the master, and cleanup is per-partition rather than all-or-nothing — a partition file that has closed successfully survives a later failure; only the in-flight partition and the (never-written) master are removed. `--skip` is still rejected; that part of this paragraph is unaffected. See `docs/DEVELOPER-GUIDE.md` → "The Snapshot Driver" and `docs/dev/SNAPSHOT-OUTPUT-PARTITIONING-PLAN.md` for the delivered design.

### Cross-Format Identity Gate

Byte-identical output files across drivers are impossible: the tree driver emits records in depth-first completion order, the snapshot driver snapshot-major. The gate is defined as: **for every output snapshot, the two runs produce the same set of `UniqueGalaxyID`s, and for each ID every output field is identical** (bitwise target; any relaxation must be an explicitly reviewed tolerance). Fixture: `micro-uchuu-ascii` read tree-ordered versus the same ASCII converted to snapshot-HDF5 and read snapshot-ordered. The test lives in the scientific tier.

Identity preconditions carried explicitly by the snapshot format (converter-owned, never reconstructed heuristically):

1. **Progenitor chain order** — `FirstProgenitor`/`NextProgenitor` links replicate the reference chain order, because `find_most_massive_progenitor` tie-breaks by chain position (SAGE parity) and gather order fixes workspace layout and merger processing order.
2. **FoF chain order** — `FirstHaloInFOFgroup`/`NextHaloInFOFgroup` replicate the reference sort, fixing subhalo slice order and central selection.
3. **Identity components** — dense `ForestIndex` + reference-ordered `HaloRankInForest` reproduce `UniqueGalaxyID` exactly.

These are the format-carried preconditions; the driver-side behaviours the snapshot driver must replicate (CentralMvir stamping, new-object sentinels, timestep derivation, central-ID propagation, marshal-time snapshot stamping) are enumerated in the Phase 5 driver parity checklist.

Resolution: **processed-generation counts, capacities, and auxiliary output ranges become `int64_t`**, and `OutputBuffer` generalises with them; `int` is retained **only** for FoF-local workspace counts, which are bounded by one FoF group, and every narrowing to `int` is explicit and checked. Note a slab itself fits in `int` today — the format caps `n_halos` at `INT32_MAX` and the peak Shin-Uchuu slab is ~315M — so this is about the *accumulated* output side, not the slab, and about not silently inheriting a 32-bit ceiling into the snapshot path.
   **Non-HDF5 build contract.** `Makefile:112` compiles every ordinary source for every package while `Makefile:272` filters out every `*hdf5.c` under `USE-HDF5=no`, so a plainly-named `snapshot_driver.c` is still compiled in a non-HDF5 build and would fail to link against the HDF5 writers. `run_snapshot_driver()` must therefore be **always buildable**: its HDF5-dependent calls compile only under `#ifdef HDF5`, with a fail-fast stub otherwise, and `make USE-HDF5=no` must stay green. This is the same trap Phase 4b hit with the reader registry, where the fix was filename discipline; here the fix is compilation guards, because `run_processing_driver()` is called unconditionally and the driver's translation unit must therefore compile and link in a non-HDF5 build. Note the guard is a **build** requirement, not a runtime path: a non-HDF5 build registers no snapshot reader (`src/io/snapshot/registry.c` compiles an empty table), so configuration rejects `tree_type: snapshot_hdf5` as unknown long before any driver runs. The stub therefore exists to keep the build green and can never normally emit its own message.
   **Phase 5 is serial-only, and must say so at startup.** Every MPI rank reaches `run_processing_driver()` (`src/core/main.c:413`) before the barrier that follows it, while the Output Contract above gives snapshot runs a *single* output partition — so a direct implementation would have every rank open and write the same file. Snapshot-ordered configurations therefore **reject `NTask > 1` at startup** with a message pointing at the distributed plan. Multi-rank snapshot execution, domain decomposition, and partitioned snapshot output belong to `MIMIC-DISTRIBUTED-SNAPSHOT-PLAN.md` and are explicitly out of Phase 5.

2. **State rotation.** Corrected 2026-08-04 — an earlier revision said the raw slab for N−1 could be dropped once N completes, which is wrong: slab N is the *progenitor* slab while N+1 is processed, because `FirstProgenitor` resolves into it and `NextProgenitor`/`Len` are read from it (`src/core/build_model.c:183-202`, `:355-370`). **Two raw slabs are live during processing.** The rotation is: retain raw slab N−1 and its processed/aux generation; load raw slab N and build current processed state; once every FoF at N has deep-copied all surviving progenitor galaxies, release processed generation N−1 *and* raw slab N−1; prepare and write snapshot-N output using raw slab N; carry raw slab N plus processed generation N into N+1; release the final slab only after final-snapshot output. Requires the instanced galaxy-pool handle API (see file inventory and item 7 below).
3. **Identity:** `UniqueGalaxyID` computed directly from (`HaloRankInForest`, `ForestIndex`) with the per-simulation multiplier. **Multiplier plumbing is split across the two phases:** *parsing* (`simulation_info.yaml` and run file → `MimicConfig.UniqueGalaxyIDMultiplier`, with explicit default seeding and precedence) and *header-bounds validation* (`snapshot_identity_bounds_valid()` from the reader's `open_run`) landed in Phase 4b. What remains here is the **encoding change** — making the `src/include/galaxy_id.h` helpers take the configured value instead of the compile-time `TREE_MUL_FAC` — plus recording the multiplier in output provenance, and then lifting Phase 4b's rejection of a non-default multiplier for tree-ordered runs. **The provenance attribute is frozen here, not left to the planner:** an `int64` attribute named `UniqueGalaxyIDMultiplier` on the `/RunProperties` group, written to **both** the master file and every per-file HDF5 output, since per-file metadata is written through its own path (`src/io/output/metadata_hdf5.c:423-456`) and the master's configuration table through another (`:487-525`) — a value recorded in only one of them leaves the other set of files unable to interpret their own IDs.
   **Migration scope is wider than `galaxy_id.h`** (found 2026-08-04): the tree readers guard forest halo counts against the compile-time constant directly at `src/io/tree/read_ctrees_ascii.c:684`, `src/io/tree/read_ctrees_hdf5.c:387`, and `:770`. Lifting the configuration rejection while those stay hard-coded would leave a tree-ordered run declaring 10¹⁰ still rejecting forests of 10⁹ halos, i.e. a configured value that is accepted and then silently ineffective. All three sites migrate to the configured multiplier or to the common helper below. `src/core/build_model.c:278` names the constant only in a diagnostic and must print the configured value instead.
   **One bound expression, not two.** `galaxy_id.h:15-17` computes `(LLONG_MAX - (M-1))/M` while `snapshot_identity_bounds_valid()` uses `INT64_MAX/M - 1`. Writing `INT64_MAX = qM + r`, the first is `q - 1 + ⌊(r+1)/M⌋` and the second is `q - 1`, so they differ exactly when `M` divides 2⁶³ — multiplier 1, 2, and other powers of two — where the snapshot form is one *stricter*. They agree at 10⁹ and 10¹⁰, so **no off-by-one exists today**. Phase 5 unifies them onto the snapshot form, because that is the frozen format's stated startup contract (`docs/dev/SNAPSHOT-HDF5-FORMAT.md:126-130`) and being marginally conservative is the safe direction. Component validation derives from the same helper: rank in `[0, multiplier)` and forest index below the same bound. **`HaloNr` contract:** `struct Halo.HaloNr` stays an `int` local index — for the snapshot driver, the halo's slab index — because virial accessors and output helpers index the input array through it. `HaloRankInForest` (int64, up to ~10¹⁰) feeds *only* the `UniqueGalaxyID` encoding and must never be stored in `HaloNr`.

8. **Physical header agreement with configuration** (Phase 4b deferred this deliberately; decided 2026-08-04). The reader validates `scale_factor` against the a_list but compares no other physical attribute against the configured simulation, so a dataset paired with the wrong package silently produces different virial masses through `MimicConfig.PartMass` and different `Rvir`/`Vvir` through the cosmology. Phase 5 compares `particle_mass_msun_h`, the three cosmology values, and `box_size_mpc_h` in the reader's `open_run`, **for every snapshot file, not only snapshot 0**, and **aborts** on mismatch. A warning is not sufficient: the failure is scientific, not operational, and a deliberate mismatch should require an explicit future override rather than being reachable by ignoring a log line.
   **Comparison is by rounding tolerance, not exact equality.** Exact is defensible for today's fixture, because the converter stamps float64 values read from the same YAML, but not as the general runtime rule: Mimic applies unit conversions to `BoxSize` and `PartMass` before storing them (`src/core/read_parameter_file.c:591-611`, `:964-974`), so equivalent metadata expressed in another accepted unit accumulates rounding. Use `fabs(header - configured) <= 16 * DBL_EPSILON * fmax(fabs(header), fabs(configured))`, require exact equality when both are zero, and reject non-finite values. This is a *rounding* tolerance asserting two values are the same number — it is not a scientific tolerance and does not carry that evidence burden. For particle mass, compare the header against `MimicConfig.PartMass * 1e10`, matching the producer's own operation (`scripts/convert/hdf5_writer.py:127`); do not divide the header and assume the inverse rounds identically. **The unit difference is the trap here:** the header stores native Msun/h while `PartMass` is in 1e10 Msun/h, so a naive comparison fails by exactly 10¹⁰.

**Frozen gate configuration (specified 2026-08-04; the prose above was not executable unattended).** An unattended run cannot choose these, and every one of them changes which fields are compared.

- **Two tiers, in this order.** First `MODEL=halos-only`, which isolates the driver, inheritance, identity encoding, and output marshalling from all physics — a divergence here is a driver bug, and this is the *early* comparison the sequencing advice below asks for. Then `MODEL=sage16`, the real gate, which exercises the full module pipeline, mergers, substeps, and the complete output schema. A `halos-only` pass alone is **not** the gate; a `sage16` pass alone forfeits the cheap bisection.
- **Run files.** The tree side uses the committed `models/<model>/input/<model>_micro-uchuu-ascii.yaml`. The snapshot side needs a new `<model>_micro-uchuu-snapshot.yaml` that is **identical except for `simulation.name` and `output.output_directory`** — the plan must require a mechanical diff of the pair showing exactly those two lines, so the module pipeline, ordering, `SubSteps`, and every physics parameter are provably the same.
- **Output snapshots.** Keep the committed list `[49, 28, 23, 16, 12, 10, 8, 7]` verbatim. Eight outputs from z = 0 upward exercise the two-generation rotation repeatedly rather than only at the endpoint.
- **Output format.** HDF5 both sides, per the output contract above (snapshot runs are HDF5-only). Note this makes file-level byte comparison meaningless — provenance differs by construction — which is why the comparison is per-ID and per-field.
- **Comparison algorithm, which must be specified because the obvious implementation is wrong.** For each output snapshot: read both runs' galaxy records; **assert no duplicate `UniqueGalaxyID` within either run** before anything else, since a dictionary keyed by ID would otherwise silently overwrite and mask a real defect; assert the two ID *sets* are equal, reporting the symmetric difference with counts; then for each shared ID compare every field's **raw bytes**, so NaN payloads and signed zero are handled as bit patterns. `numpy.allclose`, `==`, or any numeric comparison does **not** implement the stated gate. Any tolerance is an explicitly reviewed exception with recorded justification, not a default.
- **Aggregate every output partition before comparing.** `simulations/micro-uchuu-ascii/simulation_info.yaml:18` sets `forests_per_file: 100000` against 440,651 forests, so the tree side writes **five** numbered output files and the master enumerates them (`src/io/output/master_hdf5.c:76`). A comparator that opens one file would silently compare a fifth of the run and pass. Concatenate across every numbered partition on each side *before* the duplicate-ID assertion. `scripts/convert/crosscheck.py` already demonstrates the pattern.
- **Preflight: assert the two packages agree, not just the two run files.** The mechanical run-file diff protects the run files only; `simulation_info.yaml` and the a_list are package files and are not covered. `Age[]`/`ZZ[]` derive from the a_list and drive `dT`, `time_interval`, and every substep count (`src/core/build_model.c:417`, `:455`), so a one-line a_list divergence would move physics while every other check stayed green. Before comparing output, assert **exact** equality between the two builds of: the a_list contents, the derived `AA`/`ZZ` tables, particle mass, the three cosmology values, box size, the identity multiplier, and the generated output field layout. This is a gate-specific equality assertion and is deliberately stricter than item 8's tolerant general-purpose header check, which exists for arbitrary user pairings rather than for a controlled experiment.
- **Harness shape.** `make tests-scientific` builds one `MODEL`/`SIMULATION` pair at a time (`Makefile:810`, `:826`), while the gate needs two models × two simulations × two timestep schemes = eight runs. The plan must prescribe one harness that performs isolated per-pair builds, runs all eight, aggregates partitions, and constructs the fixed and dynamic run-file pairs explicitly — not a test that assumes a single ambient build.
- The test lives in the scientific tier and must fail loudly rather than skip when either dataset is absent.

**Sequencing advice for whoever slices this phase (from the Phase 4b run).** Phase 4b stayed clean partly because it was reader-only and structurally *could not* change a scientific result — the driver aborted before any physics ran. Phase 5 has no such protection: it touches physics coupling (`virial.c`), output marshalling, and identity encoding at once, and every one of those can move galaxy numbers. So do **not** leave the cross-format identity comparison as a final acceptance step. Get an end-to-end snapshot run producing output, and a first identity comparison against the tree driver, as early in the slice order as the code allows — even a partial or single-snapshot comparison — so that later slices are measured against a known-good identity baseline rather than discovering a divergence at the end with several interacting changes to bisect. Wire `snapshot_reader_open_run()` in early too: it is fully implemented and unit-tested but has no run-path caller, so nothing exercises it until the driver does.

**Practical note on building a comparison baseline (recorded 2026-08-04 from the Phase 4b run; resolved 2026-08-10).** The identity gate compares output produced by two different builds, and Phase 4b's byte-identical tree-path check had the same shape. The trap this note originally recorded — the Makefile's literal `.git/HEAD` prerequisite for `build/generated/git_version.h` breaking every `git worktree` build — **is fixed**: the prerequisite now resolves the real git directory via `git rev-parse --git-dir`, so worktree builds work and exported tarballs degrade to `unknown` version fields. `git worktree add <commit>` is therefore a legitimate way to stand up the second build; mini-millennium needs no data symlinks because its input is the committed `tests/data/input/trees_063.0`. Capturing the "before" side from the unmodified tree before starting the work remains the simplest option.

## Definition of Done

- `input.processing_order` selects a validated driver and fails fast on mismatches (done in v1.0).
- The tree driver remains byte-identical to the tagged v1.0 baseline throughout, where "byte-identical" means **bitwise equality of the galaxy output records**. Phase 5 deliberately adds the `UniqueGalaxyID` multiplier to HDF5 provenance (item 3), so whole-*file* identity is impossible by construction; **exactly four** deterministic HDF5 metadata/schema deltas are permitted, and any other metadata change is a failure:
  1. the new `UniqueGalaxyIDMultiplier` provenance attribute (item 3);
  2. the `TotHalosPerSnap` dtype widening from `int` to `int64`, which item 5's output-schema decision requires and which necessarily touches the tree path too — the per-file writer creates and writes it with `H5T_NATIVE_INT` (`src/io/output/hdf5.c:210-212`) and the master reads and republishes it the same way (`src/io/output/master_hdf5.c:128-142`);
  3. the `UniqueGalaxyID` **field description**. `src/core/core_properties.yaml:79` now reads `creation_halonr + 10^9 * (forestnr_global + 1)`, and the generator copies property descriptions into both the HDF5 `FieldMetadata` table and the run-local output schema, so that text is user-visible metadata. A configurable multiplier makes the hard-coded `10^9` false for any non-default value, so the description must change to name the configured multiplier. **Scope note:** that description previously carried a *second*, unrelated fault — it omitted the `+ 1` forest offset the encoder applies (`src/include/galaxy_id.h:31`), the identical defect corrected in the Developer Guide during Phase 4b. That half was **fixed in pre-Phase-5 work on 2026-08-10** (commit `77ab8462`, which also corrected three committed baseline schema sidecars, both tracked HDF5 baselines' embedded `FieldMetadata`, and two test docstrings), so Phase 5 finds the `+ 1` already correct and changes only the multiplier half.
  4. the `hdf5_format_version` attribute incrementing from `1.1` to `1.2`. `src/io/output/metadata_hdf5.c:110-115` states the rule outright — "Increment `hdf5_format_version` when the output schema changes" — and delta 2 is exactly such a change, so failing to bump it would leave two mutually incompatible files both claiming `1.1`. The bump is written to both per-file and master metadata.
  All four deltas are deliberate and deterministic, and all four must be **exercised** by the preservation check rather than excused by it. Any *other* HDF5 metadata change is a failure.
  **The run-local `metadata/output_schema.json` is a separate artefact with its own two expected changes, and the preservation rule must not treat them as violations.** `compute_yaml_hash()` (`scripts/generate_properties.py:617-636`) hashes the generator's own source *and* every property-generation YAML, and emits the result as `source_md5` in the run-local schema (`:1517-1533`). Phase 5 necessarily edits all three of those inputs — the generator (accessor and `calculate` emission), `core_properties.yaml` (the `UniqueGalaxyID` description), and `halo_properties.yaml` (the identity-field removal) — so `source_md5` **must** change. The run-local schema therefore changes in exactly two fields: the `UniqueGalaxyID` description and `source_md5`. Both are mechanically derived, both are expected, and a check that flags either as an unexplained delta is miscalibrated.
  **The binary galaxy records themselves stay byte-identical throughout**, which is what the tree-path preservation gate actually compares; descriptions and hashes live in the sidecar schema, not in the record stream. Binary output carries no provenance and therefore remains byte-identical as a whole file — which is why the binary vehicle is the preservation check, as in Phase 4b.
- The snapshot-HDF5 format contract is frozen as a durable spec, and the converter passes its validation battery and micro-Uchuu topology cross-check.
- The snapshot driver runs end to end, and the cross-format identity test (same `UniqueGalaxyID` set per snapshot, every field identical per ID) passes on micro-Uchuu and is part of `micro-uchuu-snapshot`'s **package-local** scientific tier — a manual, dataset-present operation, not something any automated tier or CI runs.
- The shared inheritance service, physics engine, and output buffer are consumed by both drivers with **no behavioural difference**. Three mechanical API changes are expected and are not exceptions to this: inheritance gains an explicit `struct GalaxyPool *` (item 7); the accessor/virial family plus `prepare_halo_for_output` gain the explicit input view (recorded input 1); and `OutputBuffer`'s counts, capacities and segment ranges widen to `int64_t` (item 1's integer-width contract). All three must be proven neutral by the tree-path preservation check.
- Shin-Uchuu converts, builds a clean `simulations/shin-uchuu/` package, and runs sage16 end to end with sane HMF/GSMF at z = 0, 1, 2.
- Snapshot-global physics contracts remain explicitly scoped as follow-on work (`MIMIC-SNAPSHOT-GLOBAL-MODULES-PLAN.md`).

## Risks And Mitigations

| Risk | Mitigation |
|---|---|
| Inheritance semantics drift | Already extracted and byte-identity-proven under the tree driver; identity gate re-checks end to end |
| Identity encoding overflow (super-forest) | Per-simulation multiplier (D9) set from measured counts in the conversion report. Phase 4b parses it and bounds-checks it against the dataset headers at `open_run`. **Closed 2026-08-12:** Phase 5 replaced the encoder — every `galaxy_id.h` helper takes the configured multiplier as an `int64_t` parameter, both drivers honour a non-default value, the former tree-ordered rejection is lifted, and the value is recorded in output provenance as the int64 `RunProperties/UniqueGalaxyIDMultiplier` attribute on both the per-file and master paths |
| Chain/order reconstruction diverges | Orders are converter-owned explicit links, validated round-trip; micro-Uchuu cross-check catches divergence before any Mimic code exists |
| Snapshot memory footprint at z=0 | Two-generation bound; measure struct sizes in Phase 5 design; mitigation options identified (P9 in the archived review) |
| Invalid snapshot inputs | Adjacency and link-range validation at conversion and again at read; abort, never repair |
| Persistent cross-snapshot state bugs | Cross-format identity is the direct acceptance check |
| Stochastic physics breaking determinism | Stable per-halo/per-FoF seeding rule stands as a standing constraint |
