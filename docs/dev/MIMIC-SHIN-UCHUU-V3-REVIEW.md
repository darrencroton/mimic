**Verdict: PASS WITH RISKS. No P0 or P1 defect was found anywhere in the range.** The plan's goals are met and evidenced: the Consistent-Trees ASCII route emits forest-blocked version 3 datasets whose `SourceHaloID` is the (`ForestIndex`, `HaloRankInForest`) position; `micro-uchuu-ascii-horizontal` and `shin-uchuu` are version 3 packages; the rewriter's `noop` and `cut` operations, the census, the bounded battery and the comparator's alternate modes are correct as read, as tested, and as probed with adversarial inputs the panel built; the horizontal driver's peak-occupancy partition weighting is correct and its Python mirror in the census agrees with the C code on 3,000 random cases; version 2 is gone from the code with no dangling import, and the fixtures regenerate byte-identically. **What the review found instead of bugs is thinner-than-claimed proof and deletion residue.** Twenty P2 items, none of which changes a verdict on real data today:

- **Validation strength.** The cut's per-slab "proof" accepts chains that loop away from their head; the cut's verification has no negative test; three bounded-battery detectors can be deleted with no test failing, and two of those deletions turn a FAIL into a PASS on constructed inputs; the comparator's self-check misses seven targeted mutants of the new code, and its alternate matching modes never check that a galaxy's persistent id stays paired across snapshots. Every production verdict in the record ran the strict default mode or both batteries, so none of these touches a recorded result; they are the guards the cut-vertical follow-on will lean on.
- **Fail-fast and robustness.** `forest_census.py trees` loads about 25 GB of index files before refusing a gapped dataset; `trees` and `table` never range-check `ForestIndex` and end in a traceback after a full pass; `noop` and `cut` silently drop extra input objects; `convert_trees.py` returns exit 1 for a refusal and for a validation FAIL alike while every other CLI returns 2.

- **Documentation of record.** The CHANGELOG's Unreleased section is a chronological log that describes the deleted `migrate` operation and the version 2 distribution refusal as live features of the coming release; the converter manual's census production table breaks the owner's user-facing rule (wall times, "Mac Studio", allocator narrative) and misstates its provenance; an occupancy docstring under-estimates disk by 2.6×; two package documents state something false about the code.

### P2: validation strength (the proofs are weaker than their docstrings)

1. **[A-1] The cut's per-slab chain checks accept cycles.** `rewriter/passes.py:1108-1118` (FoF) and `:1123-1139` (progenitor) check that chained members share their central or descendant, are unique, and are as many as the non-heads. A chain that leaves its head (`next_fof[head] = -1`) while the other members form a cycle, or a progenitor cycle disconnected from the `FirstProgenitor` head, passes both counts. Probe: a cut with an injected progenitor cycle completed with every slab "verified"; only `convert_trees.py validate` caught it. The current writer cannot emit a cycle, so no produced dataset is affected; the guard matters for the follow-on. Fix: assert `next_fof[i]` is −1 or `i+1` for FoF chains (they are written contiguous), and walk progenitor chains from their heads (pointer doubling) to prove reachability.
2. **[A-2] The cut's verification has no negative test.** With `_verify_cut` patched to a no-op, all 48 rewriter tests pass; with `verify_slab` patched out, only the one noop corruption test fails. Fix: four to six cut corruption cases with the existing `mock.patch` pattern (a swapped link, a wrong companion snapshot, a promoted halo kept as satellite, a mis-ranked row, a cycle).
3. **[A-3] `noop` and `cut` silently drop extra input objects.** An extra `/halos` column, header attribute, root group and sidecar dataset were added to an input; both operations completed and the output lacks all four. `rewriter/inputs.py:401-426`, `:759-763`, `:884-896` compare nothing about the object sets, nor does `horizontal_dataset.py`. Reachable only from a non-conforming input (the battery would refuse it), hence P2. Fix: about 20 lines in `prepare` refusing any object the format does not name.
4. **[C1-1] The bounded battery's second position bitset has no test of its own** (`validate_bounded.py:1030-1034`, the PD-R4-2 resolution). Emptying its repeats leaves all 25 bounded tests passing because the suite's repeated-pair corruption is caught by the position-identity check. With position identity off (the state of a sampled L-Halo or forests-HDF5 conversion) and the bitset disabled, bounded gives `identity: PASS` where external-sort gives FAIL. Reachable via `validate --bounded` on an adjacent sampled prelinked conversion with a repeated pair. Fix: an agreement case where position identity does not apply, asserting the uniqueness kind in the bounded detail.
5. **[C1-2] Two more bounded detectors can be deleted without a test failing.** (a) `NextProgenitor` membership within a snapshot (`validate_bounded.py:800`): a chain cut after its head with another chain's tail pointed at the orphaned member keeps every halo reached once; both modes FAIL today, bounded PASSes with the detector gone. (b) ASCII forest density (`_identity_totals`, `:976`), the only catch for an empty ASCII forest inside `[0, F)`. The agreement tests compare check statuses only, so a failure kind can vanish inside a check that also fails for another reason. Fix: single-fault corruptions, or assert each mutation's expected failure-kind text in both modes.
6. **[E-1] The comparator's alternate modes never check that a persistent id stays paired across snapshots** (`scripts/compare_cross_format_identity.py:1125-1131`). `UniqueGalaxyID` is "Persistent run-scoped" (`core_properties.yaml:84`: assigned at the creation halo and inherited), but in `--match-by-catalogue-id` and `--match-created-by-lineage` the field is skipped outright and nothing replaces it. Probe: one run relabels a galaxy's id at snapshot 6 with identical physics; catalogue mode exits 0 "identical". The docstring's "changes only how records are paired, never what a pair must agree on" (`:46-47`) overstates. Both production gates ran the strict default mode, so no recorded verdict depends on this. Fix: require the same (left id, right id) pairing on consecutive snapshots (16 B per pair) and name the exclusions in `--help`.
7. **[E-3] The comparator self-test misses seven targeted mutants of the new code** (the two control mutants are killed, so the harness works): unpaired rows outside the split forests dropped under the cut report (`:1027`); unpaired tree rows not failed under catalogue pairing (`:1029`); the zero-id check removed in matched mode (`:1096`); created rows' central ignored (`:1133`); a duplicate created key unchecked (`:1012`); the two cut input errors removed (`:1046`, `:869`). The first two are false-PASS class. Fix: one small fixture case each.

### P2: fail-fast, robustness and conventions

8. **[B-1] `forest_census.py trees` loads the index files before refusing a gapped dataset or a foreign aggregate directory** (`forest_census.py:280-294` vs `census/trees.py:521-532`). `load_index` is about 25 GB and minutes at Shin-Uchuu; the `links_adjacent` and `bind` refusals come after it. Reproduced with a probe. `cmd_table` orders this correctly through `prepare_table`; `trees` is the odd one out. Fix: a `prepare_trees` that refuses before `load_index`, with a test asserting `load_index` is not called.
9. **[B-2] `trees` and `table` never range-check `ForestIndex`; a bad value is an `IndexError` traceback, exit 1, after the whole of pass 2** (`trees.py:181-195`, `:558`, `:564`). `occupancy` checks `[0, n_forests_total)` (`occupancy.py:128-134`) but `table` does not require `occupancy`. Reachable only on a corrupt dataset, but it costs a full 22.5 G-halo pass and breaks "name the offending value, exit 2". Fix: check each block's min and max in `enumerate_roots` and `_label_slab`. Related: `range_rows` and `install_pieces` assume forest-blocked slabs without checking or stating it.
10. **[C1-3] `convert_trees.py` returns exit 1 for a refusal and for a validation FAIL alike** (`convert_trees.py:917-919`, pinned by `tests/test_cli.py:463`), while `rewrite_trees.py`, `forest_census.py` and `subset.py` return 2 on refusals. The bounded mode added refusals an operator must act on (rerun without `--bounded`; raise the budget) that a script cannot tell from an invalid dataset. The manual documents exit 1 only for FAIL (`README.md:53`). Fix: return 2 for `ConverterError`, 1 for a battery FAIL; update the pinned test and the manual.
11. **[C1-4] The format document's validator rule is contradicted by the bounded mode.** `HORIZONTAL-HDF5-FORMAT.md:499` says a validator must not require a whole-snapshot resident array to check a snapshot above INT32_MAX rows; the bounded mode holds 64 B per widest-snapshot row as whole-snapshot columns and does not refuse such a snapshot. No impact at Shin-Uchuu (widest 5.19e8 rows). Fix: refuse by name in the bounded preflight, or carve the mode out in the document and name `validate_bounded.py` beside `validate_v3.py` at `:511`.
12. **[A-4] The `del` statements in `_cut_chains` free nothing** (`rewriter/passes.py:481`, `:503`, `:505`, `:506`): `rank_slab` still holds its own references to the arrays it passed in, so about 49 B × n (about 25 GB at Shin-Uchuu) stays resident through pass 1, the run's peak phase. The measured 298 B × n already includes it, so the published figure is honest, but the code reads as if it were released. Fix: drop the caller's references before the call (splitting `rank_slab` does this naturally), then re-measure.
13. **[E-2] Structured-key pairing is the comparator's runtime and memory peak at production scale** (`:636-699`). Measured 18.9 s per 8 M rows per side against 0.21 s for an int64 sort, so roughly 25 min plus about 10 min of duplicate checks per output snapshot at 490 M rows; the `numpy.unique(return_inverse)` on the structured key is the 210 B per row peak. `SnapNum` equals the output snapshot on every row (`src/core/output_buffer.c:48`) and is compared byte for byte anyway, so the key can be int64 `MostBoundID` (plus the ordinal for created rows) with no loss. T-S14-3 understated this.
